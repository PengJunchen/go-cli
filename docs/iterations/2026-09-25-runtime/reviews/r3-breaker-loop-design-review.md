# R3 breaker and loop enforcement design review

Reviewed handoff snapshot `23b66de700f57a7c6b764550b73e865b74854d52` (`codex/runtime-r3-breaker-loop-handoff`), whose stated source baseline is `9258330489847c752cec29f7d933ee46e71788e`. This is a source-backed design review only; no product code or tests were changed or run.

## Review result

The design is implementable with two required corrections and one lifecycle prerequisite. Keep the breaker in its present wrapper position and define its ticket over one **logical model call**: the single call through the wrapper containing failover and retry. A ticket may therefore cover several synchronous `Stream` setup attempts before one channel is returned. This slice does not create an operation-wide provider-attempt budget or `AttemptID`; that remains R3-REM-01 work.

Before the breaker can treat channel close as joined completion, every stream-owning layer in the default chain must make close transitive: cancel on early failure, then have that same reader discard and drain its input through close, and only then close its output. The present wrappers do not meet that condition. This may be delivered as a small source-close/join prerequisite before the ticket change; it does not require moving wrappers or adding a general stream-supervisor framework.

## Required corrections

### 1. Durable loop termination must agree with live run status

The current canonical loop defers the durable terminal write inside `LoopAgent.RunCanonical` (`internal/core/loop.go`, `RunCanonical`). That defer calls `terminalOutcome(runErr)` before the outer CLI `loopDetectorMiddleware` can inspect the cancel cause (`internal/cli/assemble.go`, `canonicalLoopDetectorLoop.RunCanonical`). `terminalOutcome` currently maps any `context.Canceled` to `RunOutcomeCancelled` (`internal/core/run_commit_consumer.go`, `terminalOutcome`). A terminate disposition that cancels the child run and is converted to `ErrLoopDetected` only by the outer wrapper can therefore return an error to `TurnRunner` while the durable checkpoint says “cancelled”. The live `RunOwner` classifies a non-cancellation error as `RunOutcomeError` (`internal/core/run_owner.go`, `runOwner.run`), leaving three disagreeing results.

Normalize a confirmed `ErrLoopDetected` cause inside `LoopAgent.RunCanonical` before its terminal-commit defer runs. The durable `terminalOutcome` mapping must classify that dedicated typed failure as `RunOutcomeError`; the outer loop wrapper must return the same typed failure. Do not wrap or join `context.Canceled` into the public loop-detection error, because that would let `RunOwner` classify it as user cancellation. Preserve first-cause semantics: if parent cancellation wins first, it remains cancellation; a later detector signal cannot replace it. A detector signal that wins first remains an error even if the parent cancels during cleanup. Keep terminal persistence owned by the existing run commit and run owner code.

Acceptance must exercise the real canonical loop, prepared registry, run owner, and durable commit path. Assert `errors.Is(returnedErr, ErrLoopDetected)`, the durable terminal outcome is `RunOutcomeError`, and the same run's `RunStatusSource` snapshot reports `RunOutcomeError`; also assert the triggering prepared call does not execute, no later provider call is made, and each assistant tool call has exactly one receipt. Add the inverse race case where user cancellation is already the first cause and both durable and live status remain `RunOutcomeCancelled`. An assertion on the middleware's returned error alone does not close this boundary.

### 2. Define breaker accounting at the existing logical-call boundary

`newModelWrapperWithChain` applies the middleware chain first, then telemetry, then `circuitBreakerModel`, then the outer output guard (`internal/cli/output_guard_adapter.go`). Within the chain, failover and retry call `next.Stream` repeatedly only while setup returns a synchronous error (`internal/llm/middleware_failover.go`, `failoverModel.Stream`; `internal/llm/middleware_retry.go`, `retryModel.Stream`). They do not replay a stream error after returning a channel. Do not move the breaker inside those wrappers: that changes timeout, sanitize, retry, and failover ordering and would make one user model call consume multiple tickets.

One ticket is admitted for the outer breaker-wrapped logical call. If retry/failover makes two setup requests and then returns a valid stream, the ticket records one success only after that stream's valid terminal and joined close. If setup attempts exhaust synchronously, the one ticket records the final logical-call failure. Once a channel has been handed out, a midstream error is terminal for that logical call and must not cause retry/failover replay. This distinction is important: a one-request midstream-error test proves “no replay after channel handoff”; it says nothing about setup retry count or per-operation attempt limits.

Use the existing `DefaultCircuitBreaker` as the only state machine. Its current synchronous `Execute` records when its closure returns (`internal/production/circuit.go`); add a one-shot stream ticket to that state machine and retain `Execute` for `Generate`. A ticket must complete once, reserve/release the existing HalfOpen probe slot correctly, and not let a late or duplicate completion mutate a later state. Cancellation is neutral only when the actual caller canceled. A timeout, malformed terminal, candidate/stream cap abort, or wrapper-local cancellation while the caller remains live is a failure. In particular, checking only `ctx.Err()` at the breaker is insufficient: the breaker is inside output guard, and core also creates a child stream context. A locally canceled child can otherwise make a wrapper failure look like caller cancellation. Keep local abort causes or terminal failures distinguishable from inherited caller cancellation.

Keep open-circuit failure typed (`errors.Is(err, ErrCircuitOpen)`) and do not synthesize assistant text or a successful `Final`. A valid provider stream rejected later by the outer output guard remains breaker success, because that guard runs after the breaker and must finish reading the provider stream before it checks the candidate.

Add an assembled setup-retry test with a local provider that fails the first synchronous stream setup and succeeds the next. It should show multiple setup requests inside one logical call but only the final successful ticket result. Retain a separate one-request midstream-error test to prove no replay after handoff. Also verify a HalfOpen probe remains reserved until source close, open calls make no provider request, and a guard denial after provider close does not mark the breaker failed.

## Source-close and join inventory

The close-after-join contract must be implemented at each layer, in the existing order. Each layer owns only the channel it reads; cancellation must switch that same reader to discard/drain mode rather than starting a second competing reader. If a source ignores cancellation, that wrapper stays pending until it closes; do not close the wrapper channel early or report quiescence. The bounded RunOwner cleanup path can then retain cleanup-pending state for a non-cooperative custom model.

This inventory is a finite implementation checklist, not a request for a new supervisor abstraction. Preserve wrapper ordering. At each layer test cancellation, error chunk, cap/malformed terminal, final followed by close, and source close without final. A successful close at an outer layer is trustworthy only if every inner layer followed the same contract.

## Smallest builder sequence and acceptance

1. **Source-close prerequisite.** Update the `BaseChatModel.Stream` contract and the layers above so every owned reader has one pump, cancels on early failure, drains that source to close, and closes its output only after the inner worker/resource has joined. Hold terminal markers where a wrapper can still reject the complete stream (notably loop detection and overflow). Do not block waiting for a non-cooperative source in a second goroutine; the current owner should remain pending. Add a table-driven fake source that signals `ctx.Done`, waits for a test release, then closes; assert each wrapper's output remains open until release. Verify the real HTTP provider server observes cancellation and returns only after its response reader/body has closed.
2. **Logical-call breaker ticket.** Add an optional streaming-ticket interface to the existing breaker, with typed open/unsupported errors, one-shot completion, and neutral HalfOpen release only for actual caller cancellation. Keep Generate on `Execute`, keep wrapper placement unchanged, and test `reset`/concurrent completion so stale tickets cannot alter a newer state. The assembled ticket pump must classify setup exhaustion once or a returned stream only after final-plus-close.
3. **Prepared loop observation and termination.** Add only the frozen identity+digest value and synchronous callback to the existing prepared stages, after normalization/schema/mutation validation/freeze and before policy. Install a per-run detector session via run context; do not keep run counters in the process-global detector. Preserve warn as default and its next-turn reminder. Terminate is opt-in; its typed cause cancels the run and normalizes to `RunOutcomeError` before the durable terminal defer. The prepared fact is not approval, dispatch, execution, receipt, or mutation proof.
4. **Real-path tests.** In addition to named handoff tests, cover (a) setup error then retry/fallback success with more than one setup request but one logical ticket; (b) one midstream terminal failure with no replay; (c) HalfOpen ticket held until source close; (d) actual user cancellation neutral versus timeout/guard/protocol local abort failure; (e) every wrapper's cancel/error/cap join; (f) real sequential and parallel prepared observation, no trigger-call dispatch, exactly one receipt per proposed call, run isolation and warn default; and (g) durable terminal outcome equal to live `RunStatus` on loop termination and on user cancellation.

The handoff's existing race gate across `internal/production`, `internal/llm`, `internal/tools`, `internal/core`, and `internal/cli` remains appropriate after the changes. Passing this slice does not establish provider-attempt budgeting, full R3 retry/replay guarantees, or successful shutdown of a non-cooperative custom stream source.
