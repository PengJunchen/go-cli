# R8 streaming renderer primitive review

Reviewed fixed commit `152269b2635f7c87337e960b21f2fab1197d924d` in a fresh detached worktree. The commit adds only `internal/tui/streaming_markdown.go`, `internal/tui/streaming_markdown_chunk_test.go`, and `internal/tui/streaming_markdown_chunk_bench_test.go`. This is a primitive review; `RenderIncremental` remains the existing app path, so this does not establish an app-level streaming optimization.

## Decision

**Not accepted yet.** The following retained-window and wrapping bounds are not upheld by the current implementation.

1. **[P1] Bounded logical lengths still retain the full backing allocation.** The append path stores `part` slices directly in `windowLineParts` (`consumeASCIITextRun` → `appendWindowPart` at `internal/tui/streaming_markdown.go:332-366, 578-602`). A review probe passed a 1 MiB ASCII chunk at width 80; the renderer's final open part was short but its data pointer still addressed the original 1 MiB chunk. The more serious finish path is `Finish` → `replaceWindowWithText`: `Finish` creates the full `rendered` string, and `replaceWindowWithText` stores `strings.Split` substrings without cloning (`:144-157, 654-697`). A 512 KiB synthetic rendered input left only 256 visible bytes and a 511-byte `Window().Content`, but a retained `windowLines` element still pointed into the full 512 KiB allocation. The current stats count string lengths, not the backing bytes kept alive. Clone retained line fragments/parts or otherwise copy them into storage whose allocation is actually bounded. The source tail ring is bounded; this finding concerns retained window strings.

2. **[P1] The pending grapheme bypasses both wrapping and the 64 KiB output budget.** `Window` appends `graphemePending` after current line parts without checking the cell column or byte/line limits (`:162-185`). Review probes returned `"abcd"` as one 4-cell line at width 3, `"界界"` as one 4-cell line at width 2 even though each grapheme fits by itself, and `"✈️x"` as one 3-cell line at width 1. A single overwide grapheme may exceed width, but these outputs also keep the following renderable content on that same line. With width 65,536 and 65,537 ASCII bytes, `Window().Content` was 65,537 bytes and `HasHiddenPrefix` remained false. Include pending bytes in layout and bound enforcement; strengthen the grapheme test to assert per-line widths for sequences of two fitting wide graphemes rather than allowing `width*2`.

3. **[P2] Finish can cut the retained source tail inside a grapheme.** `setSourceTail` moves its cutoff to a UTF-8 rune start, not a grapheme boundary (`:543-576`). A source consisting of `head`, `e\u0301`, then 65,534 `x` bytes was retained from the combining mark U+0301 onward, dropping its `e` base. `Resize` subsequently reflows only this suffix, so it cannot restore the original grapheme. Keep the first retained suffix at a grapheme boundary (or discard the partial leading cluster and mark the hidden prefix).

## Other contract edges

- `Finish` calls `md.Render` on every invocation. Two identical calls produced `markdownRenderCalls == 2` and the same window. The current API does not say whether a terminal finish may be repeated; if callers can repeat it, either define single-shot ownership explicitly or make repeated finish idempotent without retaining the canonical full source.
- `AppendChunk` itself visits new chunk bytes and does not invoke `RenderIncremental`; the stats test that equates `parserBytes` with `inputBytes` is not independent work instrumentation because both counters are incremented by the same input length. `Window` does rebuild and allocate the current bounded string on every append. The added append benchmark is the right place to measure that overhead, but its `SetBytes(1<<20)` does not match the data sent: integer division gives 1,048 bytes × 1,000 chunks = 1,048,000 bytes, 576 fewer than 1 MiB. No independent chunk-scaling benchmark was run for this review.
- `Finish` performs one whole-document Glamour call per invocation, as required to preserve canonical Markdown semantics. That is an expected full-input operation, but no latency or peak-memory bound follows from call count alone. The aborted large Glamour render is not performance evidence. The full render output is also the source of finding 1's backing-allocation retention.

## Independent verification

`rtk proxy go test -list '^TestStreamingMarkdown' ./internal/tui` listed the 10 committed chunk/finish tests. `rtk proxy env GOMAXPROCS=2 go test -race -p 2 ./internal/tui -run '^TestStreamingMarkdown' -count=1` passed.

Review-only probes were added to the detached review worktree, listed with `rtk proxy go test -list '^TestReviewRenderer' ./internal/tui`, run with `rtk proxy go test -v ./internal/tui -run '^TestReviewRenderer' -count=1`, then removed. All six probes passed while asserting the reproduced problematic states above: live line overflow, 65,537-byte window, retained input backing for append and replacement, a source tail beginning with a combining mark, and repeated Finish rendering. They are not part of the reviewed commit. No benchmark, full package race, app integration, or PTY claim is made here.
