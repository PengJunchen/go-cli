# R3 production resilience remaining contract

Status: source-grounded design proposal for `R3-BLD-02`; no product code or execution ledger changed. Source snapshot: `07dddc1492a9b3631e2d1b5d997f654c5883b88e` (2026-09-25). The execution task remains `pending` in `execution-tasks.json:908-945`.

This document covers the remaining production wiring for retries, the circuit breaker, loop detection, usage/cost reporting, provider-body bounds, and tool-cache privacy. It does not redesign session persistence or compaction (`R3-BLD-03`), and it does not repeat the bounded MaxAttempts/cancellation/typed-error-classification fix tracked by `r3-retry-safety-handoff.md` / `r3-retry-safety-review.md`. That local fix must still be integrated and retested; this document does not treat it as already present at this snapshot. The accepted R3 contract review is `reviews/r3-contract-review.md`; this is an implementation map against it, not a replacement contract.

## Findings at a glance

## Source evidence and boundaries

### Retry authority and dispatch budgets

`assembleProductionResilience` creates a production retry policy with `MaxAttempts: 3` and installs it in the standard LLM middleware chain (`internal/cli/assemble.go:1167-1190`). The default chain is ordered failover → retry → timeout → sanitize → model-loop detection → validation → overflow (`assemble.go:1182-1190`; `internal/llm/middleware_chain.go:83-96`). `RetryModelMiddleware.Generate` and its synchronous `Stream` setup loop call the next model and independently ask `RetryPolicy.ShouldRetry` (`internal/llm/middleware_retry.go:247-282,285-320`). `OverflowRecoveryMiddleware` separately loops over its own `maxRetries` (`internal/llm/middleware_overflow.go:53-64,87-125,153-330`); a successful `finish_reason=length` may also trigger its own Generate continuation outside the core-owned path (`:97-106,353-428`). Failover owns another candidate loop when fallback models are present (`internal/llm/middleware_failover.go:85-133`).

These are real nested dispatch paths; the shared `MaxAttempts` contract is not enforced by any one of them. The current production retry policy accepts only `ctx` + `error` + local attempt index (`internal/production/retry.go:82-90`) and has no `AttemptID`, dispatch state, candidate-visible state, tool-dispatch state, durable acknowledgement, selected model identity, or worker-quiescence fact. The R1/R2 owner already controls run/tool lifecycle, but the model middleware still decides and dispatches its own retries. In particular, `LoopOwnsContinuation` suppresses middleware-owned length continuation; it does not disable overflow error retries (`middleware_overflow.go:153-160,241-255`).

This contradicts the approved R3 ownership rule: the still-running Loop makes one retry/fallback decision using typed facts; retry, fallback, and overflow retry consume the same operation-wide dispatch budget; a restart never replays an acknowledged incomplete run (`r3-provider-design.md:146-170,174-186`; `reviews/r3-contract-review.md:33-39`). Keep the separately owned local retry-count/cancellation/classification fix intact, then remove retry authority from nested wrappers in the minimum order below. Length continuation remains its own existing bounded run policy; it is not another local retry budget.

Streaming currently retries only a synchronous `Stream()` error. Once a channel is returned, `retryModel.Stream` returns it and does not restart on a later chunk error (`middleware_retry.go:285-320`). That is a useful safety property: it does not transparently replay after a partial stream. Keep it. The remaining gap is to surface stream terminal facts to the run owner and to account every attempted dispatch, including failures without usage; do not broaden retrying to channel errors.

### Circuit breaker

The generic state machine in `internal/production/circuit.go:82-147,186-220` is a reasonable synchronous breaker: it admits Closed/HalfOpen calls, records the returned error, and transitions under a mutex. The model adapter is not terminal-aware. `circuitBreakerModel.Stream` runs `breaker.Execute` around `m.inner.Stream(...)`; the closure returns as soon as the channel is created, so `Execute` records success at `output_guard_adapter.go:274-301`, before any `MessageChunk` or terminal error is consumed. Mid-stream provider errors are therefore invisible to the breaker even though `MessageChunk.Error` is the contract for propagating those errors (`internal/llm/llm.go:75-103`).

When open, both Generate and Stream synthesize ordinary assistant content, return nil error, and let the caller treat it as a successful answer (`output_guard_adapter.go:248-271,274-301`). That fallback can be displayed/persisted as assistant output and does not express “provider not dispatched / breaker open.” Prefer a typed terminal `ErrCircuitOpen` on the normal failure path. If product keeps fallback text, represent it as an explicit local fallback outcome, never as provider success or provider usage.

The breaker wraps the middleware chain before the outer output guard (`output_guard_adapter.go:375-400`). Count provider terminal outcomes, not output-guard rejection. The wrapper should complete one breaker decision after the stream reaches a valid Final or a typed Error/early close; do not retry after a yielded candidate merely to repair a breaker count.

### Loop detection

The component-level `DefaultLoopDetector` is reusable and thread-safe, with edit/test/tool counters and a `Reset` method (`internal/production/loop.go:136-220,230-338`). Its current Assembly adapter does not monitor an active run. `loopDetectorLoop.Run` and `canonicalLoopDetectorLoop.RunCanonical` first wait for the entire delegate run to return, skip observation on any run error, then observe the returned slice and add a reminder (`internal/cli/assemble.go:2550-2595`). It never cancels the active run, and it ignores `LoopDetectionResult.Disposition`; Assembly constructs the detector with the default `warn` disposition (`assemble.go:1487-1498`). The thresholds/config are wired, but the “stop active run” behavior is absent.

There is also a classification mismatch. The detector defaults `ToolCallKind` to `"tool"` (`internal/production/loop.go:184-190`), while `LoopAgent` emits `AgentEvent{Kind:"tool_call"}` in sequential and parallel paths (`internal/core/loop.go:726,839`). The production adapter passes those real events unmodified. Its existing “core events” test uses the detector's synthetic `KindToolCall` constant (`internal/production/production_e2e_test.go:401-414`), not the actual emitted kind. Actual tool calls therefore do not increment the default same-tool detector. Core does not emit `edit` or `test_failure` kinds in the run path; actual tool results use `tool_result` plus `IsError` and `ToolCallID` (`internal/core/loop.go:737,763-784,844-870`; `internal/core/types.go:63-99`).

Even after kind mapping, `tool_call` currently carries only `Content: tc.Name` and `ToolCallID`, not arguments (`internal/core/loop.go:726,839`). `DefaultLoopDetector` hashes `event.Content` as the “tool-call payload” (`internal/production/loop.go:195-228`), so same-name calls with different args would be treated as identical. Reuse a non-sensitive digest derived from authoritative structured call args or a narrow typed event field; do not log raw args. Scope detector state by the existing RunID/run context and reset/close it at terminal. It currently accumulates counters across every successful REPL turn, never calls `Reset`, and continues returning the same detection after threshold (`loop.go:298-338`; `assemble.go:2577-2594`).

The separate `llm.LoopDetectionModelMiddleware` is present in the standard chain (`assemble.go:1186-1189`), but it detects repeated response text rather than repeated core tool actions. Its stream wrapper forwards chunks before checking the final accumulated response (`internal/llm/middleware_loopdetect.go:138-213`). Default Assembly's complete-response guard suppresses incremental publication until candidate validation (`core/loop.go:1248-1258,1363-1380`); preserve this ordering. Do not count the response-text middleware as proof that tool-loop detection can stop a live Loop.

### Usage, cost, and budget semantics

There is already a sound provider-to-core stream usage path: `MessageChunk.Usage` is defined for the final chunk (`internal/llm/llm.go:89-96`), the HTTP stream parser fills it when usage is present (`internal/llm/provider.go:395-400,419-445`), and `LoopAgent.streamGenerateWithBudget` carries it into the completed `llm.Message` (`internal/core/loop.go:1205-1225`). Existing provider and core tests cover those projections (`internal/llm/stream_usage_test.go`, `internal/core/loop_usage_test.go`). This does **not** reach production cost accounting: `costTrackingModel.Stream` and `telemetryModel.Stream` only delegate (`internal/production/llm_integration.go:129-134`, `internal/cli/output_guard_adapter.go:304-332`), while `recordUsage` is called only by a successful Generate with nonnil usage (`llm_integration.go:120-161`). Terminal errors with usage and failed-but-dispatched provider attempts are also not recorded.

The current tracker has fixed approximate cost tiers explicitly documented as estimates, not billing (`internal/production/cost_tracking.go:16-38`). Unknown model names make `CalculateCost` fail (`:116-130`); the wrapper then only logs the failure and drops the call (`llm_integration.go:147-153`). The wrapper captures `modelName` at assembly time (`assemble.go:1175-1180`), while `/model` switch later calls `LoopAgent.SetModel` (`assemble.go:801-820`; `internal/core/loop.go:351-358`) and `RunCanonical` applies the same wrapper to that selected model on each run (`loop.go:443-451`). Without replacing the wrapper identity, switched models can be charged under the original configured name or silently fall outside the tier map. The same wrapper is injected into subagents (`assemble.go:1291-1293`); `CostTracker.RecordSubagent` exists but source references show only its definition and tests, not default production recording (`internal/production/cost_tracking.go:218-260`).

`/cost` always prints numeric totals and calls (`internal/cli/slash_handlers.go:46-82`). `emitTokenUsageEvent` prefers the last assistant API Usage or estimates from history, but the event has no source/estimated/unknown marker (`internal/cli/interactive.go:163-214`; `internal/core/types.go:102-112`). Thus a zero tracker value/call count can mean “stream usage was never recorded” or “model price unknown,” not zero provider use; estimated token values can be presented with the same shape as provider-reported values. The accepted R3 contract requires `AttemptID`, actual resolved ProviderID/ModelID, dispatch outcome, reported usage/source, price/cost source, one record per dispatched attempt, and `unknown` rather than zero for absent usage/price (`r3-provider-design.md:144-164`; `reviews/r3-contract-review.md:50,64`). Keep accounting out of the R2 action ledger.

There is no CLI budget setting or callback. Assembly calls `NewCostTracker(nil)` and does not call `SetBudgetLimit` or `SetBudgetCallback` (`internal/cli/assemble.go:1173`); defaults make a zero budget “no limit” (`internal/production/cost_tracking.go:102-113,181-215`). `recordUsage` discards a `BudgetExceededError` after logging (`llm_integration.go:147-153`). The R3 provider design explicitly leaves hard/soft admission out until PRD-04 defines behavior (`r3-provider-design.md:148-150,171`; `reviews/r3-contract-review.md:52`). Do not introduce a default hard cap or cancel a run from this task. If PRD-04 is approved later, budget enforcement belongs at provider-request admission in the run owner, not in post-hoc `CostTracker.Record`.

### Provider body bounds and output sanitization

Default compatible provider streaming is bounded: `GuardedStreamMaxBytes=400000`, `GuardedStreamMaxChunks=16384`, and `GuardedStreamMaxToolCalls=4096` (`internal/llm/stream_limits.go:8-14`); the SSE parser and JSON stream sniff path enforce the byte cap (`internal/llm/sse_parser.go:57,107-131,170-185`). The complete output-guard wrapper also counts retained text/chunks and checks full candidate payload before returning a final chunk (`internal/cli/output_guard_adapter.go:115-235`). In Loop-owned continuation mode it leaves the full-candidate check to core, which disables incremental publication for a guarded candidate (`output_guard_adapter.go:66-74`; `internal/core/loop.go:1248-1258,1363-1380`). This is a sound default safety boundary.

Provider body reads are less bounded. The active OpenAI-compatible `roundTrip` reads a non-2xx body with unbounded `io.ReadAll` and truncates the string only after allocation (`internal/llm/provider.go:513-530`). Successful `Generate` decodes directly from the body with no byte ceiling (`provider.go:229-264`). The stream JSON-detection path does cap bodies, but `roundTrip` error responses still have the unbounded read above. Native `Generate` reads both error and success bodies with `io.ReadAll` (`internal/llm/native.go:200-212`), and native streaming setup reads error bodies with `io.ReadAll` (`:268-280`); native adapters remain separately gated and must not be made default by this task. `ProviderError.Error()` intentionally excludes the raw message (`internal/llm/provider_error.go:33-64`), which is good for log safety, but it does not bound retained/allocated body bytes.

Use a single bounded-read helper for success and error payloads: read at most `limit+1`, reject/mark oversize, close the body, retain only typed status/category and a bounded safe diagnostic (or an explicit truncation bit), and never log the free-form body. Ensure overflow classification still uses a bounded typed indicator rather than retaining an unbounded response. Test an over-limit success JSON body and non-2xx body against an httptest provider, asserting deterministic failure and bounded evidence. Keep stream cap and generation cap names/limits explicit; do not conflate them with context/compaction budgets.

The default assembly creates `s.idempotentCache` and exposes it through `ProductionResilience`, but `assembleProductionResilience` installs `newProductionToolWrapper(nil, ...)` (`internal/cli/assemble.go:1204-1205,1233-1235,452`). The wrapper computes `toolCacheKey` before checking whether a cache exists, but with `cache == nil` it performs no `Get`/`Set`; therefore the ordinary assembled tool path does not currently leak arguments through cache-hit logging or return cached tool results. The helper's non-nil-cache path remains unsafe: the raw JSON key is copied into a span attribute and debug log by `FIFOIdempotentCache.Get` (`internal/production/idempotent.go:60-79`), its size grows with the arguments, and JSON marshal failure falls back to the tool name alone (`assemble.go:2671-2679`), aliasing distinct calls. Treat this as a library/injected-wrapper privacy defect plus an assembly capability mismatch, not a confirmed default-flow leak. Before wiring the exposed cache into default execution, decide whether caching is intended there; if enabled, use a bounded digest over canonical args and tool name, remove raw key instrumentation, and bypass on encoding/size failure. If default caching remains disabled, retain the non-nil helper-path regression without claiming that ordinary CLI tool calls use the cache. The audit entry already hashes args/results (`assemble.go:2691-2715`), so preserve that privacy property.

The default output guard buffers and checks the complete logical response, so marker matching across chunk boundaries should already work in this assembly path. The named `TestSanitizerMarkerAcrossChunks` is not currently present as a Go test; add it at the real `AssembleAgent`/fake-provider boundary. Split a canary secret across arbitrary transport chunks; assert it is never visible in incremental or final UI/core output, and that the complete sanitized candidate is the only candidate committed. Keep the existing complete-response buffer and 400k runtime cap. This is not a request for a second chunk-local sanitizer.

## Minimum implementation order

1. **Honor prerequisites and freeze attempt semantics.** Keep the fixed local retry safety patch (`a86de5be` plus its accepted follow-up) intact. The R3 design contract says R2 restart-safety is a builder/review gate even though the current task JSON lists only `R1-REV-01`; do not use durable input as permission to retry after process recovery (`r3-provider-design.md:196,205`; `r2-contract.md:203-204`). Reuse the current Loop owner and existing typed R1 outcome/RunID seams. Add one operation-scoped `AttemptID`/dispatch budget/fact handoff; do not create a second event store or retry runtime.
2. **Make middleware propose, not dispatch retry.** Remove local retry/failover/overflow replay loops from the active model boundary or convert them to typed candidates returned to the Loop. The Loop counts actual provider dispatches against one operation cap across retry/fallback/overflow; only it decides whether typed terminal/resource facts permit a retry. Preserve: no automatic retry after caller-visible candidate, completed assistant tool-call terminal, tool dispatch, or partial durable acknowledgement; cancellation/deadline never schedules a new attempt; stream channel errors do not replay by middleware. A live run may reuse its synchronized input/projection; recovery after restart must not dispatch again.
3. **Finish attempt result once, then update breaker and accounting.** The model adapter must report terminal stream result (including final usage/error) exactly once by AttemptID after channel/resource completion. Feed the same immutable attempt result to the breaker and CostTracker; breaker counts terminal provider failures, cost accounting stores every dispatched attempt including error-with-usage and unknown usage. Include actual model/provider identity, cost-estimate provenance, and usage-source (`reported`, `estimated`, `unknown`) in `/cost` and token usage presentation. Do not count attempt-local candidate guard errors as provider failures.
4. **Connect loop detection to live core events.** Use the existing event/RunID path, not a new polling service. Classify actual `tool_call` plus structured result/error events; map edit/test evidence only where the real tool/result schema supplies it. Use a stable digest for call args, not raw args or tool-name-only matching. Check after each relevant event; when threshold is reached, request cancellation through the owning Run context and let R1 retain the terminal/cleanup outcome. Reset detector state at run boundary or make the detector itself run-scoped. Keep the current post-run reminder as a follow-up user hint, not as the enforcement mechanism.
5. **Close privacy bounds in the real transport/cache paths.** Add bounded success/error body reads to the active compatible HTTP provider and preserve fail-closed typed diagnostics. Resolve whether the cache is a default capability before wiring it into prepared execution; in every non-nil cache path, hash bounded canonical keys and remove raw key span/log values, skipping cache on failed/oversize encoding. Keep output-guard whole-candidate buffering; test split markers and that no text is visible before final guard acceptance.
6. **Run whole-chain acceptance.** Use an `httptest` fake provider and real `AssembleAgent`, with deterministic read/tool fixtures and no external secrets/network. Assert actual dispatch count, exact typed terminal outcome, one record per provider attempt, correct selected model on `/model` switch, terminal breaker state, active-loop cancellation, body cap, no raw cache args in logs/spans, and sanitizer non-leakage. Run named tests with package race suites for `internal/llm`, `internal/core`, `internal/production`, `internal/cli`; verify every regex has a nonzero match count. Do not substitute component-only unit tests for this gate.
