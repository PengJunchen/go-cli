## Findings

- **Append publication follows file-sync success.** `Add` checks store availability under the write lock, marshals and enforces the serialized-row limit before writing, records the pre-append size, completes short writes, then syncs before changing `items` or the search index ([Add](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:190)). On append or sync error, rollback truncates to the recorded size and syncs. Either rollback error marks the store with `MemoryStorePoisonedError`; subsequent mutations fail at the availability gate. The uncertain branch does not reopen the file or claim the candidate record is physically absent ([rollback and availability gates](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:465)). Tests cover partial-write and sync failures with confirmed rollback, plus truncate and rollback-sync failures that poison the store ([append failure tests](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store_failure_test.go:17)).

- **The 1 MiB row limit excludes exactly one LF.** Append and rewrite compare the marshaled JSON length before adding LF. The reader accounts for a delimiter while bounding a row, accepts at most 1 MiB of JSON with or without a final LF, and rejects a larger record ([limit constant](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:25), [append limit check](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:205), [record reader](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:517)). Tests exercise one byte below, exact, and one byte above, verify the LF adds one byte on disk, reload the exact-limit row, and reject an oversized existing row ([boundary tests](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store_failure_test.go:297)).

- **Delete has a clear replacement commit point.** It builds a candidate map without mutating live state, fully writes and syncs the same-directory temporary file, closes it, then closes the old append handle and renames. Live items and the search index change only after rename succeeds. A post-rename reopen failure retains the deleted state and records `ErrMemoryStoreUnavailable`; pre-rename failure preserves the old state and attempts to restore its append handle, marking the store unavailable if that reopen fails ([replacement and restore paths](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:390)). Tests cover temp-write/sync/rename failures, sync-before-rename, post-rename reopen failure and reload, and delete after close ([delete failure tests](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store_failure_test.go:158)). `Close` serializes with mutations, sets the closed state once, and subsequent calls return nil ([Close](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:374)).

- **The fault-injection seam is local to each store.** The private `memoryFileIO` functions are initialized per instance; the reviewed code adds no package-global mutable hooks ([IO seam](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:65), [store-local initialization](/Users/pengjunchen/Documents/github/go-cli-runtime-worktrees/repair-20260929-memory/internal/memory/file_store.go:91)).

I found no blocker within the requested persistence scope. The reviewed behavior is per-store concurrency-safe; cross-process coordination is not introduced here.
