# R1b：跨进程长任务验收设计

状态：**设计已接受，尚未实现、尚未运行**。本设计不改变当前 Thinking 修复的 Go 源码冻结，也不把现有几项测试拼称为已通过的同一场景。R1b 后续采用独立测试提交，先验证失败对照，再实现测试与必要的通用修复。

## 要回答的业务问题

任务做了一半退出程序，再打开时，已有产物和进度是否保留？已完成的操作会不会重复？历史经过多次压缩后，工具还能否拿到继续工作所需的事实？这些是工程可靠性问题。真实模型是否能自主规划长任务、在复杂项目中保持方向，需要后续真实模型任务评分，不能由脚本回复证明。

## 固定最小场景

1. 使用实际构建的 race CLI 二进制、受控本地 HTTP/SSE peer、全新仓库与 HOME/XDG/TMP。自动 memory 显式关闭，持久 session 显式放在本次沙盒目录。session、工具、压缩实现保持原生。
2. Process A 接收 60 次用户提交，执行一组真实文件与 shell 工具，在 `task-state.json` 持久化任务 ID、随机 canary、版本和完成检查点。真实副作用写入 append-only 计数文件，标记该动作已完成。正常退出并验证退出码、进程退出和 session 落盘。
3. Process B 是新的 OS 进程，通过公开 `--resume-session` 接口恢复同一物理 session，再接收 60 次用户提交。继续前实际读取检查点，通过工具完成下一阶段文件变换。不得让驱动程序替 Agent 补写业务文件。
4. 为使测试短而可重复，单独声明低阈值 `truncating` 压缩压力配置。要求两个独立、来自真实执行路径的成功压缩事件，记录发生进程、轮次和 source/历史边界；不能把相同日志被复制两次算两次压缩。它是压力 profile，不代表公开模型比较的默认压缩策略。
5. 两进程退出后，由外部 grader 校验最终业务文件、任务 ID、canary、版本、完成阶段及副作用计数恰为一次；检查各工具 receipt、资源完成证明和待处理 action，不以 CLI exit 0 或一句“完成”代替验收。

## canary 的两条通道

- **必须保留的任务状态**：用户授权写入检查点文件的随机 canary。恢复后必须通过真实读取或持久状态取得；外部 grader 持有期望值。最终文件和检查点一起验，防止只报一句正确答案。
- **可被截断的早期对话**：仅首轮出现、没有授权持久化的另一枚 canary。记录其在压缩前后和恢复请求中的可见性。原生 truncating 会丢弃旧内容，这属于能力边界，不能为了让测试变绿而要求它保留全部早期对话。

脚本 peer 不能在最终回复或写文件参数中直接填入预知答案。它可以依据实际请求中的工具结果验证状态并发出下一步工具调用；这只能证明 Harness 的协议、工具与存储续接。需要真实模型运行才能评判模型是否主动记得保存、检索并利用事实。

## 先让验收本身经受失败对照

新增 R1b 测试前先验证 grader：不传 resume/改成新 session、删除任务检查点、重复执行已完成副作用，分别应被拒绝或评分失败。对照使用独立沙盒，不篡改正式运行产物。对于正常丢弃的早期对话 canary，仅产生观测结果，不伪装成必须修复的产品缺陷。

测试及故障修复继续遵循红→绿：只改变与触发场景有关的实现，不能直接关闭压缩、删除工具、跳过恢复或弱化资源完成检查。

## 每次输出的最小证据

| 证据 | 记录要求 |
|---|---|
| 版本 | 源码 commit/dirty patch、二进制 SHA、配置和 peer/grader SHA、测试环境 |
| 进程 | 两个不同 PID、启动/退出时间、退出码、恢复 session ID；race 结果 |
| 历史 | 每个实际请求的序号/哈希，当前输入存在；两次以上成功压缩及恢复后投影；canary 可见性 |
| 工具 | 调用与结果关联、成功/失败、资源完成证明、恢复前后 pending action、业务文件哈希和副作用计数 |
| 时间 | Process A/B 的 wall time、HTTP 时间、工具时间；构建与 grader 时间单列 |
| token | 全部主/辅助/摘要/失败请求的原始 usage 和缺失覆盖率；mock token 标为合成数据，不能当真实费用或模型效率 |
| 结论 | 工程续接通过/失败、事实丢失观测、未覆盖行为；不把“120 次用户输入”称为“120 步自主解题” |
