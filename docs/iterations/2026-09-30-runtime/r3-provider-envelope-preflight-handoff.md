# R3 first-request provider-envelope preflight handoff

Status: bounded designer handoff for the separate provider-envelope follow-up in `r3-acceptance-audit.md`. The budget section below proposes refining the earlier R3 compaction formula at this boundary, pending independent design review before implementation: the configured compaction ceiling remains a local message bound, while a known active-model limit bounds the complete provider envelope. Do not treat this clarification as approved until that review reconciles it with the older formula. This document does not close R3-DES-01, authorize a provider/protocol, or modify the durable current-submission repair. The R3 provider and compaction documents remain design contracts; R2 implementation and restart-safety review remain gates.

## Boundary and source evidence

The current Loop checks durable or non-durable message size at `loop.go:698-726`, then applies dynamic tool filtering at `728-746`, and dispatches the resulting messages/options at `1384-1387` ([`loop.go`](../../../internal/core/loop.go#L698)). The preflight receives only messages, estimator and the compaction ceiling. It cannot account for the tool schemas and provider envelope that the model will receive. The selector's `ModelInfo` has `InputTokenLimit`, `ContextWindow` and `MaxOutputTokens`, but these limits are not attached to the request at this boundary ([`llm.go`](../../../internal/llm/llm.go#L319), [`model_selector.go`](../../../internal/llm/model_selector.go#L848)).

The established compaction path treats `C` as a message-token ceiling: `MidTurnCompact` applies its 0.80 trigger ratio to the estimated message set, and `AssembleAgent` falls back to 8000 ([`midturn.go`](../../../internal/compaction/midturn.go#L70), [`assemble.go`](../../../internal/cli/assemble.go#L42), [`assemble.go`](../../../internal/cli/assemble.go#L581)). A separate provider envelope bound is available only when the active candidate supplies `InputTokenLimit`, or `ContextWindow` plus a known output reserve. The earlier draft used `C` as if it were a provider-wide request limit. An independent HTTP capture of the actual default Assembly path (39 registered tools, default threshold 30 at [`assemble.go`](../../../internal/cli/assemble.go#L1583)) sent 30 schemas and estimated 3,882 message tokens, 3,442 schema tokens, and 15 framing tokens: 7,339 total. Under the earlier rule, `messageBudget=6400−3442−15=2943`, below the 3,868-token mandatory system message, so the default request would be rejected before dispatch. The same fixture with filtering disabled sent all 39 schemas and measured 8,038 total. The proposed clarification below preserves the existing local message bound and uses candidate metadata to bound the complete envelope when available. Missing provider-limit metadata remains explicitly unknown, never evidence of provider fit. `C` remains distinct from generation `MaxTokens` ([`r3-compaction-design.md`](../2026-09-25-runtime/r3-compaction-design.md#L21)).

R3 provider design requires complete provider-scoped model identity and one resolver/catalog authority; it also keeps unknown model metadata explicit and defines sampling precedence as per-call explicit value, model setting, provider setting, then adapter default. The contract review says compaction budgeting and generation output caps must remain separate ([`r3-provider-design.md`](../2026-09-25-runtime/r3-provider-design.md#L22), [`r3-provider-design.md`](../2026-09-25-runtime/r3-provider-design.md#L27), [`r3-provider-design.md`](../2026-09-25-runtime/r3-provider-design.md#L39), [`r3-contract-review.md`](../2026-09-25-runtime/reviews/r3-contract-review.md#L58)). `ResolvedModel` already pairs its resolved candidate with a `ModelSpec`, but the selected candidate's metadata is not carried through the Loop preflight boundary. A cycler or post-switch model must not borrow the primary model's limits.

## Request admission contract

For the bounded main-request path, preflight the finalized logical request plan consumed by the provider adapter. This is not proof of exact wire tokenization or provider acceptance: only terms established by an estimator bound to the active adapter may be estimated. The selected candidate identity, its own model metadata, final messages, and generation options form one immutable request plan. Dynamic tool filtering is materialized once; the same frozen tool definitions and generation values feed both the estimate and dispatch. No option is rebuilt, tool list re-filtered, candidate re-selected, or output cap changed after admission without creating a new plan and re-running preflight.

Follow the existing compaction-design order for this boundary: consume steering/follow-up, materialize the final filtered tools/options, estimate the request, compact if needed, re-estimate the changed messages with the same candidate/options, then dispatch. If a change in messages requires a different tool set, create a new plan and re-estimate that exact set before dispatch.

The smallest useful seam is an internal prepared-request plan that the Loop creates and an adapter-facing consumer must consume for each physical `Stream` dispatch. Its snapshot contains the existing `llm.CandidateProposal` (and therefore its resolver-issued `ResolvedCandidateHandle`), the `ModelSpec` paired with that same candidate, the final message projection, and the materialized `GenerationOptions`. It also carries the resulting envelope estimate and a private single-use consumption marker. Keep the plan internal and immutable after creation; it is a request value, not a new runtime, public option, or selector-policy redesign. The estimator-only seam is insufficient: the actual adapter call must take the prepared plan as input so it cannot silently reapply the original options or send a different candidate/request.

Preparation and consumption are distinct. Preparation applies the ordered `llm.Option` closures once after final dynamic tool filtering, deep-copies the resulting finite `GenerationOptions` values and schema data, and estimates that frozen snapshot. The estimator and provider adapter must both receive that same snapshot. Dispatch must not reapply the original closures, re-filter tools, rebuild the request, reselect the candidate, or alter the output cap. The adapter-facing consumer can materialize the frozen values directly or through one canonical option derived from the snapshot; either way, it must not execute the original closures again. `llm.Option` is a function over the finite `GenerationOptions` struct, and `WithTools` captures a slice ([`llm.go`](../../../internal/llm/llm.go#L391), [`llm.go`](../../../internal/llm/llm.go#L411)); defensively copy pointer values, slices, and nested schema structures before estimate and dispatch.

The plan is ephemeral and contains no credential material. Candidate identity and `ModelSpec` must come from one `ResolvedModel` (or equivalent resolver-issued snapshot); no API key or credential lookup enters the estimator. A cycler that currently chooses inside `Stream` must offer a metadata-only peek that pairs one `CandidateProposal`, its own `ModelSpec`, and a private selection lease without building an adapter or advancing mutable cycle/session-affinity state. The current `CandidateProposal` has no lease field, so the bounded bridge is to add an optional sealed lease alongside its existing resolver-issued handle:

```go
type CandidateSelectionLease interface {
    CandidateID() CandidateID
    Commit() error
    candidateSelectionLease() // sealed: only llm-owned selectors can mint leases
}

type CandidateProposal struct {
    OperationID    ProviderOperationID
    Candidate      ResolvedCandidateHandle
    Reason         CandidateReason
    Antecedent     CandidateAntecedent
    SelectionLease CandidateSelectionLease // required for CandidateCyclerSelected
}
```

The Loop's existing `OperationDispatchAuthority.AuthorizeCandidate(ctx, proposal)` remains the only authorization path. Its narrow selection-lease helper checks that the lease names this exact candidate and commits it only after the existing operation ID, candidate-set, proposal/antecedent, prior-attempt, and `MaxAttempts` checks all pass, immediately before it marks the candidate authorized. A missing lease for `CandidateCyclerSelected`, a mismatch, a stale lease, or an attempt-budget denial leaves the selector state unchanged and grants no authorization. Represent a stale lease with its own typed denial (for example, `DeniedStaleSelectionLease`) so Core can discard the plan, re-peek, and re-estimate using a fresh proposal and lease from that re-peek with the same operation ID and antecedent before any permit; this is request-plan preparation, not `RecordPreDispatchFailure`, failover, or a provider retry. The adapter then retains its current order: an accepted decision permits creation of the private one-shot `DispatchPermit`, and `BeginDispatch` validates it against the same candidate at the actual provider boundary. A stale plan cannot reach `BeginDispatch`. The selector lease only commits the selection already proposed; it does not authorize another candidate, retry, or operation. Candidate changes on switch, cycle, or an already-authorized later attempt always require a newly prepared plan tied to that exact proposal and metadata. This preserves current retry/fallback authority and does not authorize a new retry.

The adapter-facing consumption contract needs an explicit plan-taking method, implemented by the Loop's resolved/cycler boundary and the enabled adapter path. Its exact signature is an internal design seam, not an existing method; one minimal shape is:

```go
type PreparedRequestPlan struct {
    Proposal CandidateProposal
    Model    ModelSpec
    Messages []Message
    Options  GenerationOptions
    Estimate RequestEnvelopeEstimate
}

type PreparedRequestConsumer interface {
    StreamPrepared(context.Context, PreparedRequestPlan) (<-chan MessageChunk, error)
}
```

`StreamPrepared` consumes one plan once and forwards its exact proposal into the existing authority/adapter path. It may materialize the frozen `Options` directly or via one canonical option created from those values; it must dispatch the plan's `Messages` and candidate and cannot invoke the original closures again. A second use, candidate/proposal change, or stale selection lease is rejected before provider dispatch. The current `BaseChatModel.Stream` remains the low-level adapter contract; this prepared consumer is the narrow Core-to-adapter bridge for the bounded main-operation path, not a second provider API for unrelated operation kinds.

Within this bounded main-operation path, every provider `Stream` call must consume exactly one matching prepared plan: the initial attempt, each already-authorized safe retry/failover proposal, and the single already-authorized overflow recovery attempt. Initial estimate/admission runs after the Loop has created its operation authority but before entering `ProviderOperationRunner.RunProviderOperation`; a reject, estimator error, or cancellation before the first attempt therefore creates no breaker admission and leaves breaker state unchanged. A stale-selection or operation-budget denial may occur later at authorization. The actual-dispatch fact must come from the same Loop authority counter advanced at `BeginDispatch`, never be inferred from an error message. `circuitBreakerModel` reads the operation authority attached to `ctx` with `llm.OperationDispatchAuthorityFromContext(ctx)` and type-asserts this optional observer; the built-in `providerOperationAuthority` implements it under its existing lock:

```go
type ActualDispatchCounter interface {
    ActualDispatchCount() int // synchronized with providerOperationAuthority.BeginDispatch
}
```

Only the built-in `StreamingCircuitBreaker` path may use that trusted full-operation count to settle a new explicit `StreamNoDispatchNeutral` outcome, and only for a Loop-authored typed no-dispatch/admission error when the count is zero (after preserving caller-cancellation classification). If the authority or observer is missing, retain the existing failure classification rather than assume zero. Do not reuse `StreamCanceledNeutral` or classify any provider failure as neutral. Existing generic/custom `Execute` and `ExecuteWithoutFallback` breaker paths retain their current callback-error and fallback policy. They receive no initial preflight reject because that reject is outside the runner; an existing custom breaker can opt into no-dispatch neutrality only through its own explicit optional capability, with no change to existing custom policies by default.

Once an attempt has been admitted, a retry/fallback/overflow candidate is independently re-preflighted inside the existing logical operation and consumes that operation's existing shared attempt budget. It must use the same operation authority, proposal antecedent, candidate handle, and adapter permit rules; preflight never mints a proposal, permit, retry, or additional operation. Recompute `P`, `O`, and the message budget from that proposal's own `ModelSpec` and frozen effective options; never reuse the prior candidate's capacity or output reserve. If a later candidate's plan is rejected after one or more actual provider calls, the Loop operation result must preserve those actual attempt records and their terminal provider classification. The breaker must see the real failure when any actual dispatch in the operation failed; it may settle `StreamNoDispatchNeutral` only if the trusted full-operation count is zero. Thus a primary transient provider failure followed by fallback preflight or operation-budget rejection produces no second `Stream` call, keeps the primary terminal record and failure counters, and is not reclassified as neutral. Summary, continuation, and other operation kinds keep their existing behavior.

`RequestEnvelopeEstimate` should report disjoint message, final tool-schema, protocol-framing and multimodal terms, each with a known/unknown state and reason. The enabled protocol adapter owns its framing estimate; unsupported protocols remain disabled under R0. Use the existing estimator for message and JSON-marshaled final schema structures, while keeping framing overhead distinct so terms are not counted twice. An ordinary custom `llm.Option` is not opaque once applied: its finite `GenerationOptions` result is frozen and estimated like any other option set. A custom adapter/model/protocol whose actual request behavior cannot be represented by that snapshot, or whose required term has no estimator or conservative bound, remains unknown and stops before dispatch. An estimator error or canceled context is a pre-dispatch failure, never a zero-cost estimate.

## Budget resolution

Let `C` be the configured local message-compaction ceiling (`Compaction.MaxTokens`, default 8000), `I` the active candidate's positive `InputTokenLimit`, `W` its positive `ContextWindow`, `O` the effective output reserve, and `E` the sum of estimated final tool schemas plus protocol framing. Keep two independent bounds:

1. The local message budget is `localMessageBudget = floor(C * 0.80)`. It preserves the existing MidTurnCompact threshold for messages; it is not a total-envelope limit.
2. If `I > 0`, set provider input limit `P = I`; do not subtract `O` because `I` is already an input limit.
3. Otherwise, if `W > 0` and `O` is known, set `P = W - O`. Resolve `O` from the effective generation cap after R3 sampling precedence. Clamp a positive requested cap to the active model's positive `MaxOutputTokens` before storing it in the plan; use the same clamped value for estimation and the provider body. When the request has no explicit/configured output cap, use the known `MaxOutputTokens` as the reserve. Preserve option presence: an explicit `MaxTokens=0` is not “unset” and must not be replaced with metadata. If `P <= 0`, reject before dispatch. If the effective cap/reserve cannot be established, the provider input limit remains unknown.
4. When `P` is known, set `providerEnvelopeBudget = floor(P * 0.80)` and `providerMessageBudget = providerEnvelopeBudget - E`; then compact against `messageBudget = min(localMessageBudget, providerMessageBudget)`. The 20% factor applies independently to the local message ceiling and the candidate's complete input limit; subtract `E` only from the provider-derived envelope budget. Do not apply either safety margin twice to one limit.
5. If `P` is unknown because candidate limit metadata or the output reserve needed for `W` is missing, set `messageBudget = localMessageBudget`, and keep provider-limit/provider-fit status `unknown`. Continue to estimate and report final schemas and framing, but do not subtract them from `C` or describe the request as provider-fit. This is the documented bounded local fallback, not a claim that the complete envelope fits the provider. Do not treat an absent reserve as zero.
6. If mandatory retained messages exceed the resulting message budget, a known provider-envelope allowance is exhausted by schemas/framing, multimodal accounting is unknown without a configured conservative bound, or a required request term is unsupported, return a typed pre-dispatch error and make zero `Stream` calls. Unknown provider limits alone do not turn `C` into a provider-wide cap: they retain the local message bound and unknown status.

The effective output cap/reserve is separate from `C`: `C` is never sent as generation `MaxTokens`. When provider limits are known, the complete estimated envelope is bounded by that candidate-specific limit after output reserve and schema/framing deductions. The 20% margin covers ordinary text tokenization/serialization estimation error only; it is not an image-size or provider multimodal bound. A known direct `InputTokenLimit` still uses the margin and schema/framing deductions, but not an output-reserve deduction.

For images or other multimodal blocks, preserve an explicit `unknown` estimate if provider accounting, dimensions/detail, or model support cannot be established. A configured conservative per-item reserve may be used while keeping the provider-fit status unknown. Without such a bound, do not declare the request to fit. Do not retain the fixed 85-token image heuristic as a safe upper bound. Logs and traces may report estimated terms and their `estimated`/`unknown` state, never provider-reported usage. Do not emit a `fit=true` or equivalent verified-provider-fit signal: even a fully estimated request is not provider acceptance evidence, and a custom adapter/model/protocol with unrepresented request behavior remains unknown.

This reuses the current compaction fallback without inventing a hard provider guarantee: missing model-limit metadata may still use `C` to bound messages, with provider-limit status `unknown`; the estimator must never emit provider-fit for that request. By contrast, inability to identify the active candidate or estimate a required final schema/protocol-envelope term is not a fit result; stop before provider dispatch. Unknown values are never silently replaced with zero.

## Stop conditions and external decisions

Stop before provider dispatch if the active dispatch candidate cannot be pinned, a switch/cycle cannot supply matching metadata, a required final schema or enabled-protocol framing estimate errors or is unsupported, or a cancellation occurs during estimation/compaction. Return a typed reason and keep all unmeasured terms explicit; do not dispatch under an assumed capacity.

No external decision is needed to implement this bounded estimate/admission contract. PRD-04 cost-budget policy remains an external product decision; no cost hard budget is implemented or implied by this envelope, and cost is not a context-window hard cap. Native provider/version enablement remains disabled pending the existing R0 wire-fixture and owner-approval gates. This handoff does not change either decision.
