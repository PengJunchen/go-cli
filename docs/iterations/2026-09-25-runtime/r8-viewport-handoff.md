## Source audit at fa7c969

- AccordionModel.Render walks all top-level entries and renders expanded bodies. RenderView also walks all matching entries, splits/materializes their rendered lines, and only then retains the last height lines. In single-column layout, app.go calls the unbounded Render path. The current 120-column split layout clips each panel to its tail; neither path has a scroll anchor or virtual window.
- renderViewLocked scans entries to decide whether tools exist, then builds the panels and appends the spinner, interaction, steer/follow-up, todo, and status sections. The split panel reserves a fixed two lines even though those lower sections can use more space. The viewport must receive the actual remaining body height rather than clip the whole screen and hide controls.
- Main-view Up/Down currently changes accordion selection; Enter expands/collapses. Approval has its own scrolling handler and takes keyboard priority. WindowSizeMsg updates dimensions but resets active approval detail review/offset. Keep those modal and selection semantics owned by R5; viewport input must not steal approval/HITL or editor keys.
- Event-created AccordionEntry.Full strings are rendered at event time and kept. Resizing does not reflow them. Selection is an index, so insertion/refresh can move its meaning.
- handleIncremental appends event text to streamingBuf and calls StreamingMarkdownRenderer.RenderIncremental with the accumulated text. That renderer splits the complete accumulated string, scans it again for code fences, and joins/renders stable and unstable portions. For short messages and a one-line stream it re-renders the whole current message per chunk. Its stableRendered and lastAccumulated fields also grow with the message. The cost is in repeated full-content splitting/scanning/rendering and retained rendered copies; do not assume strings.Builder.String itself copies bytes on every call.
- The R5 live-projection builder's 784 snapshot additionally appends tool output with target.Full += ... for each output event. If that path remains in the accepted R5 result, stream rendering must avoid repeated full-output concatenation there too while preserving the grouped receipt/error/status row.
- The package has no stream_buffer.go at this baseline. Stream state is in app.go and streaming_markdown.go; do not add a general buffer framework just to match a filename.
- The accepted cells.go helpers provide safeTerminalText, cellWidth, clipCells, and wrapCellText using terminal-aware grapheme/cell behavior. Reuse those helpers. This viewport slice is not a Unicode helper rewrite.
- No viewport/search model or named R8 viewport tests are present at this baseline. No benchmark measures 1k/5k/10k rows or a 1 MiB stream.

## Fixed boundaries

1. The viewport is a presentation window. It must not delete, truncate, reorder, or rewrite canonical transcript messages, tool receipts, action status, source-capture metadata, or durable cursors. A screen crop is labeled view-hidden/truncated only when useful; it is never a source-capture truncation.
2. Durable row identity comes from the R5/R2 projection: session, branch, and actual EntryID. A live tool occurrence uses only the exact correlation supplied by the accepted R5/R1 projection; ToolCallID alone is not unique across assistant groups. A standalone incomplete event stays its own row. If it lacks a durable or runtime occurrence key, a private process-local view key may keep its scroll anchor stable, but must never be serialized, used to associate events, or presented as a durable ID.
3. The viewport treats a tool-call group as one structural occurrence with its existing children, expansion state, receipt/error state, and output streams. It does not group, consume, or complete calls itself. An incomplete standalone child/event does not become a complete group child after resize, search, or scrolling.
4. Keep R5 token usage (input/output/max/cost) and run/tool lifecycle status outside the transcript window. Scrolling, search, anchor restoration, or an empty result cannot clear or replace those values. The viewport is not a source of outcome, quiescence, or saved-success claims.
5. Keep the R2 canonical source separate from view retention. R2 Snapshot is a complete snapshot at this baseline; no paged transcript/search reader is exposed. This slice can bound rendered rows and cache for the loaded projection, but must not claim session-size-independent total process memory or full-history search. Search is limited to the currently loaded transcript projection (including off-screen rows in that loaded range) and must display that scope. Adding an R2 paging/index API is a separate contract and implementation task.
6. During a live provisional assistant/tool-output stream, retain source chunks at most once as needed to show the current provisional row; keep only a finite rendered window/cache. After exact R5/R2 snapshot reconciliation, release the provisional source/render cache and use the canonical projection. Do not silently drop old text or change executor capture limits to meet UI budgets. The 1 MiB fixture below is renderer-only and does not pass through Runtime or the provider-candidate guard.

## Minimal implementation shape

Add one focused private viewport model under internal/tui. It owns only stable row-key anchors, logical source position within a row, selection/search state, follow-tail state, width/height, and a bounded visible-row plus small-overscan render window. It is not a second transcript store, session index, generic virtual-list package, or pagination implementation. Keep rendered layout entries/cache bounded by the viewport and overscan; key cache entries by row view key, content revision, width, and expansion state so a changed live tail invalidates only its row.

Use an anchor made of the durable or process-local view key plus a logical source offset within that row. On resize, rewrap from source using the accepted cell helpers and restore the same logical location, not the old terminal line number. Keep selection and search-hit keys separately from the top-visible anchor. New content follows the tail only while follow-tail is active. Manual PageUp/PageDown or selection away from the tail pauses following; End returns to the live tail. Existing Up/Down continues to move the R5 selected entry, scrolling it into view only when necessary. Search uses an explicit search mode, searches only loaded projection content on submit, stores the hit key rather than a list of copied result bodies, and reports no match or the next exact row key. Duplicate text must navigate to the correct distinct key.

Retain the current split threshold and visual layout for this slice. Give the conversation and tool panels independent anchors/follow-tail flags because the panels filter different row sets. PageUp/PageDown applies to the pane containing the selected row; End follows that pane's tail. When resizing across the split threshold, preserve the selected key and the anchor relevant to that key. If the product instead wants one unified timeline or a separate pane-focus key, that is a root decision before integration; do not silently repurpose Tab, approval scrolling, or current Up/Down selection.

For stream rendering, change the renderer boundary to accept new chunks, not require a freshly joined whole-message string for every event. Advance line/code-block state only from new bytes, render the changed tail plus visible/overscan rows, and keep no unbounded rendered-prefix duplicate. Preserve Markdown output and safe-cell behavior with golden tests. Apply the same append-once rule to grouped stdout/stderr events from R5 if the accepted live projection still concatenates each event into Full. Maintain the active provisional source only as long as needed for display/reconciliation; do not use a renderer cache as durable storage.

The screen body height is terminal height minus the measured status/footer/input/todo rows currently visible. Approval/HITL modals keep their existing exclusive input/render path and fixed action-row guarantee. Viewport resize must retain selected row, anchor, search hit, expanded state, input text/caret, usage status, and active request. If the current R5 approval-detail reset prevents its existing detail position from surviving resize, coordinate that narrow modal behavior with the R5 owner rather than changing interaction queue or authorization semantics here.
