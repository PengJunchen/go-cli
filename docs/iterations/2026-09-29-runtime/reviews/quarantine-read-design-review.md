# R2/R4 safe-read quarantine design review

## Verdict

**REJECT pending three narrow design corrections.** Reviewed `quarantine-read-design.md` against source HEAD `1144e1ebc9f339a04d502f0bdca04069c9d30ff5` (including the integrated ACP source commit `47469e3301aacf516937d36bd9dc48009c0b5653`). This is a design review; no source or tests were changed or run.

## Findings

1. **The default-whitelist description is inaccurate, and the actual wiring owner is missing.** Line 21 says the CLI assembly path does not pass `WithRegisteredPathWhitelist`. `internal/cli/assemble.go:956-969` conditionally passes it from `Sandbox.AllowedPaths`; `RegisterDefaults` applies it to the file tools only when that list is nonempty (`internal/tools/builtins.go:69-75,100-147`). With the default empty list, the `PathWhitelist` remains unrestricted (`internal/tools/bash_sandbox.go:83-127`). The missing R4 capability is therefore the same captured canonical workspace root feeding the eligible readers and durable run binding, not the absence of any assembly option. Add `internal/cli/assemble.go` explicitly to the owner table and state that configured sandbox paths are not a substitute for the run's canonical root. The root and `WorkspaceID` must come from one capture (`internal/cli/durable_session_manager.go:62-89`); today `durable_cli_session.go:44-56,134-137` retains and binds only the hash.

2. **The listed Grep/Find proof-eligible routes cannot resolve their own durable read markers yet.** The design includes `GrepTool` and `FindTool` as proof candidates, subject to an attested Go-only route (line 15). Their current trusted registration captures a whitelist but leaves `completionProof` empty; only `ReadTool` and `LSTool` receive `CompletionInlinePipelineJoined` (`internal/tools/trusted_registry.go:293-334`). Without a completion proof, the prepared invocation exposes no joined `Done` signal (`internal/tools/prepared_completion.go:25-42`), while the run-commit consumer requires a ready task with a recognized proof before it writes the exact resolution (`internal/core/run_commit_consumer.go:510-523,859-865`). A successful forced-Go Grep/Find can therefore leave its own marker unresolved, contrary to line 37. Either exclude Grep/Find from this exception initially, or specify that the attested pure-Go registration also captures `CompletionInlinePipelineJoined` and test that the read marker resolves while the older mutation marker remains unresolved.

3. **The proposed index batch cannot enforce the stated mixed read-plus-unknown rejection for calls that never become intents.** Lines 7 and 42 require the whole batch to fail for a missing/unknown action or a mixed read/mutation/unknown batch. In the real parallel consumer, prepare failures and intercepted calls are put in `RunIntentBatch.KnownReceipts`, while only successfully prepared calls become `Intents` (`internal/core/run_commit_consumer.go:602-629`). The session sink builds `WorkspaceDispatchBatch.Actions` from `Intents` alone (`internal/session/run_commit.go:243-246,320-327`), and the index's quarantine check sees only those normalized actions (`internal/session/workspace_index.go:265-279`). Thus a batch containing one safe read intent and one unregistered or policy-denied call reaches the proposed gate looking like a read-only batch. Specify how the complete assistant call batch, including no-intent denials, participates in the atomic quarantine decision, or narrow the acceptance criterion to prepared actions whose captured effects are unknown. As written, the promised “mixed ... unknown batches” rejection has no input at the index boundary.

## Confirmed boundaries

- The design preserves the important R2 behavior: a fresh below-budget request may reach the provider with an unchanged historical `unknown` receipt, while newly prepared actions are checked at dispatch admission (line 49). It does not propose clearing the older quarantine marker with a read receipt (lines 35-37).
- Session intent sync precedes the global index marker, and executors start only after the index returns `CommittedNow` (`internal/session/run_commit.go:335-354`; `internal/core/run_commit_consumer.go:443-456`). `AlreadyExists` is not a replay permit (`internal/session/workspace_index.go:229-237,257-263,294-297`).
- The proposed generation recheck can coexist with the final dispatch commit without a lock cycle if it takes only a short fence snapshot under the workspace lock and never holds the fence across index sync. The final prepared dispatch commit remains the execution linearization point (`internal/tools/prepared.go:773-790`). Current live paths are session-lock/file-lock then index: `SessionRunCommitSink` writes a session row before calling the index, and recovery holds the session file lock before `ApplyDurableResolutions` / `InspectDispatchMarkers` (`internal/session/run_commit.go:335-354,650-657`; `internal/session/durable_jsonl.go:132-189`). The index does not open or call back into sessions. Fence publish/commit callbacks are in-memory and do not acquire the index, so there is no reverse index-to-fence-to-session path in the inspected implementation.

No implementation validation is claimed; this review identifies the handoff changes needed before implementation begins.
