### Request-preflight boundary

At `internal/core/loop.go:698-726`, durable or non-durable message preflight runs before the loop constructs final `iterOpts`. Dynamic tool filtering follows at `loop.go:728-746`; the selected messages and those final options reach `model.Stream` at `loop.go:1384-1387`. The preflight functions accept messages, estimator and compaction `maxTokens`, but not the final schema/options or a model request envelope. `ModelInfo` has context/input/output limits (`internal/llm/llm.go:319-350`), yet that state is not used by this preflight path. Consequently, a request whose messages fit the configured compaction budget can still exceed the actual input limit once schemas and protocol framing are serialized, or when output tokens are reserved. Image estimation is a fixed heuristic, not a provider-aware multimodal bound.

Treat this as a separate follow-up from the durable current-input TDD fix below. The bounded builder can then define how to use active model metadata, filtered schemas and reserved output without conflating it with transcript-source repair.
Its first acceptance scenario should be deterministic: message items fit the effective input limit, but the actual filtered tool schemas plus protocol framing exceed it; assert rejection or compaction before `model.Stream`. Also cover a no-tools boundary and unknown model metadata without claiming a guarantee.

## Highest-priority bounded builder handoff

**Durable preflight must preserve the current submission.** This is a minimal, reproducible correctness gap within the existing durable projection contract; it does not require a new product decision or a full request-token redesign.

- **Source seam:** `internal/core/loop.go:1023-1056` (`preflightDurableRequest`) and `internal/core/durable_compaction.go:74` (projection validation). Mirror the already stronger identity-and-equality check in `preflightNonDurableRequest` at `loop.go:1059-1106`.
- **TDD repro:** capture the pending input's typed source identity before compaction. With a real durable Assembly/session sink, make an oversized current input cause `SummaryCompactor` to choose `cut == len(items)`. Require the exact raw input to remain outside the summary-covered prefix, or fail closed before projection commit and provider dispatch. Do not identify the input by matching text; an older row may have identical text.
- **Source and durability contract:** preserve the captured RunID, expected revision and original `Through` coordinates; do not recalculate them against the post-compaction slice. Reject a missing, changed, duplicated, or covered pending input before `consumer.commitCompaction`. For accepted compaction, the synced durable view and reopened session must show the summary plus the same raw current item in the retained suffix. Projection commit failure must continue to block provider dispatch and use the existing R2 unknown-outcome path.
- **Required behavioral cases:** (1) cut before the pending input, then assert the provider receives the unchanged raw input once and reopen preserves it; (2) cut through the pending input, then assert a typed error, zero compaction commits, zero provider calls, and unchanged raw input after reopen; (3) changed, duplicated, or same-text pending rows are rejected by source identity; (4) compaction commit failure produces zero provider calls; (5) an input that fits without compaction is sent unchanged once. Use a deterministic summarizer, local temporary session store and recording fake provider; a mock-only projection sink is not durable evidence.
- **Verification and stop condition:** verify test discovery and run focused cases, then the affected `internal/core`, `internal/compaction`, `internal/session`, and `internal/cli` race suites at the integrated SHA. Accept only when every committed projection leaves the exact pending input in its suffix, rejected projections never reach commit or provider, and reopen shows the safe result. Stop if the R2 source mapping cannot represent a retained current row without changing `Through`; return that concrete contract conflict for design rather than weakening provenance or treating a summary as the original input. The wider R3-BLD-03 closure remains gated by the pending R2 restart-safety review.
- **Explicitly out of scope:** full provider-envelope/token estimator redesign, actual tool-schema costing, model switching/catalog metadata, loop-detector candidate integration, and unrelated memory-search changes.

### Separate designer handoff: first main-request envelope budget

This is a distinct follow-up to the approved durable-current-input fix. Its goal is to budget the same finalized options and active-model metadata that the first main provider request will use.

- **Boundary:** current preflight at `internal/core/loop.go:698-726` precedes dynamic tool filtering at `728-746` and `model.Stream` at `1384-1387`. Materialize the final filtered options once and use that same set for both the estimate and dispatch.
- **Budget contract:** prefer the active model's `InputTokenLimit`; otherwise use `ContextWindow` minus the effective output reserve, capped by the configured compaction ceiling and safety margin. Subtract estimated final tool-schema/protocol-envelope tokens from the message budget. The output reserve must match the effective `MaxTokens` sent and respect `MaxOutputTokens`. Keep unknown model limits, unsupported schema/framing estimates and multimodal costs explicitly unknown instead of declaring an unverified fit.
- **Model identity:** pair the limits with the model actually chosen for this dispatch. A model cycler must not use the primary model's limits for another candidate; the current `ModelInfo` is available in resolver metadata, but the current Loop dispatch boundary does not carry that pair.
- **Behavioral matrix:** include the decisive case where message items fit but the actual filtered schemas plus protocol framing exceed `InputTokenLimit`, proving compaction or a pre-dispatch error before any `model.Stream`; verify a smaller filtered tool set changes the budget and is exactly the set dispatched; test `InputTokenLimit` precedence, `ContextWindow` fallback/output reserve, `MaxOutputTokens` clamping, active/cycled candidate metadata, estimator error, cancellation and explicit multimodal-unknown handling.
- **Stop condition and out of scope:** stop if active candidate metadata or provider-envelope estimation cannot be established; record unknown and do not claim safe budget. Keep durable current-input preservation, continuations, subagent/summarizer policy, retries/breakers and broader model-selection redesign out of this builder slice.

### Budget-contract addendum (2026-10-01)

The whole-`C` budget formula in the historical bullets above is retained as an audit record, but it is superseded for current design review and must not be used as the builder contract. The current proposal is [the R3 provider-envelope preflight handoff](r3-provider-envelope-preflight-handoff.md), whose budget amendment is pending independent design review before implementation. That proposal keeps `C` as the local message-compaction ceiling; defines `accountedMessageTokens = textMessageTokens + multimodalAmount` and `E = finalToolSchemas + protocolFraming/header`; requires `accountedMessageTokens <= floor(0.80*C)` locally and, for known candidate input capacity `P`, `accountedMessageTokens + E <= floor(0.80*P)`. When `P` is unavailable, it enforces only the local message bound and preserves provider-fit as unknown; `E` is still estimated and reported, never subtracted from `C` or treated as provider acceptance evidence. A finite configured multimodal reserve participates once in `accountedMessageTokens` while the multimodal state remains unknown; without a finite reserve, present multimodal content blocks dispatch. It re-derives candidate capacity, output reserve and frozen terms for each authorized retry, failover or overflow proposal.

The handoff's status line records that this differs from the older whole-`C` formula and requires re-review. Do not implement either budget formula until the independent reviewer approves the updated handoff SHA. This addendum does not rewrite the historical source/test claims above or alter the protected ledger.
