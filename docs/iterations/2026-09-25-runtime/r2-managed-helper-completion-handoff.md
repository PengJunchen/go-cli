# R2 managed helper completion handoff

Status: design-only handoff based on integrated snapshot `b3af60e`. It does not edit tool, core, CLI, or prepared-registry code. It narrows the approved R2 action-scoped completion proof to the existing Grep/Find/Git subprocess routes and builds on the [R2 local-quiescence proof](r2-local-quiescence-proof.md).

## Decision

Keep the default CLI's current `rg` → Go, `fd` → `find` → Go, and Git-diff → unified-diff behavior. Do not select pure-Go Grep/Find or `UnifiedDiffGenerator` merely to obtain a completion proof. Run every helper that is actually selected through the existing local process-group lifecycle, and let one sealed prepared-invocation aggregate prove that the entire call (including any permitted fallback and, for Write/Edit, the accepted mutation job) has finished.

Completion proves only local resource quiescence for that action. It does not grant `workspace_read`, change `EffectSet`, validate `AllowedPaths`, assert output completeness, or convert an error/unknown receipt to success. Unknown/custom `GitTool`, `DiffGenerator`, executor wrappers, and unmonitorable helper paths receive no proof.

The R2 contract already defines `inline_pipeline_joined`, `queued_job_joined`, and `owned_process_group_joined`. The exact sealed `PreparedInvocation.CompletionSignal()` API is not present in this snapshot's `internal/tools/prepared.go`; this handoff assumes the separately owned tools-proof slice will expose it. No new generic resource list, second run owner, or aggregate watcher goroutine is proposed.

## Integration gates

Do not integrate or persist prepared queued-completion proof until the tools-proof P1 for late attachment and stale positive proof has been fixed and independently accepted. Review `reviews/r2-managed-helper-handoff-review.md` records the open finding against tools source `1386d02ebd9d7880de43a5ffb1d0229ea5737222`. That fix has no independently accepted hash yet; keep this gate pending and do not infer or invent one.

For an unjoined helper, return its exact `PendingExecutionError.ExecutionDone()` resource channel and keep the same prepared action's `CompletionSignal().Done()` open. Completion must wait on that same positive process-group signal; the executor returning its pending error cannot close or prove the prepared action. Only after the channel closes with joined leader, readers, and process group may the action publish `owned_process_group_joined`. No later fallback starts while the helper is pending. For a queued Write/Edit, that exact per-job signal also stays open until the handler returns and any nested helper channel has closed. Wait inside the existing queue worker and existing run owner; do not create a detached watcher or unowned goroutine. Nil, unsupported, or unclosed channels never prove completion.

## Minimal composition

1. At preparation, bind the private completion recorder to the exact captured first-party executor, registration generation, implementation path, and attested synchronous wrapper chain. The recorder is action-scoped and reachable by these tools only through the private context installed by `PreparedInvocation.Dispatch` / `DispatchStreaming`. It must not be minted by `Name()`, model arguments, public effect metadata, MCP/extensions, or an arbitrary wrapper.

2. When Grep, Find, or `DefaultGitTool.runReadOnly` starts a subprocess in that prepared context, build the same `exec.Cmd` inputs and pass it to `startManagedLocalCommand`; the runner owns process group and pipe collection. Keep the command's current arguments, environment, working directory, stdout parsing, stderr diagnostics, and exit-code decisions. A helper that exits but leaves a descendant holding a pipe is not joined: `collect` must complete group cleanup and reader joining before the caller considers the helper finished.

3. These helpers and fallbacks execute serially. After each helper, continue the existing fallback path only if that attempt's leader, readers, and group are positively joined. A pending/unmonitorable group returns the existing pending resource error, with its exact `ExecutionDone` channel, before any later helper starts. The prepared action's `Done` remains open until that same channel closes and the process-group runner establishes joined completion; the synchronous executor returning the pending error cannot close the action signal. This makes all prior attempts quiescent by construction; no per-command goroutine is needed to aggregate a list of channels. If several helpers are attempted, the outer prepared signal closes only after each prior helper joined and the final fallback/output processing returns.

4. The final proof value describes the outer action: `owned_process_group_joined` when the exact call ran one or more managed helper groups and all joined; `inline_pipeline_joined` only when the exact trusted path took no helper route and its attested synchronous pipeline returned; `queued_job_joined` for a prepared queue dispatch, only after that exact job and all nested work finish. The queue worker must retain the job's done signal while a nested `PendingExecutionError.ExecutionDone()` remains open and until the handler returns; it can wait in its existing worker loop rather than adding a detached aggregator goroutine. The job signal and action signal stay open during nested cleanup. A pending job remains registered with the same `runOwner` even if the caller already received bounded `cleanup_pending`.

5. Core persists a completion proof only after that same action signal closes. A helper's exit code, a returned `ToolResult`, `DispatchCommitted`, `ExecutionIdentity`, or elapsed timeout does not substitute. If the process group cannot be monitored, the reader cannot join, or the exact executor/wrapper is unknown, the signal has no proof. For a workspace-affecting action, its workspace marker therefore stays unresolved; read-only Grep/Find does not itself create a workspace marker. A known local resource may become quiescent while the receipt remains `unknown` or `error`; resolution never rewrites that receipt.

## Behavior and memory boundaries

Do not change helper selection or observable result handling while adding lifecycle supervision:

- Grep keeps `rg` availability probing, argv/config hardening, exit-1 no-match handling, and its existing helper-error Go fallback. The accepted safety fix in `f6d9cee` improves only the pure-Go fallback's cancellation, scanner-error, FIFO, and symlink handling; it is not a reason to make that fallback the default.
- Find keeps `fd` then `find` then Go, including the current distinction between `fd` exit 1 and other failures, and the final sorted/capped output.
- Git keeps the assembled `GitDiffGenerator`, `DefaultGitTool`'s read-only argv/environment hardening, Git output when nonempty, and the existing unified preview for no-repo, error, or empty-diff cases. Preserve the `DiffGenerator` injected into queued Write/Edit and approval previews.
- Process-group completion is not a general process-tree sandbox. A child that deliberately escapes the assigned group and closes inherited descriptors is outside this proof. Unsupported OS containment, unobservable escaped work, and custom helpers remain unproved and quarantined where the workspace marker applies.

The first mid-walk Grep cancellation fixture was not valid RED evidence: it triggered cancellation only from `Context.Err()`, while the pre-fix walker polled `Done()` and therefore never cancelled. The corrected dual-poll fixture in `b296a41` cancels after the first file has produced a match in either implementation, then directly checks the closed `Done` channel without causing cancellation from the assertion. Against the old source at `b269330` it observes a partial successful result (RED); against `f6d9cee` it observes `context.Canceled` with no partial output (GREEN). Do not cite the earlier fixture's RED as evidence.

The current result limits are not all hard memory budgets. Grep defaults to 1,000 matches and 1 MiB output, but `grepWithRipgrep` first uses `cmd.Output()` and `grepPureGo` accumulates matches before `truncateMatches`; `parseRipgrepOutput` has a 1 MiB scanner token limit. Find sorts and applies its result cap after materializing helper output. `DefaultGitTool.runReadOnly` uses unbounded `CombinedOutput`; the unified fallback has a line limit, but the Git diff route does not. A managed reader may cap retained data only with differential tests proving the same visible prefix, truncation metadata, parse/error behavior, and final sort. It must continue draining pipes after it stops retaining output so process completion can still be proved. Do not claim the existing output caps bound peak memory or add a new silent truncation policy in this slice.

## RED/GREEN acceptance for implementation

Run these against real prepared registration and real tool implementations, with fake helper executables placed first in a private `PATH`. Verify exact test names via `go test -list` before `-run`.

1. Grep retains argv, environment filtering, `rg` exit-1 behavior, and existing fallback results; a helper leader with a descendant retaining stdout/stderr does not close the action signal until the group is stopped and both readers join. If cleanup cannot be proved, Grep returns pending and does not start the Go fallback.
2. Find retains `fd` → `find` → Go route and exit-code handling. A fully joined helper error may proceed to the next route; an unjoined helper cannot. Final sorting and the existing result cap are unchanged.
3. Git preview uses the real assembled `GitDiffGenerator` with `DefaultGitTool`: cover a changed repo, no repo, empty Git diff, and Git error. Assert the exact argv/config hardening and preserve which Git output versus unified fallback is returned. Custom `GitTool`/`DiffGenerator` has no signal proof.
4. Queue acceptance followed by caller cancellation keeps the exact job signal open until the existing queue worker and all nested process groups/readers finish. A pre-accept rejection is not reported as a started queue job. `DispatchCommitted` and the final tool receipt remain independent.
5. The action signal is registered once with the real run owner before the tool worker can finish. Normal and streaming dispatch seams use the same prepared invocation; no helper completion path adds an unowned goroutine. Completion evidence does not grant read permission or modify effects.

The first Read/Ls inline-proof slice remains a separate implementation/review lane. This handoff does not implement it or change the `PreparedInvocation` API; coordinate with the tools-proof owner before any consumer wires the proposed aggregate.
