## Findings

### R4ASM-01 — Concurrent Assemblies can bind a SubAgent dispatcher to another Assembly

**Initial priority:** P1, release-blocking for Assembly isolation. **Initial evidence:** source-established interleaving; no runtime stress probe was run on `e31e5f2`.

`assembleSubAgent` creates a factory closed over the current `s.model` and prepared registry `s.tr`, publishes it through the process-wide `core.RegisterSubAgentFactory`, then separately calls `core.NewDefaultSubagentDispatcher(nil)` (`internal/cli/assemble.go:1231-1236`). The nil constructor separately reads the process-wide factory (`internal/core/subagent_tool.go:91-98`). Each registry operation is individually synchronized, but registration and retrieval are not one atomic operation. If Assembly A registers, Assembly B registers, then A constructs its dispatcher, A captures B's factory. The resulting child runner uses the captured factory's `tools.ToolRegistry` (`internal/core/real_subagent_runner.go:102-108`), so it can use B's policy, Plan controller and dispatch fence. This breaks the requirement that a child stay under its parent Assembly's policy when the parent enters Plan Mode.

The normal same-Assembly path is otherwise correctly fenced: the factory receives `s.tr`; a child wraps that registry only with `filteredToolRegistry`, whose `Get` and `List` delegate to the same protected registry (`real_subagent_runner.go:102-107,222-239`). Prepared approval checks the controller and registry against the request's same fence and evaluates active Plan Mode on every preparation (`internal/approval/prepared_policy.go:53-90`); the final direct or queued commit rechecks the captured fence (`internal/tools/prepared.go:681-696`, `internal/tools/mutation.go:256-261`). `dispatch_subagent` is not a trusted Plan control and is denied while Plan Mode is active. A child call already committed before a Plan transition may finish; subsequent child calls through the correct parent registry are checked against the new generation.

**Follow-up status:** Closed by `acf40682fc93d679b25e2b2ff0ef31ea3eb24bc3`. `assembleSubAgent` now passes its locally captured factory directly to `core.NewDefaultSubagentDispatcher(subAgentFactory)` and no longer writes or reads the process-global factory. Source search at the fixed follow-up finds no Assembly call to `RegisterSubAgentFactory` or `GetSubAgentFactory`; the only CLI reference is in the regression test. Since later required-control/network failures occur after this setup, a failed Assembly also cannot leave its factory in the global registry.

**Regression evidence:** `internal/cli/assemble_subagent_isolation_test.go` first installs a sentinel global factory, constructs two independent Assembly states with separate real mock models and tool registries, and invokes each dispatcher. It verifies the sentinel is preserved and that each child calls only its own registry and model. The committed RED log ends at the expected assertion that the old Assembly mutated the sentinel global factory; it does not claim to force a scheduler interleaving. The local-factory code removes the global set/get window entirely, so a separate forced-interleaving test is unnecessary to establish the fix. The test does not itself transition a parent to Plan Mode while a child is running; the same-registry Plan behavior is supported by the unchanged runner/policy path described above.

### R4ASM-02 — Configured PostToolUse hooks need an actionable startup diagnostic

**Priority:** P2. **Initial evidence:** source-established behavior; the original test verified non-execution, not notice visibility.

`loadShellHooks` accepts `post_tool_use` and stores it for extension assembly. Prepared stages intentionally omit `HookManager.PostToolUseWrapper`; the original notice checked only whether `s.hookMgr` was non-nil, so it also warned for configurations containing only pre-tool/session hooks. In the real CLI, `cmd/cli/main.go:48-63` sends `slog` output to `.go-cli/logs/go-cli.log` by default to keep the console clean. A configured PostToolUse command therefore did not run and the user received no startup notice.

**Follow-up review at `7a40ca3`:** the loader now caches parsed hooks in `assembleState` and resolves `gitCwd` once. `AssembleAgent` preflights that cached configuration before model/tool/service assembly; `assembleExtensions` reuses the same parsed slice, so the preflight and later wiring cannot observe different hook-file reads. A valid PostToolUse hook returns `ErrPreparedPostToolUseHookUnsupported` with `%w`, its configuration path and hook index, and calls the existing cleanup path. Pre-tool/session hooks remain accepted and the stale `assemble_post_tool_use_hooks_unavailable` warning was removed. The tests now prove both branches: `TestAssembleRejectsConfiguredPostToolUseShellHook` asserts a nil assembly, `errors.Is` classification, path/index in the error, and no marker side effect; `TestAssembleAcceptsPreAndSessionShellHooksWithoutUnavailableWarning` asserts assembly succeeds and captures no old warning. The RED log records the old implementation returning a non-nil assembly; the passing regression establishes the fixed behavior.

**Closure at `c10a7a2`:** the error now carries structured `Path` and `Index` fields in `UnsupportedPostToolUseHookError`, unwraps to `ErrPreparedPostToolUseHookUnsupported`, and deliberately excludes command text. `classifyError` recognizes the sentinel and produces a PostToolUse-specific action and path/index hint. `TestClassifyUnsupportedPostToolUseHook` checks the action, location, and preserved `errors.Is`; `TestServeConfiguredPostToolUseHookShowsSafeUnsupportedError` exercises the real serve startup path and confirms the user sees the unsupported reason and path/index without the command canary. This closes the user-visible diagnostic gap while retaining the fail-closed startup behavior.

## Verified Assembly boundaries

- Assembly derives one `DispatchFence` from the prepared registry, passes it to `DefaultPlanModeController` and `ApprovalMiddleware`, and installs the approval policy and execution stages on that same registry (`internal/cli/assemble.go:1023-1120,1126-1209`). Prepared dispatch normalizes and validates the captured call before policy, stores the exact executor, and sends mutations to the configured queue; the worker uses the captured invocation and final fence rather than looking up a tool by name.
- Required trusted-control and trusted-network registrars return errors on absence or registration failure (`assemble.go:1312-1320` and following network registration loop). `AssembleAgent` returns that error and calls `runCleanup` (`assemble.go:345-347`); the local mutation queue, model, extension manager, and registered LSP cleanup are on the cleanup stack. The SubAgent follow-up no longer writes a global factory before this failure point.
- Default execution wrappers remain installed in prompt-injection → audit/telemetry → result-masking order. Tool-result cache is deliberately passed as `nil`, so this prepared path cannot return a cached result ahead of approval. The parent and sub-agent model wrapper both receive the output guard chain.
- Protected registry proxies preserve `Parameterized`, `PromptGuideliner`, `StreamingBashTool`, and `TopToolsProvider` where registered; `TopTools` results are protected again. The actual Assembly `tool_search` control works in Plan Mode, and its prepared identity/effect is checked by the policy.
- Real Assembly tests cover Write and Edit through the mutation queue, Plan blocking and per-Assembly parent interceptor isolation, and non-TTY denial without disclosing the fixture. These passed in the targeted race run below.
- `WithNoSandbox` changes the Bash sandbox only; separately configured path whitelists still flow to default file tools. The PathWhitelist follow-up at this snapshot fixes invalid-empty scope and root containment; this review relies on its independent PathWhitelist review and does not claim OS-level isolation.
