# R2 Core RunCommitSink consumer handoff

Status: source-based design for root approval; no implementation or test evidence. The source base is the execution tip b269330 on codex/runtime-stabilization. This handoff consumes the approved R2 contract, the local-quiescence proof contract, R4 prepared dispatch, and the current RunCommit binding in core. It does not change the seven-method RunCommitSink contract.

## Decision and scope

Connect RunCommitSink to the production CanonicalLoop path. Keep the durable path run-scoped and fail closed when the sink, physical binding, owner identity, or prepared invocation is missing. When no sink is bound, retain the existing Loop and registry execution path.

The seven sink methods remain error-only: CommitInput, BeginIntentBatch, RecordExecution, RecordReceipt, ResolveExecution, CommitCompaction, and CommitTerminal. Core continues to own only these typed facts and must not import session. The session adapter remains responsible for JSONL rows, actual EntryID and Seq values, and WorkspaceQuarantineIndex updates.

One narrow correction is required to the earlier rule that resolutions wait until an entire assistant tool-call group is closed. A sequential group can contain call1 with a durable receipt and proof, followed by call2 that cannot start while call1 has an unresolved workspace marker. The session validator may therefore accept only exact non-transcript completion and resolution metadata for an already-receipted occurrence in the current open assistant group. This metadata exception never relaxes index admission, never admits arbitrary checkpoints, and does not publish an incomplete group as model history.

## Existing source seams

- internal/core/run_commit.go already defines the atomic sink-plus-physical-binding context, RunCommitFromContext, RunIDFromContext, ActionIntent, and the seven error-only sink methods.
- internal/core/run_owner.go injects the claim RunID and replaces OwnerGeneration before calling the callback. It already counts dispatch workers and pending resources; this is the lifecycle owner for the same prepared completion signal.
- internal/core/loop.go owns the production canonical transcript and the sequential and parallel dispatch branches. It must consume and commit typed transcript facts directly; AgentEvent and EventStream listeners are not a durable source.
- internal/core/parallel_tools.go currently looks up tools with ToolRegistry.Get and executes them through Execute or ExecuteStreaming. The durable branch must use ToolCallPreparer.PrepareToolCall once and dispatch that returned invocation.
- internal/core/agent.go consumes CanonicalRunResult once, validates its delta, and updates history. It is the terminal commit boundary: CommitTerminal must sync before publishing the updated durable history or acknowledging success.
- internal/session/derive.go currently removes a call from the open map when its receipt is encountered, then rejects an execution row for that call if a sibling call remains open. It also rejects all checkpoints while any call remains open.
- internal/session/durable_recovery.go validates intent, execution, receipt, proof, and resolution relationships. The same relationship rules must be used by the direct SessionViewFromEntries path, not inferred from PrepareResume having run first.
- internal/session/workspace_index.go returns AlreadyExists for a repeated marker and blocks a new batch while any marker is unresolved. Neither result is a same-run replay or admission exemption.

## Run identity and input

At callback entry, obtain the sink and RunCommitBinding as one value through RunCommitFromContext, then take the run ID from the same runOwner callback context. Validate `(sink, SessionID, WorkspaceID, RunID, OwnerGeneration)` as one identity tuple from that immutable callback context; do not mix partial values across contexts or apply fallback identity. The actual runOwner is the sole source of RunID and OwnerGeneration: it injects the claim ID and overwrites/validates the generation before invoking the callback. Require every tuple member to be nonempty and valid before the first provider request. The CLI caller supplies the prepared physical session and canonical workspace identity.

Commit the initial user input before entering the first provider call. Assign all transcript indexes from the per-run canonical delta, beginning with the current input; assign assistant ordinals from the per-run assistant sequence. Steering and follow-up inputs are committed when consumed, before the next provider request. Do not derive coordinates from content equality, provider call IDs alone, or event order.

If a sink is bound but its binding or owner identity is missing or mismatched, return a typed durable-binding error before provider or tool entry. If no sink is bound, keep the existing behavior.

## Prepared dispatch and durable ordering

For each tool call, prepare once and retain that exact PreparedInvocation, its immutable identity/effect/digest snapshot, its generated IDs, and its CompletionSignal. Durable mode fails before dispatch if the registry cannot provide ToolCallPreparer. Normal and streaming dispatch both use the same prepared object; streaming uses its prepared streaming dispatch method. Do not call Get and then prepare a second invocation through a proxy.

For one sequential call, or one parallel assistant group, the required ordering is:

1. Append the canonical assistant row once for this response, then append the approved intent rows for the current batch and wait for session sync. A sequential call has its own one-action ActionBatchID; later sequential calls reuse the already-appended assistant row and append only their new intent. A parallel assistant group shares one batch ID.
2. Through the adapter, call BeginDispatchBatch only after the session sync. Dispatch is permitted only for CommittedNow. AlreadyExists and all errors stop before executor entry.
3. After index commit, register the exact prepared invocation CompletionSignal.Done and its typed proof with the same runOwner before the dispatch worker releases. Then call Dispatch or DispatchStreaming on that same prepared invocation.
4. Preserve the existing normal dispatch/identity observation row when available. It may be written before the receipt and is not, by itself, proof of stopped resources.
5. Persist the tool receipt at its canonical TranscriptIndex. Only after the receipt append and sync may a completion proof resolve that action.

In sequential mode, prepare only the current call. Do not prepare the next call until the current receipt is synced and any available local resolution has synced to both session and index. In parallel mode, prepare the whole assistant group once, then commit its approved intents in one batch before starting workers; denial receipts stay staged for canonical-order receipt submission.

Pre-reservation denials have no ActionID. They remain known in `RunIntentBatch.KnownReceipts`, but `BeginIntentBatch` must not physically append a denial receipt ahead of an earlier canonical receipt or advance the receipt cursor out of order. A denied call has no dispatch marker; persist its receipt when Loop reaches that canonical call slot. In parallel mode, buffer every result and denial in `completedReceipts[TranscriptIndex]`; once the next index is available, call `RecordReceipt` serially and advance the cursor only after that sink call returns nil. The adapter independently rejects a gap or reorder before writing. A result that completes out of order remains buffered and is not passed to the sink. A still-running dispatched worker has an unknown receipt, not a guessed late result. In sequential mode, persist the current call receipt at its canonical turn. Maintain a contiguous transcript cursor; use the full occurrence key (RunID, AssistantTranscriptOrdinal, ToolCallID), plus ActionID for reserved actions. Provider ToolCallID may repeat at a later assistant ordinal.

For a parallel group, prepare the complete approved group before BeginIntentBatch, dispatch only after the combined session/index fence, and buffer worker output by original call slot. Completion and denial order must not change physical transcript receipt order. Do not append receipts from worker goroutines.

## Completion proof, resolution, and owner lifecycle

The prepared CompletionSignal is action-scoped and fixed by Prepare. A recognized non-nil proof means its exact final executor pipeline, queued job, or owned process group has positively completed according to the frozen tools API. A nil Done channel is absence of proof, never an already-closed signal; do not register nil as a live pending resource, wait for it, or infer future proof. Do not infer completion from a normal return, absence of PendingExecutionError, ExecutionIdentity, tool name, or context cancellation.

Streaming has an additional unresolved trust seam. The first tools proof slice intentionally leaves `*StreamingBashToolImpl` without a proof because an arbitrary `StreamSink` callback may start asynchronous work; default CLI builtins use StreamingBash, so the default Bash path is not yet durable-closed. The next design/review must define a trusted core `eventStreamSink` synchronous attestation fixed before Prepare, have the prepared invocation capture that same sealed sink identity/token, reject a different sink in `DispatchStreaming`, and keep CompletionSignal fixed from Prepare. Custom/unattested sinks get no proof and durable streaming must fail closed. Do not claim streaming closure until that seam is separately reviewed and implemented.

Outcome and quiescence remain separate. A late local proof may clear a local workspace marker while the original receipt and RunTerminal outcome remain unknown or error. It never rewrites a receipt, retries the invocation, or turns the run into a successful save. Remote-terminal resolution remains fail closed until a separately approved typed protocol-terminal fact is durable and validated.

Preserve the pre-receipt ActionStateExecution observation row, including any existing ExecutionIdentity. If proof is already available there, it may be attached to that row. If proof arrives after the target receipt, append an additional proof-bearing execution row as the narrow late-metadata exception, then append the resolution checkpoint. The adapter obtains the proof EvidenceRef from the actual row returned by AppendAndSync.

The completion watcher is not a writer. Extend the existing private `runWorkerTracker` with one per-action completion-task registration, `WaitForCompletion(ctx, done)`, and `DrainReadyCompletions(ctx)`. The task carries the full action occurrence reference, the proof-bearing `ActionExecution`, and the exact Done channel. The task registration owns the resource count for that signal so the prepared path does not also register the same channel through the old `PendingExecutionError` hook. `WaitForCompletion` runs only on the Loop goroutine, uses the runOwner's existing `cleanupTimeout` set by `WithRunCleanupTimeout`/`runOwner.run`, and adds no duration constant or owner/session/index lock. If its select chooses callback-context cancellation or bound expiry, it nonblockingly rechecks that same Done channel before returning a stop result; a signal that closed in the race proceeds as ready. The existing runOwner resource observer may mark the task ready, decrement resources, and signal `changed`; it must not call the sink. The Loop invokes the same owner drain after the target receipt sync and before trying the next action or provider request. All proof writes go through that one drain path. A nil Done task is not proof-ready and has no observer goroutine or pending-resource count; after callback and actual workers/resources finish, release the run lease while leaving its global marker unresolved.

When a dispatched call has a durable receipt but its non-nil proof is not ready, wait only on the Loop goroutine after the dispatch worker has returned, with no session/index lock held and no owner mutex held. Reuse the runOwner context and the per-run value supplied through WithRunCleanupTimeout/runOwner.run; add no new timeout constant. If the select sees Done, or sees cancellation/timeout and the immediate recheck finds Done closed, continue normally; this avoids a scheduling-race false interruption of a known result. If cancellation/timeout wins and the recheck still finds Done open, a sequential group stops its suffix: append the remaining calls as not-dispatched receipts without ActionIDs where no intent was reserved. In parallel mode all calls already have result/denial/cancellation-snapshot receipts; do not issue another provider request while any dispatched proof remains pending. A non-nil signal that remains open through cancellation/timeout leaves `RunTerminal.Outcome=unknown` even if its known receipt is preserved; the runOwner execution state then follows its existing `cleanup_pending`/quarantined policy. Do not start another provider request or suffix call. A nil proof cannot pass this safe point: stop any undispatched suffix and leave its marker unresolved, without inventing a future proof task. In both modes, commit the terminal outcome if persistence remains healthy. The dispatch worker never waits for a receipt or for its own CompletionSignal.

If proof becomes ready after the caller has received cleanup_pending and the Loop callback has returned, the same runOwner supervisor is the sole late writer. Reuse the existing `changed` wakeup and worker/resource accounting in `runOwner`; add one owner-held set of completion tasks plus an explicit successful durable-terminal-sync fact. Only once callback, workers, and resources have joined, and terminal sync succeeded, may the supervisor invoke the same ready-task drain and release the session lease/run slot. The per-signal observer only marks its owner-held task ready and signals `changed`; it never waits for a receipt or writes a checkpoint. Do not create a detached writer that has no join path.

Keep a narrow optional owner lease capability on the bound per-run sink, such as `RunCommitRunLease.CloseRunCommit`; do not add lifecycle methods to `RunCommitSink`. The CLI session manager retains base ownership of its prepared physical session handle and lends an idempotent per-run lease to each sink. `CloseRunCommit` releases only that run's lease; it must not call `PreparedSession.Close` unconditionally because REPL's next request may reuse the same physical session. A session switch or process exit first marks the handle close-requested and prevents new leases, then actually closes/unlocks it exactly once after the last run lease returns. The CLI/REPL must not release a live run lease merely because its caller stopped waiting. If a writer is poisoned, no subsequent run may reuse it before reopen/recovery; the current run still releases its lease after resources join and retains its persistence error. If Done is nil, no future proof writer is expected: once the callback and all actual workers/resources finish, release the per-run lease normally and leave the global marker unresolved. If a non-nil Done remains open, retain the runOwner's lease and quarantine until it closes or the existing owner policy marks the run; do not create an unjoined writer goroutine.

Separate local resource quiescence from durable terminal success in runOwner. A CommitTerminal or earlier sink sync failure means there is no success acknowledgement and no resolution/index apply. Once callback, workers, and resources have joined, however, a poisoned writer must not keep a run lease forever: skip final proof drain, retain the unresolved global marker and persistence error, release that run's lease exactly once, and release the local run slot without rewriting the error outcome as success. Do not leave `transcriptCommitted` false as the only release gate. Track terminal sync success separately from local resource quiescence so the supervisor can distinguish safe final proof drain from mandatory local lease release. The session manager separately closes the shared prepared handle only after close-request plus zero run leases.

## Session adapter and open-group validation

Keep the core sink interface at seven error-only methods. The session adapter is the only layer that turns sink calls into session rows and index records. After each successful AppendAndSync, retain the canonical row and writer-assigned EntryID/Seq in an index keyed by the complete occurrence and row kind. ResolveExecution may fill an empty EvidenceRef only from one unique earlier row with the right type and exact action reference; a supplied nonempty ref must match exactly. Missing, ambiguous, wrong-kind, cross-occurrence, or conflicting refs fail before the resolution append.

After the local resolution checkpoint is appended and synced, call ApplyDurableResolutions with that returned checkpoint EntryID and Seq. Preserve session-file-before-workspace-index lock order; never call back into session storage while holding the global index lock. If index sync fails, keep the marker unresolved and do not admit another dispatch. Never invent IDs from ActionID, content, or a client-side generator.

Every compaction projection must come from the exact compactor result with the approved source cursor/revision. Commit and sync it before the next provider request that consumes the compacted history, and include the same immutable projection list in RunTerminal. The current CanonicalRunResult has only Events and Transcript, so thread projections through the approved post-R1 typed projection path; do not infer them from events, final text, or mutable Agent.History.

The pure journal relation validator must be shared by durable recovery and direct SessionViewFromEntries. It may allow only these rows to pass through a currently open assistant group:

- Existing intent and ordinary execution/identity observation rows for an occurrence still present in the current open group.
- A late proof-bearing execution row only when its target receipt is already physically durable, the target belongs to the current assistant group, the complete session/workspace/run/batch/ordinal/call/action/generation identity matches the earlier intent and receipt, and the row is not transcript-visible.
- A typed execution-resolution checkpoint only after its exact target receipt is durable. local_resources_quiescent must reference a unique earlier proof-bearing execution row for that same action. never_dispatched must reference the exact not_dispatched receipt. The checkpoint has no TranscriptIndex and is hidden from projection.

All other checkpoints, branch/terminal/compaction rows, transcript entries, malformed metadata, and late-proof rows for an older or different assistant group remain rejected while a group is open. Direct SessionViewFromEntries validates the relation itself; it does not rely on a loader call. The view still rejects an unreceipted open group and never projects intent, proof, or resolution metadata.

This is the sole refinement to the prior whole-group-safe-point rule. The index continues to reject every new batch while any marker is unresolved, including a marker from the same run. In sequential mode, call1 resolution must sync to the session and index before call2 begins. In parallel mode, all receipts are buffered and committed in canonical order; ready resolutions are drained in stable call order before any later batch or provider request.

CommitTerminal verifies that existing rows for the run are an exact contiguous physical prefix with matching payloads, then appends only the missing contiguous suffix and terminal checkpoint. A hole, reordering, duplicate, or payload mismatch fails. No terminal persistence error is success acknowledgement.

## Child runs

The current realSubAgentRunner passes the parent context into child Submit, which would inherit the parent sink and physical session. Durable mode must reject delegation before child launch with a typed unsupported error until a child-session factory can prepare an independent session, owner generation, and atomic sink/binding on the same workspace index. Do not mask the parent sink or unresolved marker through context values or event-stream wrappers.

## Required regression coverage for the builder

- No-sink regression: current sequential, parallel, and streaming behavior remains available without RunCommitBinding.
- Binding/preparer failures: missing or mismatched owner/session/workspace identity and missing ToolCallPreparer stop before provider/tool entry; retries preserve generated action and batch IDs; a reserved invocation rejected by its final fence keeps its ActionID and exact not-dispatched receipt.
- Compaction: exact projection source cursor/revision is synced before the next provider request; a projection append/sync failure prevents that provider request and withholds terminal/saved acknowledgment.
- Sequential multi-call: call1 receipt plus early proof resolves before call2 marker; late proof within the existing bounded wait continues when Done closes at the boundary; timeout/cancel stops the suffix and records exact not-dispatched receipts.
- Parallel canonicalization: workers finish in reverse order with one or more pre-dispatch denials; physical receipts and reopened transcript remain ordered by TranscriptIndex.
- Streaming: the same prepared streaming invocation and same CompletionSignal.Done are registered with the runOwner before worker release.
- Streaming attestation: current `*StreamingBashToolImpl` and default CLI Bash remain without proof until a separate reviewed seam seals the trusted synchronous core event sink before Prepare and rejects sink replacement at DispatchStreaming.
- Outcome versus quiescence: unknown receipt followed by valid local proof clears only the marker, never replays or changes the receipt/run outcome; nil proof leaves the marker unresolved.
- Late cleanup: after cleanup_pending and a successful terminal sync, a later signal is drained by the retained runOwner and the prepared handle closes once; if CommitTerminal poisons the writer, no late checkpoint/index apply occurs, but the handle still closes once resources join.
- Recovery/direct view: exact open-group proof and resolution metadata validates and remains hidden; wrong ref/type/identity, another-group proof, or any unrelated checkpoint is rejected. Reopen uses writer-assigned evidence IDs and validates terminal prefix/suffix behavior.
- Failure paths: AlreadyExists never dispatches; session/index/appends fail closed; no later provider call or success acknowledgement follows a sink error; child delegation returns the typed unsupported error.

This document is a design handoff only. It does not claim implementation, test, UAT, or recovery closure.
