# R4 approval policy source review

Review sequence: `6e4dc978afb7c855971cde137dfc422e57b47738` (approval baseline), `ed528cd30513b2cab246fd5389c8ff31a21168d2` (policy hardening), `defda43848e49ddea51a781acdc4e2665d30bbe7` (final pre-follow-up policy snapshot), and `d9c8933fe4f84aee5370671f62791d8b7d538376` (Plan-mode network-read follow-up). I reviewed the fixed snapshots in detached worktrees and changed no product source. This is an approval-policy review only; it does not close the R4 assembly or execution integration gate.

## Findings on the pre-fix snapshots

### P1 — Tool names could receive first-party read approval (closed at `ed528cd`)

At `6e4dc97`, `PreparedPolicy` passed only the `ToolCall` to the selected classifier (`internal/approval/prepared_policy.go:138-160`). `SafetyPolicyClassifier` auto-allows names such as `read`; `AutoClassifier` allows unrecognized names by default. Neither classification was checked against the trusted registration identity and effect set. Once the prepared registry path was added, an ordinary `Register` for a tool named `read` could therefore receive an automatic permit despite carrying `EffectUnknown`.

The pre-fix regression is recorded in `evidence/r4-prepared-revocation-red-v2.log`: `TestPreparedDefaultAndAutoReadNameNeedsExplicitApproval` observed zero approval callbacks in both Default and Auto modes. At `ed528cd`, `preparedClassifierAllowTrusted` downgrades a classifier `Allow` to `Ask` unless the request has the required trusted source/effect/scope; `PermissionAutoFull` remains an explicit exception. The actual `MiddlewareToolRegistry` regression now verifies an ordinary registered `read` is prompted in Default and Auto, and AutoFull remains explicitly permissive.

### P1 — An explicit user denial did not revoke sibling prepared permits (closed at `ed528cd`)

Before the fix, `ApprovalDeny` only recorded the callback result and returned `ErrToolDenied`. It did not advance the shared Approval generation. A sibling invocation already approved against the same snapshot could still dispatch after the user denied another call. The pre-fix `TestPreparedApprovalUserDenyInvalidatesSiblingPermit` failure is in `evidence/r4-prepared-revocation-red-v2.log`.

At `ed528cd`, an explicit callback denial publishes an Approval revocation against the request snapshot and clears the session cache (`internal/approval/prepared_policy.go:200-205,357-367`). The test confirms the sibling permit then fails with `tools.ErrDispatchFenceChanged`. A classifier `Deny` remains a local decision and does not revoke siblings; `TestPreparedClassifierDenyDoesNotPublishExplicitRevocation` checks that distinction.

### P1 — Reusable approval keys omitted the global Approval generation (closed at `ed528cd`)

The pre-fix decision key included Registry and Plan generations but not `req.Generations.Approval`. Replacing the prepared policy or another Approval-domain writer could therefore leave a new request with an unchanged cache key even though its global approval snapshot had changed. The policy-replacement regression failed on the pre-fix tree, as recorded in `evidence/r4-prepared-revocation-red-v2.log`.

At `ed528cd`, `ApprovalGeneration` is part of `preparedDecisionKeyInput` and the key construction (`internal/approval/prepared_policy.go:26-42,283-296`). `TestPreparedApprovalPolicyReplacementDoesNotReusePriorGrant` verifies a same-call request asks again after the installed prepared policy is replaced.

### P1 — A custom `ApprovalStore` was silently ignored by prepared dispatch (closed at `defda438`)

The baseline initialized `preparedStore` only for `*InMemoryApprovalStore`, while `PreparedPolicy` queried only that field. Other implementations remained accepted by the constructor, had no `initErr`, and their Deny/Allow state was skipped. A disposable actual-registry probe on `ed528cd` used an `ApprovalStore` whose `Get` always returned Deny; the prepared policy never called `Get` and the executor ran once. The permanent regression’s pre-fix failure is recorded in `evidence/r4-prepared-store-mode-red.log`.

At `defda438`, unsupported stores set `ErrPreparedApprovalStoreUnsupported`, which is wrapped in `ErrPreparedPolicyUnavailable`; the regression checks both errors and asserts zero callback and executor calls (`internal/approval/middleware.go:27-30,168-178`, `prepared_policy_failclosed_test.go:22-43`). The existing legacy `WrapToolCall` path remains separate; this change makes prepared dispatch fail closed when no fenced store adapter exists.

### P2 — An invalid explicit mode could be hidden when no resolver was wired (closed at `defda438`)

The baseline `preparedState` forced `PermissionDefault` whenever `resolver == nil`, masking an explicitly stored invalid enum before `PreparedPolicy` validated it. A disposable prepared-registry probe against `ed528cd` showed `WithPermissionMode(PermissionMode(97))` was handled under Default and could reach the callback and dispatch. The permanent pre-fix failures are recorded in `evidence/r4-prepared-store-mode-red.log`.

At `defda438`, valid modes still preserve the documented no-resolver Default behavior, while invalid stored values remain visible to the validator (`internal/approval/prepared_policy.go:251-261`). `TestPreparedPolicyValidatesExplicitModeWithoutResolver` covers both constructor option and setter paths.

## Final snapshot review at `defda438`

The core approval fixes above are present and the targeted tests pass. `AllowOnce` returns a one-call decision without writing session, approval-store, or cache state (`prepared_policy.go:185-197`). `AlwaysAllow` publishes a monotonic positive grant against the captured snapshot, persists it only under the complete identity/effect/schema/argument/generation key, and rechecks the fence before returning (`prepared_policy.go:213-248,272-309`). Parallel positive grants preserve sibling permits. Mode, Plan, registry, policy replacement, cache reload, and explicit user denial use the shared fence domains; final `PreparedInvocation.Dispatch` performs the full snapshot check before executing the pinned definition.

`RequestApproval` receives `req.Call.ToolCall()`, which returns a deep copy of the frozen JSON call (`internal/tools/prepared.go:379-385`); mutations to callback arguments therefore do not change the captured identity or dispatch arguments. No approval/session/fence lock is held while invoking the callback: state locks are released before `RequestApproval`, and the callback result is checked against the original fence afterward. A temporary barrier probe (removed after use) blocked the callback while a Registry replacement, mode change, or Plan entry occurred; each writer completed, and each released callback returned `ErrDispatchFenceChanged` without dispatch. The permanent tests cover post-decision invalidation and concurrent positive callbacks, but do not yet retain this exact writer-during-wait barrier regression.

Plan Mode takes precedence over AutoFull. Its current approval path allows only a single `workspace_read` effect or the narrow trusted-control name/source pair (`prepared_policy.go:312-332`). The current production tool registry does not mint `workspace_read`; ordinary and unscoped read tools remain `unknown`, so this review did not observe a path that can exercise that allow branch. Keep the scope/provenance requirements aligned when a future trusted read registration is introduced.

One specific follow-up guard is that the Plan branch currently accepts `EffectWorkspaceRead` without checking registration source or a non-empty scope fingerprint, while `preparedClassifierAllowTrusted` requires both. There is no current production registry mint for this effect, so this was not an exploitable path in the reviewed registry. When a trusted read registration is added, either enforce source/scope in the Plan predicate too or prove those requirements at the single minting boundary.

## Follow-up review at `d9c8933`

The follow-up fixes the Plan-mode gap: `preparedPlanCallAllowed` now accepts exactly one `EffectNetworkRead` only when the request identity is minted as `RegistrationSourceTrustedNetworkRead`, the registered name matches the call, and the name is `web_search` or `web_fetch` (`internal/approval/prepared_policy.go:312-380`). The minting boundary is narrow: `DefaultToolRegistry.RegisterTrustedNetworkRead` accepts only concrete `*WebSearchTool` and `*WebFetchTool`; ordinary `Register`, including the same concrete definitions, carries no trusted network effect. The tests exercise both real registry paths, enter Plan Mode, and dispatch the trusted tools with a local RoundTripper for fetch. The web-search fixture returns its local deterministic result. This restores the approved read-only network behavior without letting a custom same-name tool self-assert it.

The same policy now requires `EffectWorkspaceRead` to have builtin provenance, a non-zero trusted scope fingerprint, and a matching tool name in Plan Mode as well as in classifier-Allow handling. The current default registrations still have no trusted workspace-read effect, so they remain unknown until the separate path-scope registration work provides a real scoped executor. Network reads do not require workspace-path scope.

Outside Plan Mode, the policy still only downgrades an untrusted classifier `Allow`; an existing `Ask` continues to the approval callback. A trusted NetworkRead may preserve an existing `Allow`. The new explicit-Allow test covers that preservation, and the source path leaves Ask unchanged. The behavior continues to honor the separate Plan restriction and dispatch-fence generations.

The commit also retains the previously missing concurrency regressions: a real prepared registry call blocks in the approval callback while mode, Plan, or registry writers complete; the stale call then fails with `ErrDispatchFenceChanged` and does not invoke the tool. A callback-argument mutation regression changes top-level and nested maps/slices from a goroutine while dispatch reads its separately frozen arguments. These tests passed under the race detector. One non-blocking test-quality note: the writer operations currently run synchronously before the callback is released, so a future lock regression would wait for Go's global test timeout instead of failing through an explicit short bounded wait. I sent this suggestion to the builder.

## Remaining integration and review limits

- The production CLI assembly has not switched to prepared dispatch in this snapshot. `assembleApproval` still constructs `ApprovalMiddleware`, then wraps the registry with `approvalMW.WrapToolCall` and the legacy mutation wrapper (`internal/cli/assemble.go:1056-1085`). I did not count prepared-policy unit tests as CLI/Assembly acceptance.
- The new three-axis callback-wait barrier and ApprovalCallback argument-mutation tests are policy-layer coverage. They do not replace an Assembly-level prepared-dispatch gate.
- `WithAutoApprove(true)` still converts an `Ask` into an allow (`prepared_policy.go:172-179`). The owner confirmed this is the existing explicit operator full-Ask approval strategy, consistent with CLI `ApproveAuto`; it is not the name-based default-read exemption that this review found. A temporary actual-registry probe under race verified that auto-approve still cannot bypass active Plan Mode for unknown effects, an explicit classifier Deny, an explicit callback Deny, or a changed dispatch fence. The probe was removed after use.
- Callback errors return before `recordPreparedDecision`; explicit Allow, AlwaysAllow, Deny, invalid results, and policy denials are recorded. If audit policy requires an outcome span for callback transport/cancellation errors, add a regression and record that choice.
