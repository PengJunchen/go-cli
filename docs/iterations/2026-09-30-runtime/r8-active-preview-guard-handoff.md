# R8 active assistant preview under the complete-response guard

Status: Designer handoff, source review only. It does not change Runtime, TUI, tests, protected task state, or release claims. Baseline: develop `8cb287a5201ce52816d7fc67873b4d60b2b495cd`. Scope is the remaining active assistant-stream seam under [R8-BLD-01](../2026-09-25-runtime/execution-tasks.json#L1765), after the bounded renderer and viewport work; it is not a general renderer redesign or R8-BLD-02 capability decision.

## Finding

The main CLI does not publish assistant text to the event stream while a guarded provider response is still arriving. This is a deliberate output-guard boundary, not a missing TUI rendering branch. Re-enabling the existing incremental flag would make the active text visible, but it would also publish text before the full candidate has been checked. That changes the guard’s current confidentiality behavior even if the preview is labeled ephemeral and never enters the transcript.

Therefore the literal request—show generated assistant text before the provider finishes while preserving the existing complete-response “no unapproved candidate reaches downstream consumers” guarantee—has no implementation path in the current contracts. A product decision is needed before exposing speculative candidate text. There is a fully bounded, guard-preserving fallback: show a content-free “assistant response is being checked” activity state during generation. That provides visible progress, but does not satisfy active partial-answer visibility or close the original partial-text acceptance.

## Safety decision

The full-response guard’s current user-visible contract delays candidate content from the event/UI, tool-dispatch, and durable-session boundaries until the candidate has been completely checked. Core still receives and buffers raw provider chunks internally. A live preview would cross the guarded user-visible boundary. Clearing it after rejection, cancellation, or a later redaction cannot undo that disclosure. Applying the existing stateless `OutputGuard.Check` to each growing prefix is not equivalent: future bytes can complete a match, and a later full-candidate rejection can invalidate text already displayed.

The smallest strictly guard-preserving change is a content-free lifecycle signal on the default REPL event stream, for example `assistant.generating` / `assistant.generation_finished`. The producer must explicitly carry `RunID` and the assistant occurrence's canonical transcript index through the core event and TUI bridge: at this base, `stampAgentEvent` stamps run coordinates broadly but only adds transcript coordinates for message and tool kinds, and `KindToContentType` has no dedicated lifecycle mapping. Extend those mappings or populate the coordinates explicitly, then assert the default path preserves both values end to end. The signal carries no provider text, tool-call payload, candidate ID, or receipt claim. The TUI can show a bounded “response is being checked” activity indicator and clear it on accepted completion or a terminal failure. It remains outside the returned assistant events, session writes, tool authorization, and canonical transcript. The default REPL creates its event stream without an `EventBus`; `EventStreamImpl.Send` does publish to a configured bus, so a future reuse outside this exact CLI path must either treat the new typed activity event as ephemeral or use a UI-only event seam. This is safe progress feedback, not partial-answer streaming; it does not make End reveal newer response text while the provider is active.

To display candidate text during generation, the release owner must explicitly choose the product policy. The direct option is speculative preview: label it visibly provisional, retain the existing full-candidate check before normal assistant completion, tool dispatch, and durable publication, and accept that content later blocked or redacted can already have appeared on screen. If that consequence is not acceptable, keep the full-response contract and ship only progress feedback. A prefix check alone is not an equivalent third option.

This decision does not require a new R2 receipt protocol for a content-free progress indicator or an uncommitted process-local view row. R2 does remain mandatory for any “saved” or “completed” claim: only its joined owner status, exact publication binding, terminal checkpoint, same-source snapshot, and model-apply acknowledgement support that status, and the saved-success badge additionally requires zero event gaps. The exact canonical occurrence can reconcile into the installed snapshot despite a nonzero gap count; the UI must retain the visible gap/unconfirmed status and withhold the saved-success badge. `RunID` plus canonical transcript index identifies the assistant occurrence, not a durable `EntryID` and not a provider attempt. Do not infer durable identity from either.

## Required stream identity and lifecycle if speculative preview is selected

Current `AgentEvent` carries `RunID` and canonical transcript coordinates but has no provider-attempt identity or per-preview sequence. A run can contain retries/failover, continuation, overflow recovery, or a later assistant iteration. Those cannot share one unversioned live string.

The preview contract must therefore use an occurrence key containing at least run ID, canonical assistant index, provider attempt ID, and preview generation ID. Each delta and close/retract event carries a monotonically increasing sequence. The TUI accepts only the active generation’s next sequence; stale attempt/generation events are ignored. A detected gap freezes or labels the preview incomplete and cannot be repaired by guessing. A new attempt starts a new preview generation; it cannot append to the failed attempt’s preview.

Preview state is ephemeral presentation data only. It is not `AgentMessage`, a result event, a tool receipt, a run terminal, a provider usage receipt, or a canonical session row. It must not contain tool calls before the complete candidate has passed existing validation. Tool execution, R1’s complete candidate byte cap, guard checking, and the current durable commit path remain unchanged. Any accepted text shown before the final candidate is still speculative even if its provisional marker is later removed.

Cancellation and owner completion need explicit outcomes. A locally canceled preview is fenced against late chunks. A provider/owner completion that remains unknown is shown as unconfirmed and cannot be promoted or labeled saved. If a visible preview survives a rejected/canceled run for diagnosis, it stays clearly marked provisional and process-local; if the product chooses to erase it, the UI still cannot imply that the hidden candidate was never displayed. Event or UI queue gaps stay visible as gaps, not as a complete answer.

## TDD acceptance

The strict fallback can be built without changing the guard contract:

1. `TestDefaultAssemblyShowsGenerationStatusWithoutProviderContent` uses the actual default assembly and a local provider that flushes a distinctive candidate marker, sends non-empty keepalives, and holds the final chunk. Before release, assert that the UI visibly indicates generation/checking, while the marker is absent from the event stream, current TUI view, and raw PTY. Release the candidate, assert that only the checked/sanitized final answer appears, once.
2. `TestGenerationStatusIsEphemeralAndRunScoped` proves the default assembled Core → EventStream → bridge → TUI path preserves the exact `RunID` and `CanonicalTranscriptIndex` on start and end events; state is keyed to that exact occurrence, is not returned as an assistant result, is not in session JSONL, cannot overwrite another run’s status, and ignores a late close event from an older run. This is a progress indicator test; do not count it as active partial-content acceptance.
3. Keep and exercise the existing `TestOutputGuardRunsBeforeVisibleDelta`, `TestOutputGuardBuffersAcrossLengthContinuationsBeforeVisibleDelta`, and `TestOutputGuardBufferLimitFailsClosedWithoutVisibleDelta` through their current owner boundary. Extend the test only if a production default-assembly regression is missing; do not flip `publishIncremental` just to make the TUI preview test pass.
4. A PTY progress test may PageUp/End during a held stream to verify the fixed activity state remains discoverable and later completion is visible, then assert `/exit` and terminal-state restoration. Its report must say `progress-only`; it does not pass the R8 active assistant-text precondition.

If speculative text preview is explicitly selected, add these separate requirements before Builder:

1. `TestDefaultAssemblyActivePreviewBeforeProviderFinal` uses the real default main path, pins the provider after the first non-empty chunk, and waits for decoded PTY text while the source is still held open. It then PageUps, sends End, sends later sequenced chunks, and proves follow-tail reaches the newest provisional text before the provider final chunk. The fixture must gate on provider flush, Core/event observation, and actual decoded frame separately; longer sleep is not acceptance.
2. `TestPreviewAttemptAndSequenceFences` covers duplicate, stale, skipped, reordered, cross-run, cross-attempt, cancellation-after-read, retry/failover, and late-after-terminal deltas. A gap is visible as incomplete; a new candidate never silently concatenates with an earlier attempt.
3. `TestRejectedOrRedactedCandidateRemainsNonCanonical` covers a guard-blocked candidate, a redacted candidate, an over-limit candidate, cancellation, and an unknown run outcome. It verifies the chosen provisional-disclosure behavior, no preview in assistant `AgentMessage`/session JSONL before accepted completion, no tool dispatch before full validation, and no `[saved: success]` without the exact R2 publication/terminal/snapshot/apply proof.
4. `TestPreviewPromotionRequiresSameRunSnapshotAck` proves only the exact `(RunID, CanonicalTranscriptIndex)` occurrence in the same-session/branch snapshot reconciles the provisional row. A pending/failed publication, nonquiescent or unknown owner, mismatched owner generation, or missing terminal entry cannot promote it. With a nonzero event gap but otherwise valid exact snapshot, assert the occurrence reconciles, the gap/unconfirmed state remains visible, and the saved-success badge stays absent.
5. Run the real main CLI PTY journey and preserve provider-flush log, source-event trace, decoded frames before and after End, raw terminal output, exact binary/source SHA, OS/terminal/geometry, `/exit` status, and terminal mode restoration. Existing viewport-only tests and the older post-completion PTY are not substitutes.

## Handoff boundary

Ready for Builder now: only the content-free progress state if the task is narrowed to that behavior. Not ready for Builder: exposing provider candidate text before the complete-response guard, because that requires an explicit disclosure-policy decision. No R2 implementation is required just to show local provisional data; R2’s exact known terminal/publication evidence is required before any preview can be promoted or described as committed. This document does not alter the protected `execution-tasks.json` or claim R8 completion.
