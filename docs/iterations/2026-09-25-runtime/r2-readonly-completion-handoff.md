# R2 builtin read-tool completion handoff

Status: design follow-up for the approved R2 local-quiescence contract. This handoff does not change permission effects or workspace-index policy. Source inspection used the integrated runtime snapshot at `f7f4f1a`, the approved prepared-completion API, and Grep safety fix `f6d9cee`.

## Decision

Extend positive local-completion evidence first to the exact first-party `ReadTool` and `LSTool` executors. Preserve Grep/Find's current helper selection and fallback behavior. Prefer adding owned-process-group completion for the helpers they actually invoke (`rg`, `fd`, and system `find`) before considering any pure-Go selection. Do not silently switch durable CLI defaults to pure-Go implementations to obtain proof: that changes user-visible search behavior. Keep helper execution unresolved until it uses the owned-process-group join path. Do not infer completion from a tool name, ordinary return, `EffectSet`, or matching schema.

`WithForcePureGo(true)` and `WithFindForceNode(true)` remain explicit implementation options, currently documented mainly for tests. They are not a recommended durable-mode default or an equivalence-preserving substitute for the helpers. A future product decision may expose an explicit mode, but it must pin and test the behavior differences below. The assembled `GitDiffGenerator` must also remain intact; completion work must not silently replace it with its unified fallback.

This proof answers only whether the exact local execution pipeline has finished and left no owned local work running. It does not grant `workspace_read`, bypass approval or Plan policy, prove path confinement, or assert that a result is complete. A read remains subject to the independent effect and scope checks when another workspace action is quarantined.

## Prepared-completion API and registration boundary

The approved R2 contract uses one closed, action-scoped completion value on `ActionExecution` and the durable execution row:

- `inline_pipeline_joined`
- `queued_job_joined`
- `owned_process_group_joined`

The prepared tools slice exposes the matching closed `tools.PreparedCompletionProof` constants and `PreparedInvocation.CompletionSignal() tools.PreparedCompletionSignal`. The signal has `Done() <-chan struct{}` and `Proof() PreparedCompletionProof`; a nonempty proof is available only after that same non-nil `Done` channel closes. Core must register that same channel with the same run owner before releasing the dispatch worker. A missing or nil signal is not a closed channel and proves nothing. The approved contract is recorded in [the R2 local-quiescence design](r2-local-quiescence-proof.md) and [its review](reviews/r2-quiescence-design-review.md).

Mint any new inline proof only through the existing private first-party registration path (`registerDefaultTool` and a narrow internal registrar). The registrar must pin the concrete definition and the exact implementation mode; it must not use `Name()` or caller-provided effect metadata. Ordinary registrations, MCP/extensions, config-defined tools, and custom definitions that reuse `read`, `ls`, `grep`, or `find` stay without proof. The prepared pipeline may retain proof only when each configured execution wrapper has the existing trusted synchronous-wrapper attestation; an unreviewed wrapper suppresses it.

No new `EffectSet` value is required for this lifecycle change. A closed local pipeline can still have made synchronous changes before it returned; its completion proof means those local resources have joined, not that it was read-only. Remote and unknown executors, including lost-response calls, cannot use this proof to resolve remote uncertainty.

## Executor evidence and pure-Go tradeoffs

| Tool | Current path | Narrow proof condition |
| --- | --- | --- |
| `ReadTool` | `Execute` resolves and validates one path, uses synchronous `Lstat`/`Stat`, rejects special files, then reads at most the configured byte limit or lists one directory. The open file's deferred close runs before `Execute` returns (`internal/tools/read.go:92-200,216-235`). | The exact first-party definition and its final prepared wrappers return before the channel closes. A slow or blocked filesystem call leaves the channel open. This proves no worker remains after return; it does not turn the check-then-open path check into an OS sandbox. |
| `LSTool` | `Execute` performs `Stat` and a `WalkDir` restricted to immediate children, checks cancellation between entries, sorts and returns synchronously; it does not start a helper (`internal/tools/ls.go:83-211`). | The exact first-party definition and attested wrapper chain return before the channel closes. |
| `GrepTool` | Default `search` probes for `rg` and launches it with bare `exec.CommandContext`; if it fails, the code falls back to Go (`internal/tools/grep.go:188-233`). The Go path now checks cancellation and `Scanner.Err`, skips symlinks/non-regular files, and checks each file against `AllowedPaths` before opening (`:271-365`, `f6d9cee`). The `Lstat`-then-`Open` check is application-level and has a check/use race; it is not an OS sandbox. | Keep the current helper/fallback selection. Add managed process-group proof for the helper path before resolving it. Do not make the pure-Go path the durable default. Any future explicit pure-Go mode needs a separate product decision and pinned behavior tests; this change alone grants no completion proof. |
| `FindTool` | Default `find` probes for `fd`, then system `find`, using bare `exec.CommandContext` and `Output`; otherwise it walks in Go (`internal/tools/find.go:157-234,236-290`). `Execute` sorts all results after either route (`:94-154`). | Preserve current helper selection. Both helpers need managed group completion. Do not switch the durable default to `forceNode`; any explicit pure-Go mode needs its own behavior decision and tests. |

The existing constructor options already select the no-helper paths: `WithForcePureGo(true)` and `WithFindForceNode(true)` (`internal/tools/grep.go:48-53`, `internal/tools/find.go:40-45`). They are currently documented mainly for deterministic tests, and `RegisterDefaults` does not expose a durable-mode selector. Do not add a durable-only override that selects them just to gain proof. If a future explicit product setting offers pure-Go search, treat it as a user-visible behavior choice, pin the differences below, and keep its proof registration separate from the existing helper-backed defaults.

Keep these observable differences explicit if a future product decision considers a pure-Go mode:

- **Ignore and hidden files:** the `rg` command uses `--no-config` but does not add `--hidden` or `--no-ignore`; its ignore behavior comes from the helper. `grepPureGo` walks every non-directory entry and applies only the optional glob, so it can return hidden and ignored files the helper omitted. `FindTool` may select `fd` (no explicit hidden/ignore override), system `find`, or Go. The Go walker does not consult ignore files and includes dotfiles. Search results can therefore change when a helper is bypassed or absent.
- **Regex:** `GrepTool.Execute` first compiles the pattern with Go `regexp`; default mode then sends `re.String()` to ripgrep's matcher, while pure-Go mode uses the compiled Go regexp. Do not promise full dialect or result equivalence between engines. Keep a documented common-pattern corpus and pin any intentional differences.
- **Ordering and truncation:** `find` sorts its final paths, so its output order is stable across implementations. Grep does not sort matches before `truncateMatches`; pure-Go `WalkDir` traversal and ripgrep output may order matches differently, which can alter the selected prefix when match/output limits truncate results.
- **Errors:** Grep's helper errors generally fall back to Go; the Go scanner skips unreadable files but now returns `Scanner.Err` rather than silently reporting a partial scan. Find's Go path returns a top-level `Stat` or context error but skips per-entry walk errors; helper branches have their own exit-code rules. Forcing Go pins a different error boundary.
- **Cancellation:** Find's pure-Go path returns `ctx.Err()` when the walk observes cancellation. Grep's pure-Go path now propagates cancellation observed during traversal/scanning and discards partial matches on error. A completion proof may show that a returned pipeline has stopped, but it must not convert a partial result into a known success.

The initial Grep fallback safety defects are fixed in `f6d9cee`: deterministic pre-cancel, mid-scan cancel, overlong-line, FIFO, and nested symlink regressions were red on the prior source and pass after the fix. That does not enable an inline completion proof. Per-file scope remains an application-level `Lstat`/whitelist check followed by `Open`; no OS sandbox or cross-platform race-resistant openat layer was added. Keep pure-Go Grep proof disabled until the exact path and its scope boundary are separately accepted. The fix also does not change helper selection, `EffectSet`, or permission behavior.

## `AllowedPaths` remains a separate boundary

The current CLI registers `WithRegisteredPathWhitelist` when `Sandbox.AllowedPaths` is nonempty (`internal/cli/assemble.go:911-912`). `RegisterDefaults` wires it into Read/Grep/Find/Ls (`internal/tools/builtins.go:104-146`). Read checks its resolved target in `ReadTool.resolvePath`; Grep/Find/Ls call `resolveAndValidatePath`, which checks relative traversal, rejects a final symlink, resolves existing symlink components, and verifies the path against `PathWhitelist` (`internal/tools/read.go:216-235`, `internal/tools/write.go:70-145`, `internal/tools/bash_sandbox.go:87-142`). `TestAssembleAgentConfiguredPathsConstrainDefaultFileTools` exercises all four tools against allowed paths, outside paths, and a parent-symlink escape while `WithNoSandbox` is active (`internal/cli/assemble_path_scope_test.go:14-83`); the empty-path test explicitly leaves Read unrestricted (`:86-105`).

These are application-level checks with documented check/use races, not an OS sandbox. A direct `GrepTool` regression now covers a root inside the allowlist containing a file symlink to an outside target; it does not claim assembly-level or race-free confinement. Any future no-helper decision must preserve the same whitelist wiring and cannot broaden a tool's path scope. Completion and path authority remain independent.

## Preserve the assembled diff generator

CLI assembly creates `UnifiedDiffGenerator`, wraps it in `GitDiffGenerator` with the selected `DefaultGitTool`, and passes that shared instance to Write/Edit, the mutation queue, and approval previews (`internal/cli/assemble.go:834,901-906,1142`). `GitDiffGenerator` uses `git diff --no-ext-diff --no-textconv` when it has a nonempty repository diff, otherwise it calls its unified fallback (`internal/tools/diff.go:241-269`, `internal/tools/git.go:192-209`). The prepared tools slice currently recognizes only bare `*UnifiedDiffGenerator` as inline-safe for Write/Edit. Do not replace the assembly's GitDiffGenerator with its fallback just to obtain a completion proof: that silently drops the git-aware diff behavior and can change the preview/queue output. Either prove the exact assembled GitDiffGenerator path through an owned helper boundary, or keep Write/Edit without inline proof when that generator is installed. Any custom `DiffGenerator` remains opaque unless separately reviewed; do not overwrite an explicitly injected generator.

## Acceptance matrix for the follow-up implementation

Run against real `RegisterDefaults`/Assembly and the real protected `ToolCallPreparer`, not a hand-built fake registry or manually asserted proof:

1. Real `RegisterDefaults`/Assembly and the protected `ToolCallPreparer` exercise Read/Ls first: exact first-party invocations expose `inline_pipeline_joined`; `Proof()` is empty before `Done` closes and nonempty only afterward. Exercise success/error paths and a blocked wrapper whose channel remains open until released.
2. Preserve the current Grep/Find helper selection and `GitDiffGenerator`. No pure-Go durable-mode default is introduced. An ordinary custom definition named like each builtin cannot obtain a first-party proof; an un-attested execution wrapper suppresses proof. Add helper proof only after `rg`/`fd`/`find` run through the owned-process-group join path.
3. Nonempty `AllowedPaths` continues to reject absolute outside paths, parent symlink escapes, and the new nested-file-symlink Grep case even under `WithNoSandbox`. Empty `AllowedPaths` retains the existing documented unrestricted behavior; completion does not change it.
4. Any explicitly proposed pure-Go option has differential fixtures for ignored/hidden-file behavior, common regex behavior, grep ordering under truncation, Find ordering/depth/type behavior, unreadable/special-file behavior, and cancellation semantics. Document intentional differences rather than asserting implementations are equivalent. Do not use a proof slice as justification for silently changing defaults.
5. At the R2 consumer integration boundary, the exact completed local action can append one `local_resources_quiescent` resolution and release its marker only after the proof channel closes. A pending tool still blocks a second mutation; the proof never upgrades `EffectSet`, authorizes a read during another unresolved mutation, or resolves a remote/unknown external action.

This is a design handoff. The only source change referenced here is the bounded Grep fallback safety fix `f6d9cee`; it does not implement the completion proof, change effects, or alter CLI defaults.
