# R2 durable session, action journal, and recovery contract

Status: design revision in progress; not approved. The current independent review report is [r2-contract-review.md](reviews/r2-contract-review.md); its P1/P2 findings are being closed, and final prepared-dispatch signatures are delegated to [r4-prepared-dispatch-design.md](r4-prepared-dispatch-design.md). R2 keeps the current SessionTree and JSONL store and adds durable commit/recovery semantics around the existing CLI run path. It is not a general event store, database, distributed lease, or automatic action scheduler. R2 follows the typed per-run transcript from R1; it never reconstructs authoritative history from `AgentEvent` or `EventStream`.

## Required behavior

Starting a new session must create a new physical file and an empty root tree. Resuming must first select a physical session file, then select a branch/entry inside that file. A configuration value such as `rc.Session.ID` or `agentName` is a display/logical label; it is never concatenated into a filesystem path and is not the physical session identity.

The CLI must durably save the submitted user input before the first provider request. Before a tool executor is called, its complete assistant tool-call message and every intent in that dispatch batch must be durably saved. A known result or explicit unknown receipt must be durably saved before the next provider request. Final text, the terminal run outcome, all transcript records, and any compaction projections must be durably committed before the CLI says the run was saved or complete. If append, flush, or sync fails, return a persistence error and withhold the durable acknowledgment. Do not swallow a session error or advance the authoritative tree first and save later.

Durable acknowledgments occur only at semantic boundaries: submitted input, tool-dispatch batch, tool receipt, consumed compaction projection, and run terminal. Token/delta streaming does not fsync. A caller may have seen already-streamed text when a later persistence failure occurs; the CLI must report that the session commit failed and must not represent that text as durably saved.

## Identity and versioned record shape

Keep the JSONL file as the append-only authority. Version new records additively; absent `record_version` means legacy version 0 and remains readable. Version 1 records carry the applicable fields below. Unknown future versions, conflicting identities, broken parent links, and inconsistent action pairs fail closed. Do not rewrite or delete legacy session files as part of opening them.

| Identity | Rule |
|---|---|
| Physical `SessionID` | Opaque, random, path-safe ID generated by the store. New filenames use this ID and exclusive creation (`O_EXCL`); timestamps may help display/sort but cannot provide uniqueness. Persist the user's logical/display label separately. |
| `EntryID` | Opaque unique ID assigned once before the first append attempt and reused on an idempotent retry. It is unique within the physical session file. An exact duplicate ID and canonical payload is a no-op; the same ID with different content is a hard error. |
| `ParentID` | Empty only for a root entry. Otherwise it names an existing entry in the same physical file; entries never point across session files. |
| `Seq` | Strictly increasing, persisted per-file order assigned by the durable writer. It is authoritative for append order; timestamps are display metadata and never select a leaf or break ties. The writer returns the canonical record with its assigned sequence before the tree publishes it. |
| `RunID` | The R1 `RunClaim.ID`, scoped to a physical session. It is stable for the run and is not reused for recovery/retry. |
| Tool-call occurrence | Pair by `(RunID, AssistantTranscriptOrdinal, ToolCallID)`. Providers may reuse an ID such as `call_1` in a later assistant completion in the same run; preserve the provider ID unchanged and never pair only on it or on completion order. |
| `ToolCallID` | The provider's original tool-call ID within one assistant tool-call message. A terminal receipt is paired by the full tool-call occurrence key above. |
| `ActionID` | Opaque reservation ID allocated before the intent append for at most one actual executor invocation. It is distinct from `ToolCallID` and is never reused. A call rejected before reservation has no `ActionID`; a reserved call later canceled/fenced before executor entry retains the same `ActionID` in a durable `not_dispatched` receipt. |
| `OwnerGeneration` | Random generation ID for the runtime/process owner that launched the action. Never use PID alone as owner identity. |
| `WorkspaceID` | Stable digest of the canonical workspace root, used to discover cross-session unresolved child work without writing the raw path into action records. Canonicalization failure is not treated as a different/safe workspace. |

Extend `SessionEntry` with optional fields, preserving its current `ID` as the on-disk entry ID: `RecordVersion uint16`, physical `SessionID`, `RunID`, `ActionBatchID`, `ActionID`, `OwnerGeneration`, `WorkspaceID`, `InputKind`, `ActionState`, `DispatchState`, `ReceiptOutcome`, `PayloadDigest`, `ExecutionIdentity`, `AssistantTranscriptOrdinal`, `TranscriptIndex`, `CompactedThroughEntryID`, `RunOutcome`, and `CheckpointKind`. Existing `Type="user"|"assistant"|"tool"|"compaction"|"system"` values remain valid; add one internal `checkpoint` type for terminal-run, execution-resolution, active-leaf, and reconciliation records. A tool entry with `ActionState="intent"` is journal-only and is not projected as a model tool result. A terminal `Type="tool"` receipt has the R1 `ReceiptOutcome` value `success|error|interrupted|unknown`, the original non-empty `ToolCallID` and `ToolName`, the matching `AssistantTranscriptOrdinal`, and its own zero-based `TranscriptIndex`. `DispatchState` is `not_dispatched|dispatched`; if the receipt has an `ActionID`, it must match the same occurrence's durable intent reservation, including for `not_dispatched`. A call denied before reservation may have `ReceiptOutcome="error"`, `DispatchState="not_dispatched"`, and no `ActionID`. Journal-only intent/execution rows have no transcript index. Action occurrence validation uses `(RunID, AssistantTranscriptOrdinal, ToolCallID)` while `ActionID` identifies at most one executor invocation.

The R1 typed transcript remains the source for user, assistant, steering/follow-up, and tool-receipt messages. The initial user message appears once in that delta; session persistence must not append a second user row through a separate legacy path. `EntriesToAgentMessages` must restore validated assistant tool calls and exactly one terminal receipt per call, while excluding intent-only rows. Invalid, duplicate, missing, or mismatched call/receipt IDs fail closed rather than guessing.

## Durable writer and action journal

Add a narrow optional durable writer alongside the current `SessionStore` interface:

```go
type DurableSessionWriter interface {
	AppendAndSync(ctx context.Context, entries ...SessionEntry) ([]SessionEntry, error)
}
```

Callers generate and retain each `EntryID` before calling. `AppendAndSync` validates and serializes the complete batch, appends complete newline-delimited records, flushes and calls `Sync`, and returns the stored canonical records (including assigned `Seq`) only after sync succeeds. An error means there is no durable acknowledgment; any write/flush/sync error poisons that writer until it is closed and reopened through recovery. After reopen, identical IDs/payloads are idempotent and conflicting duplicates fail. A partial batch may have a durable prefix; do not dispatch any action from the batch unless the entire batch call returned success. Do not remove queued items, advance the tree, increment durable/flushed counters, or print a saved acknowledgment before successful sync.

`PendingSessionWrites.Savepoint` becomes an absolute monotonically increasing enqueue watermark, not `len(pending)`. It remains stable when older prefixes are flushed/removed and newer entries arrive. Its durable/flushed count advances only after the associated `Save`/`Sync` succeeds. A partial append or sync failure retains the exact entry IDs and suffix for recovery/idempotent retry; it must not silently discard the prefix or duplicate it on reopen.

Put one optional typed commit sink on the actual Loop production path, not on `AgentEvent`/`EventStream` listeners. Core owns the interface in a new file and `session` supplies its adapter; Core must not import `session`. The sink is attached per run with a context helper such as `WithRunCommitSink(ctx, sink)` and has these operations:

```go
type RunCommitSink interface {
	CommitInput(context.Context, RunCommitInput) error
	BeginIntentBatch(context.Context, RunIntentBatch) error
	RecordExecution(context.Context, ActionExecution) error
	RecordReceipt(context.Context, RunToolReceipt) error
	ResolveExecution(context.Context, ExecutionResolution) error
	CommitCompaction(context.Context, CompactionProjection) error
	CommitTerminal(context.Context, RunTerminal) error
}
```

This is gated on the R1 production handoff: `LoopAgent` must implement `CanonicalLoop`, and `AgentImpl` must consume its `CanonicalRunResult` exactly once before committing history or returning. `Harness.Submit` and `TurnRunner` inject their `RunClaim.ID` into the run context; a direct `AgentImpl.Run` with persistence enabled creates a fresh per-call `RunID` if no owner supplied one. At run start, capture an immutable `priorHistory` snapshot and its count/revision separately from the current user input. Keep legacy `Submission.History` compatibility through an explicit `PriorHistoryCount`/input boundary (or equivalent typed field); never determine that the last history item is the current input by comparing role/content, because repeated identical user messages are valid. `CompactionCursor.PriorHistoryCount` counts only the pre-run snapshot; the initial user input appears once in the current-run transcript delta. R2 builders wait for R1's production `CanonicalLoop` consumer and owner seams to be integrated before implementing these hooks.

The sink payloads have stable typed coordinates. `RunCommitInput` carries `RunID`, `TranscriptIndex`, `AgentMessage`, and R1 `InputKind` (`user|steering|follow_up`). `RunIntentBatch` carries one `ActionBatchID`, the assistant's zero-based `AssistantTranscriptOrdinal` and full assistant `AgentMessage`, all approved `ActionIntent`s, and known pre-dispatch `RunToolReceipt`s for rejected calls. Each `ActionIntent` contains `RunID`, `AssistantTranscriptOrdinal`, original `ToolCallID`, unique reserved `ActionID`, registered tool identity, workspace digest, canonical argument digest, and the trusted registry `EffectSet`; it does not persist raw args or credentials. `ActionID` is allocated with each durable intent reservation and names at most one actual executor invocation. If a call is rejected before intent creation it has no `ActionID`; a reserved call later prevented from dispatch has the same `ActionID` in a `not_dispatched` receipt. `ActionExecution` carries the occurrence key plus `ActionID`, `OwnerGeneration`, dispatch/resource state, and optional verifiable `ExecutionIdentity`. `RunToolReceipt` carries both the assistant group occurrence key and the receipt's own zero-based `TranscriptIndex`, optional `ActionID`, dispatch state (`not_dispatched|dispatched`), the complete tool `AgentMessage`, and R1 `ReceiptOutcome` (`success|error|interrupted|unknown`). Prior sink writes and `CommitTerminal` compare canonical transcript payloads by `(RunID, TranscriptIndex)`; action grouping uses `(RunID, AssistantTranscriptOrdinal, ToolCallID)`. `ExecutionResolution` is a separate typed resource-quiescence checkpoint keyed by `RunID` and `ActionID`; it records `quiescent` with positive `ExecutionDone`/joined-reader evidence or `operator_reconciled` with a durable reconciliation record. `RunTerminal` carries `RunID`, the final per-run `TranscriptEntry` delta, all typed `CompactionProjection`s, `RunOutcome`, and the final checkpoint. Provider `ToolCallID` is preserved unchanged and can repeat at a later assistant ordinal.

`CommitInput` is called for the initial user entry before the first provider request and for steering/follow-up as soon as the Loop consumes it, before the next provider request. The actual approval wrapper currently runs inside the registry's `Execute`, so R2 depends on the narrow R4 prepared-dispatch seam owned by `R4-EFFECT-01`. Its exact Go signature, result accessors, and file ownership are authoritative in [prepared dispatch design](r4-prepared-dispatch-design.md): `tools.ToolCallPreparer.PrepareToolCall(ctx, call) (PreparedInvocation, error)`, returning a `PreparedInvocation` that exposes `ToolIdentity`, `EffectSet`, `SchemaDigest`, `NormalizedCall`, `ArgumentDigest`, and single-use `Dispatch`. R2 must consume that seam rather than define a competing API. It provides an immutable registration snapshot (executor identity, trusted `EffectSet`, registry/policy generations and scope) coupled to normalized in-memory call arguments. Preparation performs validation and the current approval decision without executing the action or holding a registry/policy lock while waiting for user input or disk sync. After the durable marker, a single-use prepared invocation performs a short final generation/authorization fence and dispatches the exact captured executor; it never re-resolves by name. A stale fence returns a known `not_dispatched` receipt with the reserved `ActionID`. Mutation-queue work carries the same prepared invocation through the queue instead of rebuilding a Write/Edit executor or looking up the base registry again. The prepared-dispatch contract preserves current policy decisions and does not settle the pending D-01 behavior.

For sequential tool calls, commit the assistant tool-call row before the first call, then prepare and durably reserve each call in its own one-action `ActionBatchID`; wait for its receipt and, where necessary, its separate execution resolution before preparing the next call. This matches the existing sequential dispatch behavior and ensures a failure/cancel after one call cannot accidentally dispatch later calls. For parallel tool calls, prepare the entire assistant group first, commit all approved reservations and known denial receipts in one batch, then dispatch in parallel. In both modes, no underlying executor starts before the applicable session batch and global dispatch-ready marker are synced. A crash with a valid index and no marker for a particular reserved call proves it was not dispatched; if a marker exists but its receipt is absent, treat that call as unknown. The input/batch/receipt records use the assistant's original transcript ordinal for grouping and each message's `TranscriptIndex` for canonical delta order. `RecordExecution` persists a verifiable child identity when one exists. `RecordReceipt` persists the terminal typed tool message and outcome before Loop continues, but never resolves the global resource marker: an `unknown` or even `success` receipt can coexist with a still-running child. Only `ResolveExecution` may clear that marker after the shared owner observes positive quiescence (`ExecutionDone` closed after process/readers join) or records explicit durable operator reconciliation. The owner may write this later checkpoint after the caller has returned `cleanup_pending`; it is separate from the caller-visible terminal result. If quiescence cannot be proved, do not call `ResolveExecution` and retain workspace quarantine. `CommitCompaction` persists the actual projection before the next provider request uses it. `CommitTerminal` receives the final complete per-run transcript delta, all projections and the logical outcome; it verifies that prior sink commits for the same `(RunID, TranscriptIndex)` have identical canonical payloads, appends any missing final entries and terminal checkpoint, then syncs before acknowledging completion. The returned `CanonicalRunResult.Transcript` remains the per-call source of truth; the sink and final delta must agree by index and payload, so duplicate commits are idempotent and conflicting commits fail closed. If any sink method fails, Loop stops before the next provider request or dependent tool dispatch, returns a persistence error, and cannot acknowledge a successful durable save.

`RunIntentBatch` contains the `RunID`, unique `ActionBatchID`, assistant transcript ordinal/message, all approved `ActionIntent`s, and known `RunToolReceipt`s for calls rejected before reservation. Each `ActionIntent` includes physical session, owner generation, reserved action ID, assistant transcript ordinal, original tool-call ID, registered tool identity, workspace digest, canonical payload digest, and trusted registry `EffectSet`; it does not duplicate raw credentials or secrets. The session batch records its `prepared` checkpoint and rows first. Under the global index lock, `BeginIntentBatch` checks for unresolved conflicting workspace mutations and, only if clear, appends and syncs one `dispatch-ready` record for the complete batch. The conflict check and marker append are serialized together; another session cannot pass the check while a conflicting mutating marker is unresolved. Release the global lock after that short append/sync operation, before executor work. The executor starts only after both durable operations succeed. A present global marker means every approved call in the batch may have been dispatched; a missing marker (with a readable, valid index) proves that no call in it started. The marker is batch-level; an optional per-action started record may add evidence, but absence of one can never prove an action was not started. A batch containing only pre-dispatch denials needs no dispatch-ready marker. `RecordReceipt` syncs only the session receipt. `ResolveExecution` separately syncs a typed quiescence/reconciliation checkpoint to the session and then appends/syncs the corresponding global resolution; if the second operation fails, the global marker remains unresolved and quarantine stays active. All operations preserve IDs across retries. A receipt write/sync failure prevents another provider request and is surfaced as a persistence error; the durable intent remains unresolved on disk and is handled during recovery. A call rejected before reservation has no intent or `ActionID`; a reserved call fenced/canceled afterward retains its intent `ActionID` and gets a `not_dispatched` receipt.

The optional projection transport is per-call and must not add mutable loop-global `lastHistory` state. After R1's owner lane hands off, expose projections through this exact optional extension, defined in a new core file rather than changing the R1-owned result type:

```go
type ProjectedCanonicalLoop interface {
	RunCanonicalWithProjections(ctx context.Context, submission Submission, stream ...EventStream) (CanonicalRunResult, []CompactionProjection, error)
}
```

`AgentImpl` invokes this method once when available and uses the same returned projections for history and persistence. `RunCanonical` remains the compatibility path for loops without projections. The sink above is the durable checkpoint path; `ProjectedCanonicalLoop` is the typed return path. Include the captured revision in the per-run call (as an additive `Submission.HistoryRevision` or equivalent typed context value); do not synthesize it from events or mutable global history after execution. Do not alter the R1 shape until the R1 owner has handed it off.

Use an OS-backed session-file lock acquired **before** reading, repairing, or caching that file. Also use the workspace action index and its local mutation lock described below. Acquire locks in one order everywhere: session-file lock, then global workspace-index lock. Never hold the global lock while opening or waiting for another session file lock. The global lock protects only index read/check/append/sync transactions; the unresolved marker, not a lock held during execution, blocks a conflicting action in another session. On platforms where the current lock implementation is a no-op, either implement and test an equivalent lock or fail closed for concurrent/mutating session use; do not claim multi-process safety. Safe reads may proceed while mutation is quarantined only when the resolved executor has a trusted read-only effect. These are local advisory locks, not distributed leases.

The authoritative workspace quarantine index is independent of `sessionDir`: store one append-only JSONL file at `os.UserConfigDir()/go-cli/workspace-quarantine/<WorkspaceID>.jsonl`, with a sibling lock file. This coordinates cooperating CLI instances for the same OS user using the same standard user-config root, even when they use different session directories. This is a cooperation boundary, not an OS sandbox: if the user changes the standard config root (for example through platform environment), that instance is outside this lock domain. Do not allow per-session configuration to relocate the quarantine authority. Create directories with mode `0700`, files/locks with `0600`, use exclusive creation where appropriate, and sync the containing parent directory after every directory/file/lock/sidecar creation and every atomic rename before treating that metadata as durable. Sync file contents before returning a durable acknowledgment. If the user config root, lock, index, permissions, or required directory sync is unavailable, fail closed for mutation; never silently fall back to scanning only the currently selected session directory.

Before dispatch, `BeginIntentBatch` appends the complete session intent batch, then under the global index lock checks existing unresolved records and appends/syncs a `dispatch-ready` record. Any unresolved record whose trusted `EffectSet` permits workspace mutation/external effect blocks a new mutating/external action for the same `WorkspaceID`; trusted read-only work may proceed. The check and marker append are atomic with respect to cooperating processes, preventing a check-then-dispatch race across sessions. The executor starts only after both durable operations succeed. The global record carries `WorkspaceID`, `SessionID`, `RunID`, `ActionBatchID`, and a bounded list of action references `(AssistantTranscriptOrdinal, ToolCallID, ActionID, EffectSet, ExecutionIdentity?)`; it stores no raw args or credentials. A session intent without a global dispatch-ready marker is known not to have dispatched only when the global index is readable and structurally valid. A present marker means dispatch may have started for each reserved action in that batch, even if a prior `Sync` returned an error, so recovery treats a missing receipt as unknown. `RecordReceipt` writes/syncs only the session receipt; it never appends a resource-resolution record. `ResolveExecution` first syncs the typed session execution-resolution checkpoint and then appends/syncs the corresponding global resolution under the index lock. A crash or write failure between those commits leaves the global marker unresolved and quarantine active; recovery can retry resolution only from the durable proof, never from a receipt or from assuming the process stopped. The R1 `RunClaim` is process-local and does not close this cross-session TOCTOU window.

Safe-read classification is a cross-lane dependency on the independently reviewed `R4-EFFECT-01` trusted executor-identity/effect slice, mapped to source task `R4-BLD-01`. The effect must be bound to the executor returned by the registry, not inferred from a tool name or caller-supplied metadata. `read_only` is a predicate derived from the trusted registry `EffectSet`, not a separate incompatible effect enum. Effects must include behavior reachable through the executor: Git operations that can invoke repository-configured helpers (for example `core.fsmonitor`, external diff, or textconv) remain unknown/composite until a trusted first-party executor disables those program hooks or proves a restricted path. Until the seam is integrated, any unresolved/unknown effect is treated as mutating and blocked under workspace quarantine; R2 does not claim safe reads through untrusted or custom name collisions. The narrow seam can proceed from the accepted `r4-policy-design.md` and its review without waiting for R1; the full R4-BLD-01 policy implementation remains a separate task, and R4-BLD-02 remains gated by R3. R4's pending D-01 product policy remains unchanged.

Prepare a new or resumed store completely before publishing it into the live CLI assembly: resolve the selected physical session, create/open and lock the target file, recover it, build/validate its tree and branch, then atomically swap the store/tree/session pointers. Keep the previous file and lock until the swap succeeds. A failed target open/recovery leaves the old session usable. For a new session, create the file first and build a fresh empty tree with an empty root `ParentID`. `/resume` must not pass a physical file ID to `SessionTree.MoveTo`; file selection and branch/entry selection are separate operations.

## Compaction projection seam shared with R3

R3's preflight can compact the provider's effective history without creating a normal `AgentMessage`; R2 must persist that exact projection. Do not infer it from events, from final text, or from a later event-derived `Agent.History`. Keep the current R1 `CanonicalRunResult` shape untouched until its owner lane has handed off. Add a separate typed projection seam after that handoff:

```go
type CompactionCursor struct {
	PriorHistoryCount uint64
	TranscriptCount   uint64
}

type CompactionProjection struct {
	ExpectedHistoryRevision string
	Through                 CompactionCursor
	Summary                 string
}
```

The projection is returned per run with the canonical run result (not stored as mutable loop-global `lastHistory`). `ExpectedHistoryRevision` is an opaque revision captured with the immutable `Submission.History` snapshot and session/branch base; it changes on `SetHistory`, session/branch switch, or a committed history mutation. The sink rejects a projection from another source revision or active branch. Entries appended by this same `RunID` after the snapshot do not make its source revision stale. The cursor is always in the original run-start coordinate space `priorHistory + current canonical transcript delta`, never an index into an already-compacted/effective slice. `TranscriptCount` is the number of current-run transcript entries included from the beginning of the delta. If it is greater than zero, `PriorHistoryCount` must equal the total source `priorHistory` count; otherwise the boundary is not a valid prefix. The initial submitted user is only the first transcript-delta item and is counted once. Multiple projections retain their original provenance cursor and are never renumbered after an earlier summary is inserted. A boundary cannot split an assistant tool-call message from any matching terminal receipt.

The prepared restore input is a typed `SessionView` containing `{SessionID, BranchID, Revision, Messages, SourceEntryIDs}`. `Messages` and `SourceEntryIDs` are ordered and have equal length; each projected model-history message maps to the exact durable source `EntryID` that produced it. `Agent.SetHistory` and `EntriesToAgentMessages` must not erase this provenance before a run captures its snapshot. The run-start cursor maps `PriorHistoryCount` through this `SessionView`; transcript ordinals map through the returned current-run `TranscriptEntry` delta. Projection commit resolves the exact source `EntryID` by this mapping, never by matching role/content or by using an effective post-compaction array index.

After validating the expected revision and cursor, R2 maps that exact source boundary to a real final `SessionEntry.ID` and appends an `EntryTypeCompaction` record with `Summary` and `CompactedThroughEntryID`. The compaction record is an append-only projection marker; it does not delete source entries. Its `ParentID` is the current durable leaf and may be later than `CompactedThroughEntryID`. Restore must therefore rewrite `BuildContext`/`DeriveMessages` to select the latest applicable projection by its explicit source boundary, insert its summary at that boundary, and retain every uncovered suffix entry after that boundary through the current leaf; the physical row position of the marker is not the compaction boundary. Covered earlier prefixes and obsolete projection markers are not reintroduced. Reopening must yield the same one summary plus suffix, exactly once. A stale or unmappable projection is a persistence/protocol error; do not persist it against a guessed leaf.

For model history only, restore a compaction summary as one `Role="user"` context message with a fixed prefix that labels it as an untrusted summary of prior conversation, not a new request or instruction. Leave `InputKind` empty, attach no `ToolCalls`, `ToolCallID`, or `ActionID`, and keep the durable row as `EntryTypeCompaction`, never `EntryTypeUser`. The UI must retain its compaction type and must not render the summary as a newly submitted user prompt. This role mapping uses existing provider roles and does not elevate summary text to `system` authority.

## Recovery, torn tails, and orphan child quarantine

Recovery runs under both the session-file lock and the global workspace-index lock before the store/tree is exposed. First validate complete JSON records, version, entry IDs, sequence, parent links, and batch/index references without requiring every tool call to already have a receipt. A `prepared` batch may have a valid prefix because a failed append/flush/sync can leave some complete rows on disk. The canonical assistant row is always first in a session batch; recover its full call list, then correlate any intent-prefix rows by `ActionBatchID` and occurrence key. Reconcile each still-open call against the valid global index by `(RunID, AssistantTranscriptOrdinal, ToolCallID)`: a matching dispatch-ready action reference means it may have dispatched and missing terminal receipt becomes `unknown`; no matching marker means it could not have dispatched and recovery appends an `interrupted` receipt. This applies both to a partially persisted batch and to later sequential calls that had not yet acquired an intent row/batch. Preserve already-durable receipts. If the global index is unreadable, malformed, or unavailable, absence of a marker is not proof of no dispatch: fail closed and quarantine the workspace. Sync all synthesized closure receipts and any quarantine updates before running final tool-call group closure validation or exposing history. A malformed complete record, unsupported version, conflicting duplicate ID, invalid sequence, broken parent, or inconsistent already-terminal group still fails closed; never skip corrupt complete rows and continue with a partial history.

* A valid final JSON object without a trailing newline is preserved; append exactly one newline and sync before accepting new writes.
* A final suffix is repairable only when the parser proves it is truncated (for example, `unexpected EOF`). Copy the exact raw suffix to a quarantine sidecar and sync it; sync the sidecar's parent directory after creating it. Only then truncate the source to the last complete newline, sync the source, and sync its parent directory if repair required a rename/replacement. Invalid syntax that is not demonstrably truncation fails closed. Do not truncate or rewrite malformed complete/middle lines.
* The serialized JSON object, excluding its terminating LF, is capped at exactly 1 MiB. Append rejects a larger row before acknowledgment; the reader accepts exactly that same maximum plus the delimiter. Test 1 MiB−1, 1 MiB, and 1 MiB+1 symmetrically.
* A dispatch batch is not eligible to start until its complete session batch and global dispatch-ready marker have both synced successfully. A partial session batch without a marker therefore proves no dispatch; a valid marker, including one found after a caller saw a sync error, means dispatch may have started. Reconcile open assistant tool-call groups to `interrupted` or `unknown` using this rule **before** enforcing group closure. If a valid terminal receipt exists but the run terminal does not, restore the known receipt and mark the run incomplete/interrupted; do not resubmit the old user request automatically. Recovery status is surfaced so the user can choose a new request or reconcile.
* A pending resource identity is not a bare PID. `ExecutionIdentity` records the OS instance and the exact owned child/group instance (for example boot or host generation, PID plus process-start token, and verified process-group/job identity); do not persist command arguments or credentials. For a Unix process group, positive quiescence requires the owned leader to be waited, the owned group to be verified absent, and owned readers to be joined. This proves only that the recorded owned group is gone; it is not an OS sandbox or universal process-tree containment.
* If an intent has a child-spawn window with no persisted verifiable identity, a known/observable escape from the owned group, the identity is unsupported/unreadable, or an owned resource is still alive, persist/derive workspace quarantine. Block conflicting mutations across all session files with the same `WorkspaceID`; allow trusted safe reads and show the unresolved action. Release resource quarantine only after independently verified termination of the recorded owned resource or an explicit durable operator-reconciliation checkpoint. A stopped child can still leave `ReceiptOutcome="unknown"`; clearing resource quarantine never rewrites that receipt to success and never triggers replay. An actively escaping descendant that calls `setsid`/`setpgid` and closes inherited descriptors is not detectable by this process-group mechanism; R2 does not claim automatic containment or quarantine for an unobservable escape. Restart can verify only recorded owned identities, not every process that might have escaped. Unsupported platforms remain quarantined or fail closed until explicit reconciliation.

The only safe automatic tail repair is the verified final torn suffix. A valid no-newline record is delimited rather than discarded. A complete malformed line, invalid tree, or unknown version remains visible as an open failure requiring repair. After a writer error, recovery determines which exact records made it to disk using ID/payload idempotency; timestamps, in-memory `FlushedCount`, an `Append` return without `Sync`, or a cleared R1 in-memory RunSlot are not durability or process-exit evidence.

## Crash matrix

| Crash point | Durable state and restart behavior |
|---|---|
| Before user-input sync | No provider request has started. No run is acknowledged; user may submit again. |
| After user-input sync, before provider/tool intent | Restore the user input and an incomplete run marker. Never automatically call the provider again. |
| Partial session intent batch, or later sequential call not yet reserved, with no matching global dispatch-ready action reference | No executor for that call could have started. Recovery appends an `interrupted` receipt for each still-open call without a matching reference, syncs them, then validates the full tool-call group. |
| Global dispatch-ready action reference present, before/during executor dispatch | That reserved call may have started, including when a prior sync returned an error. A missing terminal receipt becomes `unknown`; do not dispatch again. If an owned child may still run or identity cannot be verified, quarantine conflicting workspace writes. |
| After side effect, before receipt sync | Same unknown/no-replay behavior. A live verified child retains quarantine; a stopped child can release resource quarantine while its action receipt remains unknown. |
| After receipt sync, before resource-quiescence and terminal sync | Restore the complete assistant-call/tool-receipt group and known receipt. | During append, flush, or sync | Caller receives persistence error and no durable ack. Poison writer, reopen/recover, compare IDs and canonical payloads, preserve valid prefix, quarantine only a demonstrably torn final suffix. |
| During/after compaction generation but before projection sync | Source transcript remains intact; do not claim the compaction was durably installed. After projection sync, restore its summary once and retain the suffix after its exact `CompactedThroughEntryID`. |
| Parent CLI SIGKILL while child continues | Startup verifies the exact recorded child/group identity. Safe reads may continue; conflicting workspace mutation stays blocked until verified exit or explicit reconciliation. No PID-only kill and no action replay. |
