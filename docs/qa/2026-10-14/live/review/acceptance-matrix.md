# Independent acceptance matrix for live Dot / Magpie runs

This review covers a real `go-cli` binary driven through Magpie and the local Codex task that coordinates the run. Keep the actor of every action explicit: a Dot request, a Codex-side action, and a human approval are different events. A model catalog response or provider configuration only proves discoverability/configuration; it does not prove an inference completed.

## Outcome rules

Record each row as `PASS`, `FAIL`, `INCONCLUSIVE`, or `NOT RUN`, with source paths and hashes. A row passes only when the evidence listed below agrees across independent surfaces. Missing, synthetic, stale, manually edited, or redacted-away fields make the relevant row inconclusive. The overall live-run claim passes only when all requested rows pass. State limitations separately; do not expand a narrow pass into a platform-wide or OS-sandbox claim.

Never put API keys, bearer tokens, cookies, full authorization headers, or credential-bearing config in evidence. Keep original global Codex/Magpie settings unchanged. Record only redacted config source, selected provider/model identifiers, relevant request/response metadata, and evidence hashes.

## Round-to-evidence linkage

For each real user turn, keep a small redacted ledger that links:

1. the turn number, actor (`Dot`, `local Codex`, or `human`), session ID and user input hash;
2. Dot's provider attempt/span to Magpie's completed upstream request and response IDs;
3. provider model ID, finish reason and provider usage fields, preserving `unknown` when absent;
4. each provider tool-call ID to Dot's prepared/approval/execution/result lifecycle;
5. observed filesystem or process state before and after the call; and
6. any screenshot/terminal capture and its source stream hash.

Record the correlation method explicitly: a shared request/session ID is strongest; otherwise use single-flight execution and matched time, model, and reported usage, and label it as timestamp-based. The current OpenAI-compatible adapter records selected provider/model and usage in its own traces but does not preserve the upstream completion response ID or served-model field in the returned message. If the gateway cannot provide a stable join key, call the association timestamp-based and keep it inconclusive when overlapping requests make the match ambiguous.

Do not merge retries into a single successful response. Record failed attempts and retries separately. A gateway can expose available models without completing a request, and a successful response can contain no tool calls; these are separate observations.

## Context-compaction protocol

Use a fresh, isolated session and an ordinary Dot conversation. Introduce a unique canary sentence exactly once, then continue with real prompts/responses and safe tool work until production compaction fires. Do not edit session JSONL or invoke a manual trim/compact operation. Preserve the pre-compaction and post-compaction session artifacts and production logs. After compaction, ask a neutral recall question in a new turn without restating the canary; inspect the actual provider request sent after compaction and verify that it contains the canary in retained context and that the answer matches. If no compaction event fires, report `NOT RUN` and adjust the next run rather than manually manufacturing evidence.

## Live PPTX protocol

Generate one fresh input JSON with `scripts/e2e_live_review/generate_fixture.py`. Save it with the run evidence and hash it. The fixture provides a unique title nonce, four exact distinct slide titles, three synthetic metric strings, and two prompts; it never generates a presentation. In turn 1, Dot creates the editable four-slide file through its own model-requested tool calls. Capture the first file and hash before sending turn 2. Turn 2 is a distinct user submission in the same CLI session and requests the single status change. Capture the resulting file and hash, then run `scripts/e2e_live_review/verify_pptx.py`.

The structural verifier is one part of review. It checks that turn 2 preserved the slide shape order, names, geometry, and embedded image bytes as well as all text outside the requested status replacement. Render every returned slide to PNG with LibreOffice and `pdftoppm` when those tools are available, open every slide at readable size, and record visible clipping, overlap, empty slides, unreadable text, broken images, and whether the status edit landed on slide 4. Save unmodified renders and screenshot hashes. A structurally valid deck can still fail visual review.

## Source inspection notes

This document is a review contract, not evidence that any live case has passed. The repository has earlier local deterministic-provider evidence under `docs/qa/2026-10-14`; that evidence proves real CLI/tool behavior against a local protocol simulator and must not be relabeled as Magpie inference or model-quality evidence. Record this live run in its own subdirectory and cite evidence by exact run ID and hash.

The current live runner sets the application's approval mode to `ask` and isolates the CLI `HOME`, config path, and working directory. It does not establish an OS-level filesystem/process sandbox. Unless an independently verified sandbox profile is added and observed, report Bash containment as untested and describe allow/deny as application approval behavior only.
