# R6-DES-TRUST-DISPATCH-01: Persistent project-trust revocation at dispatch

Status: designer handoff for builder review. This document is the implementation contract for closing the live-dispatch revocation gap. It does not change product code or claim that the behavior is implemented.

## Decision

Project-source trust has one monotonically increasing generation per canonical workspace root. Persist the active manifest and generation in the existing trust entry; persist revocation as a compact tombstone at the same canonical-root key. A grant and every revoke advance the generation, including revoke when no active entry exists. Revoke never deletes the last generation. Regrant replaces the tombstone with a fresh active manifest at the next generation, so an invocation captured before revoke cannot become valid again even when the source manifest bytes are identical. Overflow, malformed generation, store failure, lock failure, or unknown trust state denies dispatch.

Each verified project-source capability carries its canonical root and the generation that matched its manifest. Project-sourced tool registrations capture that immutable binding. Every ordinary, streaming, and queued prepared dispatch performs one final `CommitIfCurrent` against the persistent trust record, and only inside that check may it enter the existing process-local `DispatchFence.commit` linearization point. The lock order is always the trust-store OS lock, then `DispatchFence`; neither lock is held during approval waits, journal I/O, queue waiting, or tool execution.

The commit marker defines the boundary: a revoke serialized before it prevents dispatch and produces a known pre-dispatch result. A revoke serialized after it cannot claim to stop the already-committed action; in-flight work follows the existing R1/R4 cleanup and receipt rules.

## Evidence and existing contracts

- R6 already requires revocation to persistently advance trust generation so uncommitted old approvals become stale, while a committed action may finish ([`r6-entrypoints-design.md:31-35`](../2026-09-25-runtime/r6-entrypoints-design.md#L31)). Project trust remains permission to load a frozen project source manifest, not a tool effect or sandbox bypass; current config bytes must be the bytes that were verified, with no reopen-after-hash ([`r6-entrypoint-design.md:40-44`](../2026-09-25-runtime/r6-entrypoint-design.md#L40)).
- The R4 prepared-dispatch contract already requires a one-use permit, a final generation check immediately before execution, no locks across approval or execution, dequeue-time checking for mutation jobs, and a durable `not_dispatched` receipt after a reserved action is rejected before commit ([`r4-prepared-dispatch-design.md:74-95,119-137`](../2026-09-25-runtime/r4-prepared-dispatch-design.md#L74)).
- `TrustEntry` currently stores manifest version/root/digest and source records, but has no trust generation or revocation state. `RevokeTrust` removes entries. `FileTrustStore` serializes only through the mutex on that particular instance; `Add` is a load-modify-write, so two manager instances can overwrite each other's additions ([`trust_store.go:12-59,73-117`](../../../internal/approval/trust_store.go#L12), [`trust.go:45-48,85-94,116-140`](../../../internal/approval/trust.go#L45)).
- Existing private-file code provides the needed primitive: `privatefile.WithExclusiveLock(ctx, path, callback)` uses a stable `path.lock` sidecar and supports cancellation; atomic replacement uses a private sibling file ([`lock.go:11-22,37-101`](../../../internal/privatefile/lock.go#L11), [`privatefile.go:24-65`](../../../internal/privatefile/privatefile.go#L24)). OS advisory locking is implemented for Linux and macOS only; other platforms return an unsupported-lock error ([`lock_unix.go:1-35`](../../../internal/privatefile/lock_unix.go#L1), [`lock_other.go:1-15`](../../../internal/privatefile/lock_other.go#L1)).
- Prepared dispatch currently captures registry/approval/Plan generations and marks `DispatchCommitted` inside `DispatchFence.commit`; ordinary and streaming calls converge on that marker, and queued mutations use `commitAndInvoke` at dequeue ([`prepared.go:74-105,631-697,760-785,918-1028,1046-1090`](../../../internal/tools/prepared.go#L74)). The fence callback is expressly limited to an in-memory marker and must not do I/O ([`prepared.go:187-205`](../../../internal/tools/prepared.go#L187)).
- Project custom tools currently receive an assembly-time `IsTrusted` check and then use ordinary `Register`, while their `Execute` starts the configured command. This is a load-time gate only and does not tag each live invocation with its project trust state ([`assemble.go:2555-2609`](../../../internal/cli/assemble.go#L2555), [`custom_tool.go:43-63,87-110`](../../../internal/tools/custom_tool.go#L43)). Project MCP source selection records its manager, while `mcpServerSource.loadCurrent` calls `LoadTrustedWithManager` and accepts the newly verified capability on each reload ([`mcp_source_generation.go:46-64,227-262`](../../../internal/cli/mcp_source_generation.go#L46)). That allows an existing assembly's watcher to observe a later grant unless it also pins the assembly-time trust generation. MCP source generations are replaced through a reload callback and watcher; revocation can therefore wait for reload/polling, so final dispatch must enforce the epoch before that poll ([`mcp_generation.go:58-80`](../../../internal/cli/mcp_generation.go#L58), [`hot_reload.go:16-34`](../../../internal/mcp/hot_reload.go#L16)).
- The R6 snapshot handoff already defines the immutable `VerifiedProjectSources` capability and current-user-owned trust file boundary. It also says grants activate on a later invocation and project MCP/custom sources must be registered only from verified provenance ([`r6-trust-snapshot-api-handoff.md:20-33,35-51,72-78`](r6-trust-snapshot-api-handoff.md#L20)).

## Persisted state and migration

Keep the current JSON object keyed by canonical root and extend `TrustEntry` with:

```go
TrustGeneration uint64 `json:"trust_generation,omitempty"`
Revoked         bool   `json:"revoked,omitempty"`
```

An active source-trust entry has `TrustGeneration > 0`, `Revoked == false`, and its existing manifest fields. A tombstone has `TrustGeneration > 0`, `Revoked == true`, `Path == CanonicalRoot == map key`, `ManifestVersion == 0`, and no source records or digest. Set its `ExpiresAt` to a fixed past RFC3339 value as a compatibility fail-closed marker for older readers that ignore the new `Revoked` field. New code must use `Revoked`, not infer revocation from expiry. `TrustedProjects` and `trust list` omit tombstones or label them revoked; they must never display a tombstone as active trust.

Migration is lazy and does not rewrite files merely by reading them. A pre-generation active manifest record is interpreted as generation 1. Its current manifest and expiry behavior remain intact. A path-only/legacy entry still cannot authorize frozen project sources. The first grant or revoke writes the generation field under the transaction lock. A zero generation on a tombstone, noncanonical key, key/root disagreement, malformed entry, or generation overflow fails closed. Store reads do not chmod or repair the file. Existing ownership rules stay in force: current-user-owned regular file mode `0600`, private current-user-owned parent, atomic replacement and sync.

`RevokeTrust(ctx, root)` canonicalizes the root once. For an existing root, resolve symlinks and require a directory. For a deleted root, preserve the CLI contract: require an absolute clean path and resolve its nearest existing ancestor, which must already be canonical and a directory; append the missing suffix. This allows revocation after workspace deletion without accepting a noncanonical alias ([`trust_command.go:262-307`](../../../internal/cli/trust_command.go#L262)). In one store transaction it finds the current canonical entry and any old caller-path aliases that identify that same canonical root, takes the maximum valid generation, increments it, removes aliases, and writes one canonical tombstone. It writes a tombstone even when no record exists (generation 1). `TrustProjectSourceSnapshot` requires the already-confirmed snapshot, loads the canonical entry under the same transaction lock, increments its generation, and writes the active manifest at that generation. Legacy `TrustProject` must also use this transaction and cannot overwrite or lower a versioned epoch; its path-only record remains unable to mint a project-source capability. All three operations check `ctx` before waiting and after acquiring the lock. A grant remains ineffective in its grant invocation; the next load mints the generation-bound capability.

Tombstones are retained indefinitely, one small record per root that has been revoked, because a live old runtime can hold a prepared invocation for an unbounded time. Regrant overwrites that root's tombstone. This bounds storage to one record per distinct canonical root rather than accumulating revoke history. The guarantee covers clients using this generation-aware protocol; an already-running older binary that neither takes the sidecar lock nor checks generations cannot be fenced by the new binary and must be restarted before an operator relies on live revocation.

## Store transaction and platform contract

Add an optional transaction capability without changing the existing `TrustStore` method set:

```go
type TransactionalTrustStore interface {
    Update(context.Context, func(entries map[string]TrustEntry) (dirty bool, err error)) error
}
```

`Update` passes a fresh mutable snapshot that the callback must not retain. On a nil callback error, the store persists the map only when `dirty` is true and releases the lock after the durable write completes. Read-only dispatch checks return `dirty=false`. The callback must be short and must not call the public store methods recursively. `DefaultTrustManager` uses this capability for source-trust check, grant, revoke, and final commit; a custom legacy `TrustStore` without it cannot mint dispatch-capable project-source trust.

`FileTrustStore.Update` takes its instance mutex, then `privatefile.WithExclusiveLock(ctx, canonicalStorePath, ...)`, reloads and validates the current private JSON file under that OS lock, calls the transaction callback, and uses `privatefile.WriteAtomic` before releasing the lock when dirty. All public `Load`, `Save`, `Add`, and `Remove` operations use the same sidecar lock and instance-mutex-before-file-lock order. `Add` and `Remove` remain load-modify-write transactions, so independent `FileTrustStore` instances and processes do not lose distinct updates. Preserve the existing API shape while protecting the epoch invariant: `Add` may replay an identical same-generation record but cannot change fields at that generation or lower it; `Remove` converts any generation-bearing entry to the next tombstone and only physically removes unversioned legacy data; `Save` remains a whole-store replacement only if it preserves every existing generation (a removed versioned entry must be represented by a newer tombstone). Generation overflow rejects all three operations. Canonicalize the configured store path (absolute path plus canonical parent) once so all processes that resolve the same user config file take the same sidecar lock. Never unlink the stable `.lock` file.

`InMemoryTrustStore` implements `Update` with its own mutex and the same epoch/tombstone rules for tests or explicitly ephemeral use. Independent in-memory store instances are independent trust domains. Production CLI continues to inject one persistent manager at `$HOME/.config/go-cli/trust.json` ([`main.go:41-45`](../../../cmd/cli/main.go#L41)); there is no fallback from persistent-lock failure to process-local locking.

The cross-process guarantee is supported on Darwin and Linux, where `privatefile` provides cancellable advisory locking. On other GOOS targets, project-source grant/check/final dispatch fail closed with an explicit unsupported-lock/concurrency error; do not silently provide a weaker promise. If the product later requires Windows or another OS, add and review an OS-backed lock implementation before enabling project-sourced execution there. The trust file and sidecar remain private; lock-acquisition errors, ownership/mode violations, malformed JSON, or unavailable transaction capability cause a pre-dispatch rejection.

## Runtime interfaces and wiring

Add a narrow interface in `internal/tools` so tools does not import `approval`:

```go
type ProjectTrustBinding interface {
    CanonicalRoot() string
    TrustGeneration() uint64
    Valid() bool
    CommitIfCurrent(context.Context, func() error) error
}

type ProjectSourcedToolRegistrar interface {
    RegisterProjectSourced(context.Context, ToolDefinition, ProjectTrustBinding) error
}
```

`approval.VerifiedProjectSources` is the only production binding minted by a successful `CheckProjectSourceSnapshot`. Add its persisted `TrustGeneration` and an unexported reference to the generation-aware `DefaultTrustManager` when minting it. Its `CommitIfCurrent` verifies the seal, then calls a store-level read transaction: check the same canonical root, active state, expected generation, manifest version/digest identity, and expiry from the current persisted entry; do no project filesystem reads or config reloads; call the supplied short commit callback while the store lock is still held. A manually built or decoded config cannot create this binding.

At assembly, project custom tools use `RegisterProjectSourced` with the binding from the exact `VerifiedProjectSources` that supplied their configuration bytes. Project-provenance MCP candidates carry that same binding into `BeginMCPGenerationUpdate`; preserve its current all-or-nothing generation publish/disable behavior. User/global tools continue using their current registration path and carry no project binding. Registry/decorator/MCP generation updates must copy the binding into `toolRegistrationMetadata`, `registeredToolSnapshot`, protected proxy pins, and `preparedInvocationConfig`. A missing binding, invalid capability, unknown provenance, or wrapper that cannot preserve it rejects the project registration; never fall back to ordinary `Register` after a project registration failure. Every `Get`, `List`, search, and streaming proxy returned for a project tool must route through the captured prepared-dispatch path.

Apply the same binding to project skill adapters and project extension-provided tools when their provenance is exact. `registerSkillTools` reads project skills from the verified captured source manifest, so its deferred loader must retain the capability and materialize through the project-sourced registrar. Custom-tool and plugin-path provenance must come from `ProjectOverlayForVerifiedSources()` and be checked against the merged values before binding; a non-empty project slice replaces that layer's merged slice, while user/global-only registrations remain unbound. Do not infer project ownership from a merged `Config` alone. Project extension hooks and middleware execute outside the prepared tool dispatch seam and remain an uncovered live-revocation boundary in this design; do not describe them as protected by the tool binding.

For every project-owned `mcpServerSource`, latch the exact assembly-time `ProjectTrustBinding` (canonical root and trust generation) from the `VerifiedProjectSources` that supplied its initial bytes/config, and carry that binding with the source through candidate construction and `BeginMCPGenerationUpdate`. `loadCurrent` may re-verify sources to detect revocation or manifest mismatch, but it must compare the result with the latched root and generation; it must never replace the binding with a newly granted generation. A missing initial binding is also latched as unavailable, so a watcher created while the project is untrusted cannot activate after a later grant. If the latched binding is revoked, unavailable, or differs from the current verified capability, permanently disable that project source for the lifetime of the current assembly. Later polls in that assembly may keep it disabled but cannot publish tools under a later generation; only a fresh assembly can consume the new grant. This rule applies only to project-owned sources. User/global static configuration, MCP sources, and tools retain their current source and reload behavior without a project trust binding.

Make all prepared execution routes converge on the existing `preparedInvocation.commit(ctx)`:

```go
mark := func() error {
    return fence.commit(capturedFence, func() {
        if ctx.Err() == nil {
            invocation.committed.Store(true)
        }
    })
}
if projectBinding != nil {
    return projectBinding.CommitIfCurrent(ctx, mark) // trust-store lock -> fence lock
}
return mark()
```

This is an ordering sketch, not a request to export the fence's private `commit`. The callback is the existing in-memory marker and generation comparison only. The store lock is released after the callback and before the prepared executor runs. Direct `Dispatch`, `DispatchStreaming`, and the mutation queue's dequeue-time `commitAndInvoke` already reach `p.commit`; no path may substitute an `IsTrusted` check during `PrepareToolCall` for this final check. Queue admission/enqueue may capture the binding, but a queued job checks only when dequeued immediately before execution.

On trust-generation mismatch, tombstone, expiry, canceled lock wait, unsupported lock, or store error before the marker runs, the invocation remains uncommitted and one-use-consumed; no executor or MCP peer request starts. Do not classify by error text or sentinel alone: `DispatchCommitted()` is the authority for whether the final mark ran. If lock cleanup reports an error after the marker ran, the result is committed/ambiguous and must never be relabeled `not_dispatched` or retried. In the R2 durable path, after an `ActionID` is reserved, persist exactly one `not_dispatched` receipt for a terminal result with `DispatchCommitted()==false`. If reservation has not happened, do not invent an `ActionID`. Receipt persistence failure remains a journal/commit failure and must not trigger dispatch retry. A successful final commit followed by revoke is `DispatchCommitted == true`; preserve the existing unknown/success/error outcome and R1 quiescence rules until execution completes. The final check reads only the private trust record; it does not reopen project source files or hash executables, so it introduces no filesystem check-then-use window. Existing source-manifest changes are still detected at the next trusted load; live file monitoring is outside this handoff.

MCP polling and registration cleanup are still useful for removing stale tools and closing retired clients, but they are not the enforcement point. An old project MCP registration must fail the trust-generation commit immediately after revoke even if the reloader has not polled yet. A regrant with the same manifest produces a new generation and requires fresh assembly; the current assembly's project source latch stays invalid, and its watcher cannot publish a new client or proxy under that generation.

## TDD acceptance cases for the builder

Write these before implementation. Use deterministic barriers at approval return, trust-lock acquisition, final fence commit, queue dequeue, and executor entry. Assert executor counters and receipts, not just returned error strings.

1. **Two managers share a persistent root generation.** Grant through manager A, check through manager B, and verify both see the same nonzero generation. Revoke through B; A's old verified binding and prepared invocation both fail their final commit, report `DispatchCommitted()==false`, and never invoke the executor.
2. **Cross-process revoke during Ask.** A subprocess with a second manager revokes the root while the first process's Ask callback is blocked. Release Ask with allow. The old call fails at final commit; the reserved `ActionID` receives one durable `not_dispatched` receipt; the executor count remains zero. No trust lock is held while Ask is blocked.
3. **Revoke after permit, before direct dispatch.** Prepare and approve at generation `g`, revoke to `g+1`, then call `Dispatch`; assert one-use consumption, no executor side effect, no commit marker, and a known not-dispatched terminal result.
4. **Same live project custom tool, second call.** Assemble a project `CustomCommandTool` once at `g`, invoke its protected registry proxy once, revoke through a second manager, then invoke that same live proxy again without rebuilding Assembly. The second command never starts, despite the old definition remaining registered.
5. **MCP revoke before poll.** Hold MCP reload polling, prepare a project MCP call at `g`, revoke, then dispatch through the still-registered old proxy. Assert zero peer `tools/call` requests before the next poll. After polling, stale definitions are disabled/retired as already specified.
6. **All dispatch shapes share the check.** Repeat stale-generation rejection for direct prepared dispatch, streaming dispatch, and a captured mutation job revoked while queued. Streaming emits no chunk; the queue's terminal `not_dispatched` cannot be followed by worker execution.
7. **ABA is impossible.** Prepare at `g`, revoke to `g+1`, regrant the exact same source manifest at `g+2`; the old binding still fails and a freshly checked binding at `g+2` succeeds.
8. **An existing project MCP watcher cannot adopt a regrant.** Assemble and publish a project MCP source at `g`, retain an old prepared permit, and hold the watcher before its next poll. Revoke to `g+1`, regrant the identical manifest at `g+2`, then release the same watcher. The old permit fails and the current assembly permanently disables that source; subsequent polls and attempted calls through its prior registrations produce zero peer `tools/call` requests. Repeat with a poll during the tombstone before regrant, then poll again after regrant; it must remain disabled. A fresh assembly at `g+2` may call the peer.
9. **Commit wins before a later revoke.** Pause inside the executor after observing `DispatchCommitted()==true`, revoke from another manager/process, then let the executor finish. It is allowed to finish, and its receipt remains committed; revoke is not reported as cancel/quiescence.
10. **Independent stores do not lose writes.** Concurrent `Add`/generation updates through multiple `FileTrustStore` instances and subprocesses preserve every distinct root and produce one monotonic sequence for a shared root. Exercise actual sidecar locking, not only one instance's mutex.
11. **Cancellation while waiting for the sidecar lock.** Hold the lock in another process, start `CommitIfCurrent` with a cancelable context, cancel while waiting, and assert prompt context error, no fence marker, no executor side effect, and a terminal not-dispatched receipt when an action was reserved.
12. **Fail-closed migration and permissions.** A legacy full manifest loads as generation 1 without a rewrite; path-only legacy trust still cannot mint a binding; revoke writes an expired-compatible tombstone and next grant advances beyond it. Insecure/replaced files, lock sidecars, parents, malformed generation, overflow, or unsupported OS locks never authorize project dispatch.
13. **Canonical root and aliases.** An existing symlink/caller-path revoke canonicalizes once, increments the target root epoch, removes old aliases transactionally, and invalidates bindings minted for that root. A deleted canonical root remains revocable through the nearest existing canonical ancestor rule. Canonicalization failure does not touch another root.

In addition to the numbered cases, maintain a source-provenance matrix: project custom tools, verified project skill adapters after deferred materialization, project MCP tools before watcher polling, and project extension-provided tools must all retain the exact root/generation binding through their protected proxy; user/global custom tools, skills, MCP servers, and extensions must not acquire a project binding. Project extension hooks/middleware are explicitly outside this matrix and remain uncovered until they have a reviewed commit/dispatch seam of their own.

The project-extension assembly test may inject a `PluginLoader` into the private assemble state to exercise verified-overlay selection, registration, and prepared dispatch. A separate Darwin native-plugin test builds a real `.so`, changes the configured source after capture, and assembles the same verified bytes in two trust generations. Both assemblies must resolve to the same content-addressed materialization path because Go's plugin cache keys modules by path; the file lease must survive closing the first assembly while the second remains active and be removed after the final close.

Native Go plugins exceed the ordinary 1 MiB project-source file cap even in a small test fixture (the stripped fixture is about 6.6 MiB). Therefore only an explicitly project-sourced extension module whose path ends in `.so` may use the existing 16 MiB aggregate manifest ceiling as its per-file ceiling. The aggregate ceiling stays 16 MiB, all other project source files stay capped at 1 MiB, and both per-file and remaining-aggregate sizes are checked before allocating/copying captured bytes; streamed reads retain the same limits. Extension modules larger than 16 MiB and captures that would push the aggregate above 16 MiB fail before any plugin loader or `Init` callback runs. This exception enables the native proof and does not broaden other executable/configuration sources.

Suggested focused verification after those tests land: `go test ./internal/privatefile ./internal/approval ./internal/tools ./internal/cli`, followed by the repo's required `make verify`. Keep unit, subprocess, and full-suite evidence reported separately.

## Implementation ownership and limits

Builder scope is limited to trust entry/store transaction support, a generation-bound verified-source dispatch guard, project-source registration propagation, the project MCP source binding latch and no-rebind reload rule, and the shared prepared commit seam plus focused tests. Expected source boundary: `internal/approval/{trust.go,trust_store.go,project_source.go}`, `internal/privatefile/{lock.go,lock_unix.go,lock_other.go}`, `internal/tools/{trusted_registry.go,registry.go,middleware_registry.go,prepared.go,prepared_registry.go,mcp_generation.go}`, `internal/cli/{assemble.go,mcp_generation.go,mcp_source_generation.go,trust_command.go}`, and their focused tests. Extend only files required to carry the binding through the already-owned pipeline. Do not change trust manifest capture semantics, approval effect classification, Plan behavior, R2 journal schema, or the R1 rule that a post-commit revoke does not prove execution stopped.
