# Pi and OpenCode design reference

## Evidence boundary

This comparison is pinned to released code available on 2026-10-01: Pi **v0.99.2**, released 2026-09-30 at commit [`005af57d88ee23b33778f343a9595b32e67ff788`](https://github.com/earendil-works/pi/commit/005af57d88ee23b33778f343a9595b32e67ff788), and OpenCode **v1.18.34**, released 2026-09-30 at commit [`aec0b9a6d8898f68f923aaf08b7306d931fd9d76`](https://github.com/anomalyco/opencode/commit/aec0b9a6d8898f68f923aaf08b7306d931fd9d76). The go-cli comparison is against baseline `d5052d5612907f9fe073942ea7a7004b27c39958`. Pi product documentation is dated 2026-10-01 where used. OpenCode V2 specifications and docs are experimental and are excluded from shipped-capability claims.

| Runtime and cancellation | The Agent API exposes prompt, continue, abort, and lifecycle events; the coding agent composes that loop with its CLI/TUI. | `SessionPrompt` records the user input and executes a serialized per-session loop; the server/runtime is usable separately from the TUI. | `AgentLoop`, `Agent`, `Harness`, and `TurnRunner` separate execution from streaming and provide cancel/steer/follow-up seams ([interfaces.go](../../../internal/core/interfaces.go#L89)). Keep run ownership and cancellation in the runtime contract; UI streams are observers, not lifecycle owners. ## Decisions for current design work

- Keep session history, provider-turn admission, prepared tool dispatch, and user-facing events as distinct contracts. Persist enough identity to explain which model answered and which actions reached their dispatch boundary.
- Enforce Plan and approval rules on the exact prepared invocation, and document process/container isolation separately. A permission label alone is not a sandbox.
- Track the `/model` persistence gap and the subagent child-session persistence difference. For subagents, verify the assembled CLI's real runner and effective approval/trust behavior; the standalone factory's simulated fallback is not the CLI's configured runner.
- Treat output truncation, complete-response validation, retry policy, and cost accounting as separate mechanisms with separate budgets and evidence.
