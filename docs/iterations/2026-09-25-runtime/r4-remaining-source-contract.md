## Current registered-tool path

The real Assembly has a protected dispatch path already. `assembleTools` creates `DefaultToolRegistry` behind `DeferredToolRegistryAdapter`, registers the seven default tools and configured Git/custom/MCP/LSP/remote/skill tools, then `assembleApproval` obtains the registry's `DispatchFence`, creates the shared Plan controller and prepared approval policy, and wraps the registry in `MiddlewareToolRegistry`. `assembleProductionResilience` installs the path normalizer, synchronous execution wrappers, and mutation queue as prepared stages. `assembleExtraTools` registers the narrow first-party control and network-read capabilities; ordinary custom, MCP, extension, LSP, and remote registrations keep ordinary registration provenance. `assembleLoopAgent` gives this final registry to Loop, whose `buildToolDefinitions` copies `Parameters()` only when a registered proxy implements `tools.Parameterized`.

At dispatch, the protected proxy snapshots the exact registration, executor, schema, effect, generations, and prepared stages; it applies path normalization and validates the frozen schema when one exists, then asks the prepared policy before direct dispatch or captured mutation-queue dispatch. The protected `Get`/`List` proxies do not fall back to raw execution. These source slices are already present and reviewed; R4 does not need another registry or middleware architecture.

## Minimum remaining implementation and acceptance

### R4-EFFECT-01: complete the real effect/scope inventory

The effect enum includes `workspace_read`, but no production registration mints that effect or a non-empty `TrustedToolScope`. The existing inline-reader registrar gives only Read/Ls a completion proof; it registers an empty effect set, which resolves to `unknown`, and the builtins test asserts the scope fingerprint is zero. Grep/Find are ordinary registrations and also remain `unknown`. `preparedPlanCallAllowed` correctly requires a built-in `workspace_read` plus non-zero scope fingerprint, so no assembled local reader currently qualifies for that Plan Mode exception. Configured path checks still constrain the executor, but they are not captured in trusted identity.

Current Assembly effect map: `write`/`edit` are `workspace_write`; `bash` is `unknown` with local-process completion proof only; `read`/`ls` are built-in `unknown` with inline completion proof only; `grep`/`find`, all registered Git tools, `git_pr_create`, `remote_bash`, LSP, custom commands, MCP and extension tools are ordinary `unknown` registrations. `web_fetch`/`web_search` are the two narrow `network_read` registrations. `task_get/list`, `goal_get/list`, `ask_user`, `enter_plan_mode`, `exit_plan_mode`, and `tool_search` are narrow `control` registrations; todo/task/goal mutations remain ordinary unknown. This is fail-closed today. Git status/diff/blame and other Git paths that can invoke configured helpers must remain unknown until their full execution path is bounded.

Minimum follow-up: add one narrow registration path for reviewed, side-effect-free local readers whose executor is bound to a canonical, non-empty configured path scope. Preserve `unknown` for an empty/unrestricted path list, same-name custom replacements, unreviewed helpers, Git operations, and LSP. Bind the exact normalized path scope into the immutable identity; do not infer scope from tool name or completion proof. The existing `workspace_write` behavior remains approval-gated and the configured path checks remain in the executor.

Add an Assembly-backed effect inventory test that enumerates every registered definition and records its effect/provenance, including dynamic ordinary registrations as `unknown`. Extend it with a Plan Mode dispatch table: scoped audited local reads and the reviewed network reads are the only allowed read effects; every workspace/git/network/external mutation, composite helper, custom/MCP/extension collision, and unknown is stopped before executor invocation. Include two path roots to prove a prepared approval/Plan decision cannot cross scope, and retain the current same-name replacement, stale-generation, queue-dequeue, and direct/streaming single-use regressions. The bounded unit tests for these races already exist; the missing piece is the full assembled registry/effect matrix, not another copy of the seam tests.

### R4-BLD-02: finish model schemas and bounded capture

The registered default set is Read, Bash, Write, Edit, Grep, Find, and Ls. Only Write and Edit implement `Parameterized`; Read, Bash, Grep, Find, and Ls do not. `LoopAgent.buildToolDefinitions` therefore sends those five tools without a model-visible schema, and the prepared validator has no schema with which to reject their malformed or extra arguments before policy/dispatch. `TestPreparedRegistryAcceptsRegisteredDefaultToolSchemas` only checks that the list is non-empty; it does not inspect schema coverage. The same interface gap exists among assembled extras: `web_search`, `web_fetch`, todo/task/goal tools, and Plan controls have no `Parameters()` contract, while Git, custom commands, remote Bash, LSP, and SubAgent provide schemas. Enumerate the whole Assembly registry rather than adding schemas only to `RegisterDefaults`.

Minimum follow-up: expose an accurate object schema for every model-visible shipped built-in (including empty-object schemas for true no-argument controls), and test that schema validation and executor validation accept/reject the same representative calls. Cover required fields, types, enums/bounds, optionals, aliases, and a mixed provider/tool fixture. Unknown fields should be rejected where the actual executor contract does not accept them. Add an Assembly-to-Loop/tool-definition assertion so proxy capability preservation is tested at the consumer boundary.

Capture gaps remain in directory paths: Read builds the complete directory string; Ls collects all immediate entries then builds the full string; Find collects all matches before truncating to 1,000. These limits do not bound memory before accumulation. Read's regular-file byte limit and the default SSH client's bounded capture are already present; RemoteBash also bounds its returned output and stdout/stderr metadata. Keep those guarantees, but add a registered RemoteBash test that verifies output and metadata limits together. For directory tools, cap retained entries/bytes during traversal/formatting and test a large directory plus the pure-Go Find fallback, not only the `fd` happy path. Retain Grep's bounded capture and cancellation behavior.

The default Assembly still constructs `NewWebSearchTool()` without a provider, which installs `MockSearchProvider`; it returns successful mock content. `TestAssembleAgent_WebSearchDefaultUsesMockProvider` and the Brave-without-key fallback test assert this old behavior, directly opposite to the R4-BLD-02 requirement to fail clearly when no real provider is configured. Replace those assertions with a typed/unavailable error test for default and incomplete Brave config; keep configured `fetch`/Brave local-transport tests.

Path acceptance is partly complete and deliberately narrower than an OS sandbox. Keep the empty-path compatibility test; the current Assembly test already exercises configured absolute-path and symlink rejection across the default file tools, while the task's separate names `TestReadRejectsParentSymlinkEscape`, `TestRegisterDefaultsReadToolUsesConfiguredPathWhitelist`, `TestReadToolRejectsAbsolutePathOutsideAllowedPaths`, `TestReadToolRejectsSymlinkEscape`, `TestAssembleAgentPropagatesPathWhitelistToDefaultTools`, `TestDefaultReadGrepFindLsRejectAbsolutePathOutsideAllowedPaths`, and `TestDefaultReadGrepFindLsRejectSymlinkEscape` are absent. Do not duplicate those cases just to match names if the existing assertions are retained and expanded to cover the contract. Document that `AllowedPaths` constrains those file tools and does not confine Bash or eliminate filesystem TOCTOU. The other planned regressions `TestBuiltinToolSchemasMatchExecutors`, `TestSearchStopsAtBoundedCapture`, `TestGrepCancelReturnsContextError`, `TestWebSearchMissingProviderFailsClosed`, and `TestRemoteBashOutputAndMetadataBounded` are also absent; adjacent tests/reviews cover only the bounded slices noted above.
