# R3 breaker and loop enforcement handoff

Status: source-grounded implementation design; no product code or ledger changed. Source baseline: `9258330489847c752cec29f7d933ee46e71788e`. This handoff closes only R3-REM-02 (terminal-aware circuit breaker) and R3-REM-03 (live loop detection) from `r3-production-remaining-contract.md`; it does not complete R3 or change retry, cost, compaction, or provider routing policy.

## Terms and ownership

The loop detector observes a **frozen prepared attempt**: one registered tool identity and the digest of its normalized, schema-validated, frozen JSON arguments. It does not establish that approval passed, dispatch committed, an executor ran, or a receipt was persisted. Approval-denied and never-dispatched frozen attempts still count as attempts. They must not be reported as executed actions.

The breaker owns provider-attempt admission and provider-terminal classification. The stream producer owns its stream worker and request resources. The Loop owns cancellation of the active run, while the existing R1 RunOwner and RunCommit owner retain sole authority over run terminal sync, cleanup-pending state, and acknowledgement. Neither detector nor breaker may write a run terminal or durable receipt.

## R3-REM-02: breaker result follows the stream terminal

`DefaultCircuitBreaker.Execute` admits under its mutex, executes a synchronous closure, and records the closure's return immediately (`internal/production/circuit.go:117-147,186-220`). The CLI's `circuitBreakerModel.Stream` wraps only `inner.Stream(...)` creation in `Execute` (`internal/cli/output_guard_adapter.go:274-301`), so channel creation is currently recorded as success before any chunk is read. Its open path also creates an ordinary assistant final chunk with nil error; Generate does the same with assistant text (`output_guard_adapter.go:248-271,274-301`). Default Assembly has no configured fallback. The interface contract already requires a stream channel to close (`internal/llm/llm.go:222-230`), and provider streaming closes its channel from the owned producer goroutine (`internal/llm/provider.go:280-319`).

Keep the existing breaker as the sole state machine and keep its synchronous `Execute` path for Generate. Add only a narrow one-shot streaming attempt ticket to the same state machine: admission checks the existing Closed/Open/HalfOpen state and returns either `ErrCircuitOpen` or a ticket; the ticket accepts one terminal classification and updates the same counters/transitions. A ticket is not a second breaker and cannot be reused. A HalfOpen ticket reserves its probe slot; a caller cancellation releases that reservation without counting as success or failure, so a canceled probe cannot permanently consume the only HalfOpen slot.

The streaming adapter owns one reader pump. It calls the inner `Stream` only after breaker admission, validates chunks, retains the terminal classification, and does not publish a terminal error or close its output until the inner channel has closed and its pump has finished. A valid provider success requires exactly one well-formed `Final` followed by close with no later data. A synchronous setup error, nil channel without an error, provider/chunk error, close without `Final`, data after `Final`, or malformed terminal is a failure. Caller context cancellation is neutral only when the caller context is actually canceled; a provider timeout while the caller context remains live is a provider failure. If cancellation is requested, cancel the source and drain to close before completing the ticket. If the source never closes, keep the attempt and owning run pending; do not count success, retry, or acknowledge a completed run.

The model adapter must propagate typed `ErrCircuitOpen`; it must not turn an open circuit into assistant content or a successful `Final`. Count a provider's valid terminal independently of the outer output guard: a complete provider stream that is later rejected by output policy is still provider success. Do not print raw provider errors to logs as part of this change; preserve typed errors for callers and log only safe categories.

The default chain puts `outputGuardModel` outside the circuit wrapper (`internal/cli/output_guard_adapter.go:366-400`). Today its streaming goroutine returns early on source error, cancellation, cap overflow, or malformed data without draining the inner stream (`output_guard_adapter.go:115-185`); core likewise returns immediately on cancellation or a chunk error (`internal/core/loop.go:1133-1168`). These early returns can strand the breaker/provider pump while the run appears finished. Require wrapper channel close to be the owned producer's completion boundary: all stream sends stop and request/body cleanup finishes before close. On every early-error/cancel path, OutputGuard and core must cancel the inner source and drain its owned channel to that boundary before returning. This is needed for the normal assembled path, not a claim that an arbitrary non-cooperative custom model can be forcibly stopped. Such a source remains pending; the R1 owner must not issue success while the callback has not returned.

### Breaker acceptance

Add tests at the real `AssembleAgent` boundary with a loopback `httptest` streaming provider, the default wrapper chain, and a controlled server-side release point. Component-only breaker tests are useful but do not establish the assembled path.

- `TestAssembleBreakerWaitsForStreamTerminalAndClose`: return headers and a non-final chunk, hold the stream open, and prove the breaker remains in-flight rather than recording success. Release a valid final and close; only then observe success.
- `TestAssembleBreakerTerminalErrorOpensWithoutReplay`: return a typed mid-stream error after the channel has been handed out; assert the terminal reaches the caller, the breaker records one failure after source close, and there is exactly one provider request.
- `TestAssembleBreakerOpenIsTypedAndDoesNotDispatch`: open the breaker, call Generate and Stream through Assembly, and assert `errors.Is(err, ErrCircuitOpen)`, no synthetic assistant/final event, and no additional HTTP request.
- `TestAssembleBreakerRejectsNilOrIncompleteStream`: nil channel, close without final, final followed by data, and chunk error each fail closed; none may be recorded as success.
- `TestAssembleStreamCancellationWaitsForOwnedWorker`: cancel after a partial chunk; a cooperative server observes cancellation and closes, then the run returns canceled only after the reader/guard pumps have joined. A deliberately held source must remain pending until the fixture releases it; it must not produce success or a retry.
- `TestAssembleOutputGuardFailureStillJoinsProvider`: trigger an output-guard rejection after the provider has produced a complete stream; verify provider success is recorded only after source close and the rejected candidate is not committed.

### Breaker implementation surface

Expected source changes are limited to `internal/production/circuit.go` and its tests for the one-shot stream ticket; `internal/cli/output_guard_adapter.go` and tests for terminal-aware pump/open behavior and output-guard drain; `internal/core/loop.go` and tests for cancellation/error drain to the stream-close boundary; and `internal/llm/llm.go` / provider tests to make the close-after-resource-cleanup rule explicit and verify the built-in provider path. An optional streaming-ticket interface keeps existing custom `CircuitBreaker` implementations source-compatible; the assembled adapter must fail closed if the configured breaker does not implement it. If custom model implementations cannot honor the stream contract, report them as pending/non-cooperative; do not add an unbounded goroutine or claim that context cancellation stops them.

## R3-REM-03: observe frozen attempts while the run is active

The current Assembly middleware observes only after `Run` or `RunCanonical` succeeds (`internal/cli/assemble.go:2512-2595`), skips observation on errors, and always adds a next-turn reminder. It ignores `LoopDetectionResult.Disposition`. The detector's default kind is `"tool"` (`internal/production/loop.go:170-192`), while LoopAgent emits `"tool_call"` before dispatch (`internal/core/loop.go:709-727,819-840`); those events contain a name and call ID, not normalized arguments. Treating `message.ToolCalls` as canonical would be wrong: they are model proposals before registry lookup, normalization, schema validation, or policy. The configured same-tool threshold is already wired, defaults to 3, and the detector's existing same-tool algorithm counts consecutive equal keys (`production/loop.go:170-220,296-312`). Production `Disposition` defaults to `warn`; Assembly config currently wires thresholds but not disposition (`assemble.go:1487-1497`, `internal/config/types.go` LoopDetectorConfig).

Add one synchronous, observational prepared-stage callback to the existing audited `tools.PreparedToolStages` pipeline. Invoke it after the registration snapshot, path normalization, captured-schema validation, mutation-payload validation, and `freezeToolCall`, but before policy/approval and before constructing a `PreparedInvocation` (`internal/tools/prepared_registry.go:101-151`). Its value contains only the captured `TrustedToolIdentity` and `FrozenToolCall.Digest()`; it carries no raw arguments, call ID, executor, policy result, or dispatch capability. Those are the same immutable identity/digest values later exposed by a successful real `PreparedInvocation.ToolIdentity()` and `.ArgumentDigest()` (`internal/tools/prepared.go:291-339,352-390,582-600,657-672`). The callback may return an error to reject the attempt; a nil return merely resumes the unchanged normal policy → fence → invocation pipeline. It cannot construct an invocation, mark `DispatchCommitted`, create a completion proof, skip approval, or invoke an executor. Keep it in the existing trusted assembly stages rather than adding a general observer registry.

The detector key is the full registered identity plus argument digest, excluding ToolCallID. Use the existing same-tool consecutive-repeat policy: the first key occurrence is count 1, a different key resets to 1, and the configured threshold triggers at `count >= threshold` (default 3). Compare full identity, including registration generation, executor fingerprint, and scope, so a replacement registration is a different key. Do not log the digest or raw arguments. Count only frozen prepared attempts: unknown tools, failed normalization/schema validation, and values that cannot be frozen do not reach the callback. A later approval denial or a prepared invocation that never enters its executor is still an attempt and remains counted.

Keep the prepared-stage boundary narrow. Add an immutable `tools.FrozenPreparedAttempt` value containing only `TrustedToolIdentity` and the 32-byte argument digest, and one optional callback on the existing trusted stages. Only the fixed internal Assembly installs this callback; it is not an extension or user-plugin hook. The callback is invoked synchronously and may only return nil to continue or an error to reject; it receives no mutable call, executor, `PreparedInvocation`, dispatch marker, completion signal, or proof constructor. A nil result does not approve the call or bypass any existing gate. For detector plumbing, adapt the identity snapshot plus argument digest to a fixed-size `production.PreparedAttemptKey` through an unambiguous domain-separated encoding; an optional method on `DefaultLoopDetector` consumes that key and applies the existing consecutive-count rule. Do not fabricate an `AgentEvent` or place synthetic data on the user event stream to smuggle this fact.

Give each `Run`/`RunCanonical` a private detector session and cancel-cause context. Do not store live counters in `production.RegisterLoopDetector` or reset a globally registered detector; that registry is process-shared. A run-local session owns its threshold state, sticky first detection, and cancel function, and is discarded when the wrapped run returns. Preserve the existing default `warn` disposition and next-turn reminder behavior. To make termination explicitly selectable without changing default behavior, add a validated optional `production.loop_detector.disposition` setting (`warn` default, `terminate` opt-in; `steer` retains reminder semantics). On a terminating threshold, set a typed `core.ErrLoopDetected` cause and cancel the current run; report the same fixed typed error from the prepared callback. After the delegate returns, the wrapper must inspect `context.Cause(runCtx)` and surface `ErrLoopDetected` even if a non-durable proxy converted the preparation rejection to an ordinary tool result and core returned only `context.Canceled`. Use no reminder as a substitute for stopping the current run.

Both execution routes already converge on the prepared registry: the ordinary protected tool proxy prepares before dispatch, and the durable `runCommitConsumer.prepareInvocation` uses `ToolCallPreparer` (`internal/tools/middleware_registry.go:164-183`, `internal/core/run_commit_consumer.go:367-414`). Propagate `ErrLoopDetected` after writing the existing known interrupted/error receipt in the durable path; do not swallow it as an ordinary tool-policy denial. In the parallel path, the consumer prepares the group before starting dispatch workers (`run_commit_consumer.go:600-653`); if the observer cancels during preparation, assert no executor starts after the threshold and every assistant ToolCall receives exactly one canonical known/terminal receipt. The existing Loop / RunOwner path emits and syncs its terminal outcome; the detector must not do that work itself.

The post-run path may continue adding a reminder for `warn`/`steer`, but it must not re-observe `tool_call` events as frozen attempts or double-count them. Keep any other event-only dimensions advisory unless actual source events provide trustworthy facts; this slice does not invent edit/test evidence or turn model-proposed tool calls into dispatch facts.

### Loop acceptance

- `TestPreparedAttemptFactsMatchInvocation`: through a real `MiddlewareToolRegistry`, obtain an allowed `PreparedInvocation`; assert the observer receives exactly its `ToolIdentity()` and `ArgumentDigest()`, and no raw args or call ID. Repeat through the actual durable `runCommitConsumer.prepareInvocation` route.
- `TestPreparedAttemptCountsBeforeApproval`: return a policy denial after freeze; assert the attempt was observed once, no `PreparedInvocation` was returned, and the executor ran zero times.
- `TestLoopDetectorStopsRealRunAtThreshold`: use real Assembly/Harness, a real prepared registry, and an executor call counter. At the configured threshold for the same identity+digest, assert typed `ErrLoopDetected`, no executor for the triggering attempt, no subsequent provider dispatch, and one R1-owned terminal sync. Also prove a different args digest or changed registration identity resets the consecutive count.
- `TestLoopDetectorParallelGroupDoesNotDispatchAfterThreshold`: produce a real parallel tool-call response with duplicate frozen calls that reaches threshold during preparation; assert no later group executor is started, each call has one canonical receipt, and no duplicate action evidence is fabricated.
- `TestLoopDetectorRunStateIsIsolated`: run two turns/Assemblies; a prior run's counts do not affect the next and no per-run observations appear in the global production registry.
- `TestLoopDetectorWarnRemainsDefault`: with no disposition setting, a threshold preserves warning/reminder behavior and does not cancel; with explicit `terminate`, the active run stops at the threshold.

### Loop implementation surface

Expected changes: `internal/tools/prepared.go`, `prepared_registry.go`, and `trusted_registry.go` for the immutable frozen-attempt value and one trusted stage callback; `internal/production/loop.go` for a fixed-size prepared-attempt key and the same consecutive-count rule while retaining current threshold/disposition defaults; `internal/cli/assemble.go` and `internal/config/{types.go,validator.go}` for per-run session installation and opt-in disposition; `internal/core/run_commit_consumer.go` and its tests for fatal propagation/parallel pre-dispatch handling; plus tool, core, and CLI assembly tests. Keep all observation and cancellation state inside one run; do not add a new process-global registry or event store.

## Verification boundary

The current named component tests do not prove either assembled behavior. The implementation gate should first run the new named tests, then the affected race packages (`internal/production`, `internal/llm`, `internal/tools`, `internal/core`, `internal/cli`) with `GOMAXPROCS=2`, `-p 2 -race -count=1`. Preserve the prior failure, cancellation, open-circuit, and warning-default cases. Do not claim a whole-R3 gate, provider retry budget, durable replay safety beyond existing R1/R2 ownership, or successful termination of a non-cooperative stream source from these slices.
