# R7 Extension Tool Projection Readiness Handoff

**Status:** Designer proposal for independent review  
**Exact source baseline:** `develop` at `c02a1604cbc61e545028e9ead068ce4db262c22d`  
**Scope:** Assembly handling after a configured extension successfully loads and initializes, but one of its requested tools cannot be registered into the assembled tool registry. This document is the only planned change in this handoff; it does not amend the protected task ledger.

## Decision

Treat any error returned while projecting an initialized extension tool into the Assembly tool registry as an Assembly failure. Return no `AgentAssembly`; preserve the typed tool-registration error and the existing cleanup error chain. Emit a redacted registration-failure record, and emit `assemble_extensions_ready` only after every extension tool has registered successfully. Do not add a general `AssemblyDiagnostics` or degraded-Assembly API for this slice.

The failure policy applies to actual `ToolRegistry.Register` errors, such as an invalid tool name/schema or an MCP name reservation. It does not redefine duplicate-name policy. `tools.DefaultToolRegistry.Register` explicitly retains last-registration-wins behavior (`internal/tools/registry.go:17-22,61-64`), and its existing registration path replaces a prior entry (`internal/tools/mcp_generation.go:540-568`). A plugin tool that replaces a built-in is therefore not an instance of the current `Register`-error gap. Any policy change for built-in replacement needs a separate acceptance decision and must preserve the existing registry contract unless that decision changes.

This is the narrow fail-closed boundary for the reported gap: the extension initialized successfully, so silently omitting one of its requested tools would return a runtime that does not match the configured extension. Failing Assembly avoids presenting that partial projection as ready. It does not change existing fail-on-error behavior for `PluginManager.Load` or `Init`.

## Source evidence and additive contract

`AssembleAgent` runs `assembleTools` before `assembleExtensions`; any extension assembly error is joined with `s.runCleanup()` before the function returns (`internal/cli/assemble.go:410-421`). `assembleExtensions` creates and retains the `PluginManager` before loading it, calls `Init`, then currently logs and ignores each tool registration error before appending hooks/middleware and logging ready (`assemble.go:1070-1092`). At registration time, `prepareRegistrationMetadata` snapshots parameter schemas with `freezeToolSchema`; it deep-copies JSON-compatible values but does not enforce the prepared schema keyword subset (`internal/tools/mcp_generation.go:573-592`; `internal/tools/prepared.go:436-463,498-568`). A channel or cyclic/non-JSON value in `Parameters()` fails that existing snapshot with `tools.ErrPreparedValueNotJSON` (`internal/tools/prepared.go:38-39`); unsupported keywords are rejected later by `ValidateParameterSchema`/`validatePreparedSchemaNode`, not by `Register` (`internal/tools/prepared_registry.go:290-316`). The deferred registry can also reject an MCP-reserved name (`internal/tools/deferred.go:287-296`).

The Extension Registry already preserves successful tool registration order, but it exposes only bare tool values (`internal/extension/registry.go:43-58,74-92,282-290`; `PluginManager.Tools` at `internal/extension/plugin_manager.go:385-392`). It already records coordinator-assigned extension ownership for hooks and exposes owner-bearing `HookRegistration` values (`registry.go:133-152,326-336`; `internal/extension/types.go:111-117`). Add the analogous owner-bearing `ToolRegistration` snapshot and `PluginManager.ToolRegistrations()` while keeping `Tools()` source-compatible. Record the owner from `extension.Name()` in the per-extension staging registry during coordinator Init and copy that metadata only when the stage commits. Do not infer owner from `Tool.Name()`; extension code controls that value.

Add a narrow typed error in `internal/cli`, for example `ExtensionToolRegistrationError`, carrying safe owner, tool, and coarse failure-class fields plus an unexported underlying cause. Its `Error()` must not print the cause, schema, arguments, plugin path, or arbitrary extension text; `Unwrap()` retains the original error for `errors.Is`/`errors.As`. Diagnostic owner/tool labels should preserve only short ASCII identifiers matching `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`; replace any other label with `<redacted>` without changing registration acceptance. Use the same safe labels and a stable class (`non_json_schema` for `tools.ErrPreparedValueNotJSON`, `name_reserved` for `tools.ErrMCPNameReserved`, or `registration_rejected` otherwise) in `assemble_extension_tool_register_failed`; do not attach the raw `err` field. No new global ToolRegistry collision rule, effect grant, dispatch route, or Hook DTO behavior is part of this change.

When a tool projection fails, stop the loop immediately and return the typed error. Do not append this manager's hooks or middleware and do not log `assemble_extensions_ready`. The successfully projected prefix may remain in the private assembly-local registry, but it is not published: later Agent/Assembly construction and the registry exposure occur only after `assembleExtensions` succeeds (`assemble.go:429-438,487-560,1262,1356`). Do not attempt manual per-tool rollback or call `PluginManager.Shutdown` directly in this error branch.

## Cleanup contract

The common Assembly close owner is initialized before subsystem assembly (`internal/cli/assemble.go:612-638`). On any `assembleExtensions` error, `AssembleAgent` already calls `s.runCleanup()`; that joins the same close owner (`assemble.go:395-421,775-781`). `closeResources` shuts down each retained PluginManager in reverse order and waits for the published shutdown to complete (`internal/cli/assembly_lifecycle.go:634-648`). Since the manager was appended before `Load` and this failure occurs after successful `Init`, the initialized extension receives its normal `Shutdown` through that existing owner. The error return must preserve both `errors.As` access to `ExtensionToolRegistrationError` and any cleanup errors via the existing join. This slice must not create a second shutdown path or claim that cleanup succeeded when it returned an error.

## Source-trust and lifecycle boundaries

This hunk must be integrated separately from the active R6 loader/source-binding changes in `internal/cli/assemble.go`. It may consume only the loader output already authorized by the R6 frozen-source boundary. For project-owned plugin files, post-verification loading must use the exact bytes captured in the current `approval.VerifiedProjectSources` capability (or R6's reviewed private materialization of those bytes); it must never reopen the original project path. `docs/iterations/2026-09-30-runtime/r6-trust-snapshot-api-handoff.md:66,74-76` defines that requirement. Any test loader seam must be private to the `cli` package, invoked only after the same source/provenance checks, and receive the captured capability/bytes rather than an unverified path. Do not add a public `AssembleOption` that can replace the loader or bypass trust.

Keep the R7 Hook DTO/privacy contract unchanged. This task does not edit `internal/cli/extension_bridge.go`, Hook actions, hook error DTOs, tracing attributes, project trust policy, or live Hook/Middleware revocation semantics. The configured native-plugin success journey remains required; the existing `TestConfiguredGoPluginLifecycle` exercises a real configured `.so` through load, Init, hook dispatch, and Assembly close (`internal/cli/native_plugin_lifecycle_test.go:26-112`).

## TDD acceptance for the Builder

1. **Owner snapshot:** add `TestToolRegistrationOwnerSurvivesStageCommit` (or equivalent) in `internal/extension`. Two extensions register tools in order. The returned `ToolRegistrations()` snapshot preserves order and records the coordinator owner, even when a tool's own name suggests another owner. Mutating the returned slice does not alter registry contents. Existing `Tools()` behavior remains source-compatible.
2. **Configured mid-batch rejection:** run the real `AssembleAgent` path with extensions enabled and a private, verified-loader test seam. One initialized fixture extension registers a valid unique tool followed by a parameterized tool whose schema contains a channel value (or whose tool name is held by an actual MCP reservation). For the channel case, the existing registration snapshot must fail with `tools.ErrPreparedValueNotJSON`; do not add semantic schema-keyword validation to `Register`. The failure must produce `*ExtensionToolRegistrationError` with the correct safe owner/tool and stable class `non_json_schema` (or `name_reserved` for the MCP case); `errors.Is` must still reach the exact underlying sentinel. Assert `assembly == nil`, no extension-ready record, exactly one `Shutdown`, and the redacted failure record contains no source path or schema/error canary. No tool from the successful prefix may be dispatched or returned to a caller. The test must exercise `AssembleAgent`, not call `assembleExtensions` alone.
3. **Configured positive control:** extend the existing real native-plugin journey with one valid, uniquely named tool. Assert it is present/executable after `AssembleAgent`, the configured extension remains usable, and Assembly close records exactly one normal `Shutdown`. Keep the existing supported OS/CGO behavior: a supported native-plugin test may not silently skip when its required CI gate is enabled.
4. **No duplicate-policy regression:** explicitly document/test that this task does not turn every duplicate tool name into a failure. Preserve `DefaultToolRegistry` last-writer-wins semantics and any existing builtin replacement expectation. The mid-batch negative case must fail for a real registration error, not for a newly invented collision policy.
5. **Trust-preserving injection:** the test seam must not authorize project sources. Exercise the same verified-source check as production; for project-owned input, prove the injected loader receives/uses the captured bytes and that changing the original path after capture cannot change the extension materialized by the loader. Keep the R6 binding implementation in its separately owned hunk/commit.

The narrow implementation surface is owner-bearing tool registration metadata in `internal/extension/{types.go,registry.go,manager.go,plugin_manager.go}` plus the failure return/logging in `internal/cli/assemble.go` and targeted tests. Because R6 also owns `assemble.go`, the Builder must coordinate the hunk and rebase/integrate after the R6 byte-binding change; this handoff grants no permission to overwrite that work. No task-ledger, CI, Makefile, Hook DTO, or unrelated tool-registry edits are authorized by this design.

## Acceptance mapping and non-claims

This closes the concrete configured-extension case where a successfully initialized extension tool is omitted after `Register` fails and Assembly still reports ready, covering R7-BLD-01 truthful lifecycle status/error (`docs/iterations/2026-09-25-runtime/execution-tasks.json:1594-1609`) and the Assembly wiring boundary (`docs/iterations/2026-09-25-runtime/r7-lifecycle-design.md:68,194-202`). It does not complete R7-BLD-01, R7-DES-01, or R7-REV-01; does not resolve dormant APIs; and does not claim external exporter conformance or broader R7 acceptance.
