# R2 local-quiescence proof handoff

Status: source-based design finding; no product changes. Reviewed recovery validator `b18e78bf7c0c231d487d7b0085fc419538806611` and the R1/tool lifecycle APIs in `98a4cafb04564e7201fe57b454bea379855aa87f`.

## Finding

`session.validateExecutionResolutionEvidence` accepts `ResolutionLocalResourcesStopped` only when its referenced `ActionStateExecution` row has `ExecutionIdentity` (`internal/session/durable_recovery.go:498-518`). That excludes a legitimate trusted synchronous executor with no asynchronous resource. It also treats identity as the gate even though `core.ExecutionIdentity.Validate` checks only process-group/job identity shape and explicitly does not prove that the resource stopped (`internal/core/execution_identity.go:19-67`). Keep identity validation for rows that carry one, but do not use identity presence as quiescence evidence.

R1 provides useful in-process lifecycle signals, but not a per-action durable proof. `tools.PendingExecutionError` promises that `ExecutionDone` closes only after a resource is positively stopped and joined (`internal/tools/pending_execution.go:3-15`); `core.executeSingleToolRegistered` registers that channel with the owner on error (`internal/core/parallel_tools.go:152-188`), and `runOwner` holds the run claim until callback/transcript/workers/resources finish (`internal/core/run_owner.go:88-107,407-409`). The owner counts live workers/resources; it does not export which prepared action completed which resource set. A callback return or absence of `PendingExecutionError` is not enough for global resolution.

The local process path has stronger private evidence: `managedLocalCommand.collect` waits for the leader and output readers and records whether the owned process group is gone (`internal/tools/process_scope.go:90-162`); on delayed cleanup, `observeProcessCompletion` closes only after the leader/readers join and the group is positively absent (`:267-289`). Bash uses this lifecycle but returns ordinary success after it (`internal/tools/bash.go:230-292`); neither the process proof nor a structured `ExecutionIdentity` currently reaches the core sink. Remote Bash deliberately distinguishes local transport completion from remote command completion and keeps uncertain remote execution pending (`internal/tools/remote_bash.go:178-233`). That boundary must remain: stopping an SSH/HTTP client is not remote terminal evidence.

Write/Edit are synchronous when invoked directly: `WriteTool.Execute` and `EditFileTool.Execute` perform their filesystem operation inline (`internal/tools/write.go:200+`, `internal/tools/edit.go:80+`). The configured mutation-queue path is different. `WithMutationQueue` enqueues a per-file job and waits for either its result or `ctx.Done()` (`internal/tools/middleware.go:71-130`); `DefaultFileMutationQueue.startWorker` may still be applying that job after the caller returns on cancellation (`internal/tools/mutation.go:240-254,257-279`). Its current result channel is per job, but it is not surfaced as a lifecycle receipt to R1. Therefore direct Write/Edit may use an explicit prepared synchronous-completion contract; queued Write/Edit must use the exact job-completion channel and stay pending if the caller stops waiting first.

## Minimal proof and validation change

Keep `ExecutionResolutionEvidence` and its `local_resources_quiescent` value. Add one small typed completion proof to `core.ActionExecution` and its durable `session.SessionEntry` execution row. The proof is a closed set tied to the final prepared invocation, not inferred from `EffectSet`, a tool name, a return value, or a PID:

- `prepared_executor_complete`: the sealed `tools.PreparedInvocation`'s final executor/wrapper completion channel closed. It may be emitted only when that prepared pipeline guarantees its synchronous stages have returned and own no detached work.
- `queued_job_complete`: the final prepared mutation-queue stage's per-invocation job channel closed after its handler returned. `ctx.Done()` must not close this channel; it remains pending until the queued effect stops.
- `owned_resources_joined`: all resources registered to this invocation produced their positive completion receipts. Include `ExecutionIdentity` for OS process-group/job members that require identity-based recovery checks; identity is supplementary metadata and still not itself a stopped signal.

The existing sealed `PreparedInvocation` is the narrow place to expose this proof because it captures the exact final executor and its dispatch fence (`internal/tools/prepared.go:548-560,596-632`). The minimum extension is `ExecutionDone() <-chan struct{}` plus `ExecutionCompletionProof() (ExecutionCompletionProof, bool)` on that sealed interface. The proof is available only after that channel closes; the captured executor/wrapper/queue owns its closure. This is a per-invocation completion receipt, not a second dispatch permit or general lifecycle framework. If an installed wrapper cannot join or expose its resource, that invocation has no local completion proof and stays unresolved.

`WriteTool.Execute` and `EditFileTool.Execute` can issue `prepared_executor_complete` only for the final inline chain after every installed stage has returned; their base filesystem work needs no process identity. If the prepared stages include `WithMutationQueue`, the invocation instead gets `queued_job_complete` from the result channel for that exact queued job. `WithMutationQueue` must retain/register the accepted job's completion when its caller selects `ctx.Done()`; returning the context error is not a join. The queue worker itself may be long-lived, but one job's result channel closes only after its handler returns (`internal/tools/mutation.go:240-254`). Custom handlers/wrappers that can leave untracked work cannot issue either proof. Bash/StreamingBash use `owned_resources_joined` only after the existing process-group, leader, and reader checks have succeeded; pending process completion reuses the actual `ExecutionDone` signal, and remote Bash never turns that local signal into remote-terminal evidence.

`ActionExecution` and the durable execution row need only a `CompletionProof *tools.ExecutionCompletionProof` (plus the optional existing `ExecutionIdentity`). Keep the execution-resolution checkpoint's `EvidenceRef` pointing to that exact row. Add the same typed proof field to `session.SessionEntry`; no parallel session enum or duplicate identity shape is needed. `validateExecutionResolutionEvidence` should then require: matching complete action occurrence and intent; a dispatched action; an execution row after the intent and before resolution; a well-formed recognized completion proof; and exact equality between the proof's executor snapshot and the intent's persisted `ToolIdentity` snapshot (registration generation and executor fingerprint included). For `owned_resources_joined`, validate every listed resource receipt and validate any supplied identity shape. A row containing identity but no completion proof must fail. A no-resource proof does not require `ExecutionIdentity`.

The execution-proof data is a structured fact written through the prepared invocation/queue owner path. Recovery validates that fact and its row/intent linkage; it does not treat identity as proof, recreate runtime authority from the persisted identity/effects DTOs, or add a second signature mechanism. Unknown/config-controlled executors, untracked helper-capable callbacks, MCP/remote lost-response outcomes, and subagent work without its own durable lifecycle remain quarantined. A known local resource may later be proved stopped while its receipt remains `unknown`; resolution never rewrites the receipt or replays the action.

## Bound run identity for the next consumer

The current core seam has `WithRunCommitSink`/`RunCommitSinkFromContext`, but the context carries only the sink (`internal/core/run_commit.go:30-57`). `RunCommitSink`'s comment says the adapter is bound to a prepared session/workspace, yet it has no identity getter; `ActionIntent` requires caller-supplied `SessionID`, `WorkspaceID`, and `OwnerGeneration` (`:96-111`). `RunIDFromContext` already supplies the owner claim ID (`:11-26`, injected at `internal/core/run_owner.go:256`). `PreparedSession.View()` exposes physical `SessionID` and branch/revision, but no workspace (`internal/session/durable_contract.go:18-25`); the session preparer derives its physical ID in `PrepareNew` (`internal/session/durable_jsonl.go:63-109`). No production call sites for `BeginIntentBatch` or ID generators for action/batch IDs exist yet.

Add only a typed binding alongside the existing sink context:

```go
type RunCommitBinding struct {
    SessionID       string // physical ID from PreparedSession.View()
    WorkspaceID     string // canonical ID from WorkspaceIndex.EnsureWorkspace()
    OwnerGeneration string // generated by the runtime owner, never a PID
}

func WithRunCommitBinding(context.Context, RunCommitBinding) context.Context
func RunCommitBindingFromContext(context.Context) (RunCommitBinding, bool)
```

Attach the session/workspace binding after session preparation and workspace-index bootstrap; inject the runtime-generated `OwnerGeneration` into it before entering the run. `RunIDFromContext` continues to supply the per-run claim ID, and `RunCommitBindingFromContext` supplies the other three fields for `ActionIntent`. Generate `ActionBatchID` once per assistant dispatch group and a fresh `ActionID` per reserved invocation in core; retain those exact IDs and payloads across append/sync retry. Do not derive identity from a display label, cwd string, tool name, or unbound sink, and fail before provider/tool dispatch if durable mode lacks a complete binding. Keep the approved `RunCommitSink` interface unchanged. Add narrow tests that missing binding blocks `CommitInput`/provider entry, retries reuse the exact generated IDs, and separate calls/runs do not collide.

## Child run boundary

`SubagentTool` delegates through `subagentDispatcherAdapter.Dispatch` (`internal/core/subagent_tool.go:345-379`); `realSubAgentRunner.Run` creates a fresh agent/harness but calls `h.Submit(ctx, prompt)` with the parent context (`internal/core/real_subagent_runner.go:114-129`). The current run-ID owner overwrites the child run ID, but `RunCommitSink` remains inherited unless explicitly replaced. Reusing the parent sink would write child input/tool receipts into the parent's open action group; dropping it would silently allow non-durable child mutations. Durable subagent execution therefore needs a child-session factory that prepares an independent physical session/branch, fresh run identity and owner generation, and a child-bound sink, while reusing the same workspace index and `WorkspaceID`.

The parent `dispatch_subagent` marker cannot itself reserve the same workspace as a mutation while the child must reserve that workspace; doing so can block the nested child behind its waiting parent. A context-level sink mask or event-stream mask must never bypass an existing unresolved workspace-index marker. Only after R4 proves the exact first-party orchestration registration is pure scheduling, and the child has an independent prepared session/sink on the same workspace index, may a separately reviewed typed delegation fact avoid creating a competing parent mutation marker; all actual workspace effects remain child-owned markers. That proposal is not approved for implementation by this handoff. Until the child sink/lifecycle closure and marker semantics are reviewed, durable mode must reject delegation before launch. Plan Mode and untrusted same-name/custom subagent tools remain denied; no name-based quarantine bypass is acceptable.
