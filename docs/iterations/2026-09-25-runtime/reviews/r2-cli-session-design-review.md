# R2 CLI session design review

Reviewed snapshot: `72b82ad3c25fe2dc1b12a6a5b952d3514311e25a` (`r2-cli-session-handoff.md`), based on source snapshot `b7ffe0bc6d4d7795fe54c058189e7699a038b1f1`. This is a source-based design review; no code or tests were run. The overall direction is implementable, but the handoff needs the following lifecycle and selection details before approval.

## Required revisions

1. **Scope “new physical session” to a CLI/session invocation, not each run.** The decision says “A new run creates a fresh physical file” (line 9), while the existing REPL is one `REPLSession.Run` that repeatedly calls `executeTurn`/`TurnRunner.RunTurn` from `readInput` (`internal/cli/repl_session.go:125-138, 514-565`). The manager owns one selected physical handle across those turns. State that a new command/REPL session invocation prepares a new physical session by default; each REPL turn borrows and returns a lease on that same handle. This preserves the intended per-turn RunCommit identity without creating a new empty file for every user message.

2. **Avoid reacquiring a lock already held by the manager.** The replacement rule at lines 48-50 prepares/recoveries the target before close-requesting the old handle. That is right for a different physical ID, but deadlocks if the target is the same ID: `PrepareResume` opens the file and waits for its exclusive `flock` (`internal/session/durable_jsonl.go:132-138`, `internal/session/flock_unix.go:22-49`), while the manager's current `PreparedSession` retains that lock until `Close` (`durable_contract.go:90-100`). Define same-ID/same-branch selection as a no-op; same-ID/different-branch selection must reuse the existing prepared handle after the run-lease safe point and perform the durable branch-selection operation there. Only a different physical ID is prepared independently before swapping. Do not close the current handle first just to make same-ID `PrepareResume` work.

3. **Refresh the in-memory slash tree after durable commits without writing the transcript twice.** The table at lines 24-25 correctly removes `persistSession` as a durable writer and line 28 builds the tree/view from the prepared snapshot, but it does not say how that tree advances after each turn. Today `setupSlashContext` builds it once (`internal/cli/repl_session.go:287-315`), and the legacy `persistSession` is what appends each new turn's user/assistant entries into the in-memory tree (`:901-958`). After the durable sink owns those rows, a later `/resume`, `/switch`, or `BuildContext` can otherwise see a stale tree. Require a refresh/update from the same `PreparedSession` canonical snapshot after successful terminal sync and before accepting the next slash command or user turn. This is a projection update only, not a second journal append; a snapshot-specific strict tree builder or equivalent narrow adapter is sufficient.

4. **Bind `prompt --fork` to an exact source physical session.** The existing flag carries only an entry ID (`internal/cli/prompt.go:64-83, 302-333`). With durable mode defaulting to a fresh physical file, that entry cannot be resolved safely unless a source file is selected. The line 28 statement that `--fork` is not a physical selector should also say that durable `--fork <entry-id>` requires an exact `--resume-session <physical-id>` (or an equally explicit source-ID argument), and that the entry is validated in that file. Missing source identity must fail before provider entry; never search the directory or choose a “latest” file.

## Accepted boundaries

The handoff correctly moves durable preparation/recovery ahead of publishing the runtime; makes configured persistence mandatory rather than logging and falling back; distinguishes display labels from physical IDs; treats the old boolean `--resume` as unsupported unless an exact resolver exists; and keeps physical session selection separate from branch/entry selection. The workspace-root canonicalization and digest are explicit and fail on path-resolution errors. It also correctly makes input sync precede provider entry, requires terminal/transcript/compaction sync before durable success, prohibits a second legacy transcript writer, and rejects child runs before their first provider request until independent child-session ownership exists.

The lease model is implementable with the existing `PreparedSession` lock and `core.WithRunCommit` binding, provided the reviewed core completion-signal handoff is incorporated first. The command path must surface final manager/`PreparedSession.Close` errors: `CloseRunCommit` only returns a per-run lease, while current `AgentAssembly.Cleanup` is a no-error callback and currently ignores store close errors (`internal/cli/assemble.go:255, 681-710`). The handoff already calls for classified durable close errors; keep that as an acceptance requirement when choosing the manager API.

The handoff is **needs revision before design approval** for the four items above. Its acceptance matrix is appropriately labeled as future real-command/crash-restart validation, not existing evidence.

## Fixed follow-up review

Follow-up snapshot: `38e44683df9c5beee3b226ed2b32e221003d07b5`, a docs-only revision of `72b82ad3c25fe2dc1b12a6a5b952d3514311e25a`. The four findings above are closed:

- A physical file is prepared once per selected CLI session; interactive `RunTurn`s borrow the same handle.
- Same ID/same branch is a no-op. Same ID/new branch reuses the locked handle at a safe point; only a different ID gets an independently prepared target.
- After successful `CommitTerminal` sync, the CLI refreshes slash-tree state from the same canonical prepared-session snapshot, without another journal write.
- Durable `prompt --fork` requires an exact source physical ID and validates entry ownership before provider entry.

The follow-up also correctly specifies dynamic completion-signal handoff while the dispatch worker is still counted; one owner-cached `context.WithoutCancel(callbackCtx)` bookkeeping context bounded once by the existing cleanup timeout, never reused for dispatch; and propagation of the manager's final `PreparedSession.Close` error through CLI shutdown. Same-ID lock avoidance is consistent with the actual exclusive-flock contract, and the updated matrix covers session reuse, tree refresh, fork identity, and close failure. No implementation tests were run because this was a document-only design review.

**Final CLI design verdict: approved for design**, with one integration prerequisite: line 3 still labels core handoff `9bdef4a3bbe1d51f3b0289fea15f31004185288b` as approved/fixed, although the separate review of that exact snapshot found it needs revision for the dynamic `Done` and cancellation-bookkeeping semantics now referenced here. Before implementation relies on this dependency, update the cross-reference to the separately reviewed, approved core-handoff revision. This dependency does not reopen the CLI lifecycle findings above.
