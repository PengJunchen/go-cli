# R2 core consumer design review

Reviewed snapshot: `9bdef4a3bbe1d51f3b0289fea15f31004185288b` (`r2-core-consumer-handoff.md`), parent `b26933069e9f85edc3c940ce2caaed4aff160068`. This is a source-based design review only; no implementation or tests were run. The `cc40940` to `9bdef4a` delta is a sound, narrowly scoped recheck of the same completion channel when cancellation or timeout wins the select, but the full handoff still needs the following changes before design approval.

## Required revisions

1. **Completion `Done` is not available at the pre-dispatch registration point.** Lines 34 and 40 say to retain/register `CompletionSignal.Done` before calling `Dispatch`. In the prepared-tools API, `PreparedCompletionSignal` is a fixed handle, while `Done()` can be attached during dispatch or queue acceptance (`internal/tools/prepared.go`, `PreparedCompletionSignal` lifecycle; `internal/tools/prepared_completion.go`, `begin`). Sampling `Done()` before dispatch therefore sees nil for valid inline or queued executions and can misclassify them as having no proof. Register an owner-held placeholder containing the full occurrence and fixed signal handle before dispatch while the worker is counted. After normal/streaming dispatch returns or errors, the worker must transfer the handle's final `Done`/proof state to the same owner before decrementing its worker count; the owner must not observe a quiescent gap. Only a nil value from that final handoff means no completion signal. Cover dispatch rejection/error and queued cancellation through the same path.

2. **Cancellation persistence needs a bounded bookkeeping context.** Line 62 requires recording not-dispatched suffix receipts and committing a terminal outcome after cancellation/timeout when persistence is healthy. The callback context is canceled, and the session append/index APIs reject canceled contexts at entry, so using that context makes this required bookkeeping fail immediately. Derive a bookkeeping-only context with `context.WithoutCancel(callbackCtx)`, retaining the existing run binding, and bound it by the run owner's existing `cleanupTimeout`. Use it only for durable receipt/resolution/terminal bookkeeping, never to launch provider or tool work. A deadline or IO/sync error means no acknowledgement and the marker stays unresolved; filesystem sync itself is not interruptible, so promise only context checks at operation boundaries.

3. **Name all default CLI tools that lack completion proof.** Lines 54 and 102 identify StreamingBash, but default Write/Edit are also unproven: the default CLI wraps its diff generator in `*GitDiffGenerator` (`internal/cli/assemble.go`), while the prepared-tools inline proof path recognizes only the approved inline generator (`internal/tools/trusted_registry.go`). Consequently default Write/Edit can produce no completion signal either. State that default Bash, Write, and Edit are not durable-closed until their separately reviewed proof seams exist; the existing nil-proof behavior must leave markers unresolved and must not imply full default CLI closure.

4. **Record the implementation dependency.** The source base named in line 3 (`b269330`) does not contain the prepared completion-signal API this design consumes. Require integration of the reviewed tools completion API (`1386d02`, cherry-pick `575ef32`) before the core consumer implementation begins. This is a sequencing dependency, not a defect in the proposed core ownership model.

## Accepted design boundaries

The handoff correctly keeps the seven-method sink error-only and session-independent in core; prepares once and uses the same invocation for ordinary and streaming dispatch; writes intents/index admission before executor entry; serializes receipt persistence in canonical order; and separates outcome from local quiescence. The owner-only late writer, explicit terminal-sync-success fact, lease release after local resources join even when persistence is poisoned, REPL base handle plus per-run lease, exact compaction/terminal prefix, and typed child-delegation rejection are coherent with the approved R2 session and local-proof contracts. The `9bdef4a` immediate `Done` recheck closes the select-boundary race once the signal-handoff timing above is corrected.

This review does not claim code, test, runtime, or recovery closure. The fixed handoff is **needs revision before design approval**; the three behavioral revisions and one sequencing note above are the complete findings for this snapshot.

## Fixed incremental follow-up review

Reviewed follow-up: `84ce030594228a9b5b8a3ebd5ff303580fc108a3`, a documentation-only delta to `9bdef4a3bbe1d51f3b0289fea15f31004185288b`. The rejection above remains the verdict for 9b; this section records the final verdict for 84ce.

The follow-up closes the three behavioral findings:

- `PreparedCompletionSignal` is a stable handle while `Done()` is dynamic. The core registers an owner-held placeholder before dispatch, then transfers the final channel/proof from the same handle while the dispatch worker is still counted. The transfer is atomic with worker/resource accounting, covers return/error/panic and accepted queued work, classifies nil only after final handoff, and preserves the existing separate `never_dispatched` path for a rejected final fence. The cancellation/timeout select rechecks the same channel(s) before stopping, and a single safe-point wait uses one existing cleanup bound for a sequential action or parallel task set.
- Cancellation bookkeeping uses one cached, bounded cleanup-only context that preserves the callback's run binding/values, shares the existing `cleanupTimeout` across receipt/resolution/index/terminal writes and late drain, and cannot be used for provider/tool dispatch. The text correctly limits cancellation to boundary checks rather than promising an interruptible filesystem `Sync`; timeout or IO failure withholds acknowledgement and retains quarantine.
- The default proof boundary now names ordinary Bash with a supported sandbox/process-group path separately from default `Write`/`Edit` using `GitDiffGenerator` and `StreamingBash`. It does not claim those default Write/Edit/streaming paths are durable-closed without captured trusted proof, and prescribes preserving receipts while leaving markers unresolved and stopping later work.

The `1386d02` prepared-completion API dependency is explicit and correctly remains a prerequisite to consumer implementation; the handoff does not claim that this API is already present in the stated `b269330` source base. The existing one-shot run lease, late-writer ownership, poisoned-terminal behavior, and sequential/parallel receipt ordering remain consistent with the earlier approved R2 boundaries. No tests were run because this delta changes design documentation only.

**Final design verdict for 84ce: approved for implementation handoff.** This approval is for the core consumer design only; it is not implementation, integration, test, restart, or recovery acceptance. The earlier 9b rejection is retained as history and is superseded only by this fixed follow-up conclusion.

One non-blocking wording clarification is requested in the next docs-only edit: line 68's “or existing owner policy marks the run” must mean a status transition only. Marking the run quarantined never substitutes for a completion signal/resource join and never releases a live lease. Lines 66 and 70 already establish the required join-before-release behavior; the follow-up should make that interpretation explicit so the implementation lane cannot misread it. This clarification does not reopen the 84 design approval or require another full design review.
