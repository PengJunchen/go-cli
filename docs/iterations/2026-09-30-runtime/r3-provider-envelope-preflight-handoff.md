# R3 first-request provider-envelope preflight handoff

Status: bounded designer handoff for the separate provider-envelope follow-up in `r3-acceptance-audit.md`. This document does not close R3-DES-01, authorize a provider/protocol, change product policy, or modify the durable current-submission repair. The R3 provider and compaction documents remain design contracts; R2 implementation and restart-safety review remain gates.

## Boundary and source evidence

The current Loop checks durable or non-durable message size at `loop.go:698-726`, then applies dynamic tool filtering at `728-746`, and dispatches the resulting messages/options at `1384-1387` ([`loop.go`](../../../internal/core/loop.go#L698)). The preflight receives only messages, estimator and the compaction ceiling. It cannot account for the tool schemas and provider envelope that the model will receive. The selector's `ModelInfo` has `InputTokenLimit`, `ContextWindow` and `MaxOutputTokens`, but these limits are not attached to the request at this boundary ([`llm.go`](../../../internal/llm/llm.go#L319), [`model_selector.go`](../../../internal/llm/model_selector.go#L848)).

R3 compaction already defines the budget order and its unknown fallback: direct `InputTokenLimit` takes precedence; otherwise derive an input limit from `ContextWindow` less the output reserve; cap by the configured compaction ceiling; apply the existing 20% safety margin; subtract the final tool-schema and protocol-framing estimates. Missing model limits permit the local ceiling as an explicitly unknown provider limit, not a claim of provider fit. A known direct input limit does not receive a second output deduction. The compaction ceiling remains distinct from generation `MaxTokens` ([`r3-compaction-design.md`](../2026-09-25-runtime/r3-compaction-design.md#L21)).

R3 provider design requires complete provider-scoped model identity and one resolver/catalog authority; it also keeps unknown model metadata explicit and defines sampling precedence as per-call explicit value, model setting, provider setting, then adapter default. The contract review says compaction budgeting and generation output caps must remain separate ([`r3-provider-design.md`](../2026-09-25-runtime/r3-provider-design.md#L22), [`r3-provider-design.md`](../2026-09-25-runtime/r3-provider-design.md#L27), [`r3-provider-design.md`](../2026-09-25-runtime/r3-provider-design.md#L39), [`r3-contract-review.md`](../2026-09-25-runtime/reviews/r3-contract-review.md#L58)). `ResolvedModel` already pairs its resolved candidate with a `ModelSpec`, but the selected candidate's metadata is not carried through the Loop preflight boundary. A cycler or post-switch model must not borrow the primary model's limits.

## Request admission contract

For the bounded main-request path, preflight the finalized logical request plan consumed by the provider adapter. This is not proof of exact wire tokenization or provider acceptance: only terms established by an estimator bound to the active adapter may be estimated. The selected candidate identity, its own model metadata, final messages, and generation options form one immutable request plan. Dynamic tool filtering is materialized once; the same frozen tool definitions and generation values feed both the estimate and dispatch. No option is rebuilt, tool list re-filtered, candidate re-selected, or output cap changed after admission without creating a new plan and re-running preflight.

Follow the existing compaction-design order for this boundary: consume steering/follow-up, materialize the final filtered tools/options, estimate the request, compact if needed, re-estimate the changed messages with the same candidate/options, then dispatch. If a change in messages requires a different tool set, create a new plan and re-estimate that exact set before dispatch.

The smallest useful seam is an internal prepared-request plan that the Loop creates and an adapter-facing consumer must consume for each physical `Stream` dispatch. Its snapshot contains the existing `llm.CandidateProposal` (and therefore its resolver-issued `ResolvedCandidateHandle`), the `ModelSpec` paired with that same candidate, the final message projection, and the materialized `GenerationOptions`. It also carries the resulting envelope estimate and a private single-use consumption marker. Keep the plan internal and immutable after creation; it is a request value, not a new runtime, public option, or selector-policy redesign.

Preparation and consumption are distinct. Preparation applies the ordered `llm.Option` closures once after final dynamic tool filtering, deep-copies the resulting finite `GenerationOptions` values and schema data, and estimates that frozen snapshot. The estimator and provider adapter must both receive that same snapshot. Dispatch must not reapply the original closures, re-filter tools, rebuild the request, reselect the candidate, or alter the output cap. The adapter-facing consumer can materialize the frozen values directly or through one canonical option derived from the snapshot; either way, it must not execute the original closures again. `llm.Option` is a function over the finite `GenerationOptions` struct, and `WithTools` captures a slice ([`llm.go`](../../../internal/llm/llm.go#L391), [`llm.go`](../../../internal/llm/llm.go#L411)); defensively copy pointer values, slices, and nested schema structures before estimate and dispatch.

The plan is ephemeral and contains no credential material. Candidate identity and `ModelSpec` must come from one `ResolvedModel` (or equivalent resolver-issued snapshot); no API key or credential lookup enters the estimator. A cycler that currently chooses inside `Stream` must offer a metadata-only peek that pairs one `CandidateProposal`, its own `ModelSpec`, and a private selection lease without building an adapter or advancing mutable cycle/session-affinity state. Plan consumption is the commit/stale-plan boundary: the existing Loop `OperationDispatchAuthority` validates the same proposal, consumes the selection lease at most once, and rejects a stale lease before granting a dispatch permit. The existing adapter path remains responsible for the one-shot `DispatchPermit` and `BeginDispatch` at the actual provider boundary. A stale plan is discarded and the candidate is re-peeked and re-estimated; it cannot dispatch or mint a permit. Candidate changes on switch, cycle, or an already-authorized later attempt always require a newly prepared plan tied to that exact proposal and metadata. This preserves current retry/fallback authority and does not authorize a new retry.

Within this bounded main-operation path, every provider `Stream` call must consume exactly one matching prepared plan: the initial attempt, each already-authorized safe retry/failover proposal, and the single already-authorized overflow recovery attempt. Initial estimate/admission runs after the Loop has created its operation authority but before entering `ProviderOperationRunner.RunProviderOperation`; a reject, estimator error, or cancellation before the first attempt therefore creates no breaker ticket and does not change breaker state. A race that makes the initial cycler selection lease stale at consumption must be reported as a typed `no-dispatch` outcome that the runner maps to its neutral breaker result, never `StreamFailed`; do not mislabel it as provider failure or cancellation. Once an attempt has been admitted, a retry/fallback/overflow candidate is independently re-preflighted inside the existing logical operation and consumes that operation's existing shared attempt budget. It must use the same operation authority, proposal antecedent, candidate handle, and adapter permit rules; preflight never mints a proposal, permit, retry, or additional operation. A candidate-plan error after an earlier dispatched failure returns through that already-admitted operation result, so it neither adds a breaker ticket nor rewrites the terminal attempt facts. Summary, continuation, and other operation kinds keep their existing behavior.

`RequestEnvelopeEstimate` should report disjoint message, final tool-schema, protocol-framing and multimodal terms, each with a known/unknown state and reason. The enabled protocol adapter owns its framing estimate; unsupported protocols remain disabled under R0. Use the existing estimator for message and JSON-marshaled final schema structures, while keeping framing overhead distinct so terms are not counted twice. An ordinary custom `llm.Option` is not opaque once applied: its finite `GenerationOptions` result is frozen and estimated like any other option set. A custom adapter/model/protocol whose actual request behavior cannot be represented by that snapshot, or whose required term has no estimator or conservative bound, remains unknown and stops before dispatch. An estimator error or canceled context is a pre-dispatch failure, never a zero-cost estimate.

## Budget resolution

Let `C` be the configured compaction ceiling (`Compaction.MaxTokens`, default 8000), `I` the active candidate's positive `InputTokenLimit`, `W` its positive `ContextWindow`, `O` the effective output reserve, and `E` the sum of estimated final tool schemas plus protocol framing. The message budget follows the existing R3 compaction proposal:

1. If `I > 0`, `raw = min(C, I)`; do not subtract `O` again because `I` is already an input limit.
2. Otherwise, if `W > 0` and `O` is known, `raw = min(C, W - O)`. Resolve `O` from the effective generation cap after R3 sampling precedence. Clamp a positive requested cap to the active model's positive `MaxOutputTokens` before storing it in the plan; use the same clamped value for estimation and the provider body. When the request has no explicit/configured output cap, use the known `MaxOutputTokens` as the reserve. Preserve option presence: an explicit `MaxTokens=0` is not “unset” and must not be replaced with metadata. If the effective cap/reserve cannot be established, the derived input limit remains unknown.
3. If no input limit can be derived because candidate limit metadata or the output reserve needed for `W` is missing, use `C` only as the existing local fallback and mark provider-limit status `unknown`. Do not treat an absent reserve as zero, or turn a ceiling or estimate into evidence that the provider will accept the request.
4. For the chosen local `raw` value (including `C` when marked provider-limit `unknown`), `safe = floor(raw * 0.80)`, preserving the existing MidTurnCompact safety margin. Then `messageBudget = safe - E`. Compact against this message budget. If `W - O <= 0`, mandatory retained messages, final schemas, or framing still exceed it, or a term required for admission is unknown without a configured conservative bound, return a typed pre-dispatch error and make zero `Stream` calls.

The effective output cap/reserve is separate from `C`: `C` is never sent as generation `MaxTokens`. The 20% margin covers ordinary text tokenization/serialization estimation error only; it is not an image-size or provider multimodal bound. A known direct `InputTokenLimit` still uses the 20% margin and schema/framing deductions, but not an output-reserve deduction.

For images or other multimodal blocks, preserve an explicit `unknown` estimate if provider accounting, dimensions/detail, or model support cannot be established. A configured conservative per-item reserve may be used while keeping the provider-fit status unknown. Without such a bound, do not declare the request to fit. Do not retain the fixed 85-token image heuristic as a safe upper bound. Logs and traces may report estimated terms and their `estimated`/`unknown` state, never provider-reported usage. Do not emit a `fit=true` or equivalent verified-provider-fit signal: even a fully estimated request is not provider acceptance evidence, and a custom adapter/model/protocol with unrepresented request behavior remains unknown.

This reuses the current compaction fallback without inventing a hard provider guarantee: missing model-limit metadata may still use the local compaction ceiling, with an `unknown` status. By contrast, inability to identify the active candidate or estimate a required final schema/protocol-envelope term is not a fit result; stop before provider dispatch. Unknown values are never silently replaced with zero.

## TDD acceptance matrix

Use deterministic local provider fixtures and recording estimators. The decisive rejection case should exercise the real default Assembly/Loop request path, with a candidate `InputTokenLimit` and final filtered schemas/framing sized so messages alone fit but leave no budget for the full envelope (for example, `messageTokens <= safe` while `messageBudget <= 0`). Assert a typed pre-dispatch error, zero provider `Stream` calls, and unchanged breaker state. Add a neighboring case where compaction can reduce the retained request enough to fit, and allow dispatch only after re-estimating the compacted request under the same candidate and frozen options. Also add a positive-fit case through actual default `AssembleAgent` with the complete 39-tool registration, `Compaction.MaxTokens=8000` (`safe=6400`), and the active adapter's estimator: the request must be estimated and then accepted by the recording provider using the same final filtered schemas and effective output cap.

| Case | Required assertion |
|---|---|
| Prepared plan is consumed at every dispatch | Initial call, already-authorized transient retry/failover, and the one allowed overflow recovery each consume one newly prepared plan. Capture candidate handle/identity, `CandidateProposal` reason and antecedent, messages, schemas and frozen generation values at estimate and provider boundary; each pair is identical. A new proposal invalidates the prior plan, and one plan cannot authorize two physical `Stream` calls. |
| Candidate preparation and stale lease | Initial preparation performs no adapter `Build`, credential resolution, provider `Stream`, dispatch-permit grant, or mutating cycler/session-affinity advance. Pure peek pins the candidate metadata. A stale selection lease is rejected before provider dispatch, discarded and re-peeked/re-estimated; it grants no permit. A first-attempt stale outcome is breaker-neutral/no-dispatch. |
| Authorized transient fallback preflight | After a typed safe failure, the existing Core proposal for the fallback candidate is re-preflighted against that candidate's own metadata and frozen options. If it fits, exactly that proposal is consumed and dispatched once. If it does not fit or its estimate is unknown, no fallback request or permit is produced; the existing operation authority and shared attempt count remain authoritative. |
| Default 39-tool positive fit | Assemble the actual default CLI agent and its full 39-tool registry with `C=8000`, `safe=6400`, and a recording active-adapter estimator. Prove a fitting request is dispatched with the same canonical final schemas the estimator saw; this checks the positive path in real assembly, not a hand-built schema-only model. |
| Options materialized once | Include a counting custom `llm.Option` that sets ordinary finite `GenerationOptions` fields. Assert the closure is invoked exactly once after filtering; the estimator and captured provider body receive its frozen values (including effective `MaxTokens`) and exact filtered tool schemas. |
| Filtered options are the admitted options | A dynamic tool filter returns a smaller schema set; estimate receives those exact definitions and the provider fixture receives the same canonical definitions. No post-estimate filtering or rebuild occurs. |
| No-tools boundary | An empty final tools list costs zero schema tokens while protocol framing remains separately accounted for. |
| Limit precedence and ceiling | Positive `InputTokenLimit` wins over `ContextWindow`; direct input limit does not subtract output reserve; `C` caps either known limit; the 0.80 safety factor is applied once. |
| Context fallback and output cap | With no `InputTokenLimit`, derive from `ContextWindow - O`; prove per-call/model/provider/adapter cap precedence, clamp requested `MaxTokens` to known `MaxOutputTokens`, assert the same effective cap is estimated and sent, and preserve explicit zero as present. |
| Switch/cycler identity | Select or switch to a candidate with limits different from primary; assert its candidate ID, provider/model identity and its own `ModelSpec` remain paired through preflight and dispatch. An unknown selected candidate remains unknown and never borrows primary limits. |
| Missing model metadata | Use the configured compaction ceiling as the documented local fallback, assert the provider-limit result remains `unknown`, and assert no test or log claims guaranteed provider fit. |
| Estimator failure/cancellation | A schema/framing estimator error or pre-dispatch cancellation returns before `Stream`; no zero-token fallback or retry is manufactured. |
| Multimodal unknown | Unknown image accounting is visible as unknown; a configured conservative reserve can be used without changing that status; with no bound, preflight rejects before `Stream`. |
| Unrepresentable custom adapter/protocol | A custom adapter/model/protocol whose actual request behavior is not represented by the frozen request snapshot, or any required term without an estimator/conservative bound, remains unknown, never emits a fit-known trace/log state, and fails before `Stream`. A custom `llm.Option` that only sets finite `GenerationOptions` fields is covered by the one-time materialization case above and is not rejected as opaque. |

The durable current-submission identity/projection repair remains its own builder task and its acceptance cases must not be folded into this matrix. The summarized conversation, subagent and summary-model policy, continuation semantics, retry/breaker policy changes, and broad selector/resolver redesign are also outside this handoff. The request-plan candidate pin only makes preflight and dispatch refer to the same candidate proposal.

## Stop conditions and external decisions

Stop before provider dispatch if the active dispatch candidate cannot be pinned, a switch/cycle cannot supply matching metadata, a required final schema or enabled-protocol framing estimate errors or is unsupported, or a cancellation occurs during estimation/compaction. Return a typed reason and keep all unmeasured terms explicit; do not dispatch under an assumed capacity.

No external decision is needed to implement this bounded estimate/admission contract. PRD-04 cost-budget policy remains an external product decision and is not a context-window hard cap. Native provider/version enablement remains disabled pending the existing R0 wire-fixture and owner-approval gates. This handoff does not change either decision.
