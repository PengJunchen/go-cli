# R2 session RunCommitSink adapter handoff

Status: source-based design proposal only; this revision changes no product code. Source baseline is `7ed603e`, which includes the accepted atomic run binding (`c1edd4d`) and validated-session re-Sync before recovery authority (`0c01907`). The sink adapter is still unimplemented. Completion-proof persistence/validation and trusted remote-terminal evidence remain prerequisite schema work; no approval of those gaps is implied here.

## Construction and lifetime

Build one sink per run around the already prepared `session.PreparedSession` and one `*session.WorkspaceQuarantineIndex`. A candidate constructor is:

```go
func NewDurableRunCommitSink(
    prepared session.PreparedSession,
    index *session.WorkspaceQuarantineIndex,
    workspaceID string,
) (core.RunCommitSink, error)
```

The constructor calls `prepared.Snapshot()` once before the run's first `CommitInput`, validates the snapshot's physical session, active branch, active leaf, and `PublishedView`, then keeps the immutable run-start view/revision/source-ID mapping, durable rows, and cursors. It obtains `prepared.DurableWriter()` from that same handle. It never calls `PrepareResume` or opens a second session store. The snapshot is a defensive view of state; the prepared handle's lock and writer remain the authority.

Each sink method reads `core.RunCommitFromContext(ctx)` and `core.RunIDFromContext(ctx)`. It requires that the context names this sink, the same physical `SessionID` and canonical `WorkspaceID`, a valid non-empty `OwnerGeneration`, and the same `RunID` as the payload. `WithRunCommit` atomically carries sink and binding; the actual `runOwner` overwrites `OwnerGeneration` with its fresh generation before invoking the callback (`c1edd4d`). The CLI and sink do not invent it. A sink instance is run-scoped and serializes all writes. The prepared session stays open while its owner may still commit a resolution.

Workspace identity is derived and canonicalized by the CLI from the selected workspace root. A fresh workspace is explicitly initialized with `EnsureWorkspace` before any action could be dispatched; the sink does not silently bootstrap a missing index. For resume, session recovery uses the same index as its `RecoveryAuthority` while holding the session lock. The lock order stays session file then workspace index. Session append/sync completes before calling an index method, and the index never calls back into session storage.

For new entries, set `RecordVersion=1`, physical `SessionID`, current `BranchID`, and `ParentID` from the active leaf; chain entries within a batch through their immediate predecessor. Use non-nil pointers for valid zero `TranscriptIndex` and assistant ordinal values. Let `AppendAndSync` assign `Seq` and `PayloadDigest`; after success refresh the active branch/leaf and max sequence with `Snapshot()` on the same prepared handle. Do not update or expose the live tree/history before append and sync succeed.

The public `RunCommitSink` stays the seven-method error-only interface; do not add row IDs or status results to it. The adapter assigns opaque entry IDs before a first append, retains them across an in-process retry, and uses the canonical `SessionEntry` rows returned by `AppendAndSync`—including their physical `ID` and `Seq`—to build indexes only after sync succeeds. On reopen, rebuild the same indexes from `PreparedSession.Snapshot().DurableEntries` in physical append order; do not reopen the store or trust `PublishedView` as a complete journal.

Index full row identity, not a text approximation: `(SessionID, WorkspaceID, RunID, AssistantTranscriptOrdinal, ToolCallID, ActionBatchID, ActionID, OwnerGeneration, row kind/state)`. Empty `ActionBatchID`/`ActionID` is valid only for a proven unreserved occurrence; never synthesize either. Transcript rows additionally key by `(RunID, TranscriptIndex)`, and the terminal checkpoint by its stable `TerminalCheckpointID`. Every lookup must be unique and its full canonical payload must match. Empty, ambiguous, conflicting, or reordered matches fail closed before a resolution checkpoint is written. Never infer identity from message text, completion order, or `ToolCallID` alone.

## Method-to-record mapping

| Sink method | Session record(s) and durable order | Workspace-index behavior |
|---|---|---|
| `CommitInput` | Append one `Type=user` row with `RunID`, `InputKind`, `TranscriptIndex`, and the full `AgentMessage` payload (`Content`, blocks, and usage). Repeated identical text at a later index is a new input. | None. Return only after session append, flush, and sync; the core must not start a provider request before this succeeds. |
| `BeginIntentBatch` | Validate the assistant tool-call message and every intent/known-denial occurrence. Append the assistant `Type=assistant` row first, then approved `Type=tool, ActionState=intent` rows only. Do **not** append `KnownReceipts` here: a denial at a later transcript index must not jump ahead of an earlier dispatched call's receipt. The Loop seeds those denials into its same in-memory canonical receipt buffer and later submits them through `RecordReceipt` in order. The assistant row is written once per `(RunID, AssistantTranscriptOrdinal)` even when sequential mode reserves later calls in separate one-action batches. Intents store `ActionID`, `ActionBatchID`, owner generation, occurrence coordinates, lowercase-hex `ArgumentDigest`/`SchemaDigest`, `ToolIdentity.Snapshot()`, and a defensive `EffectSet.Values()` copy; never raw args or credentials. | Only after the complete session batch sync, build one `WorkspaceDispatchBatch` containing all reserved actions and call `BeginDispatchBatch`. `WorkspaceDispatchCommittedNow` permits the core to proceed to the same prepared invocation's final fence. `WorkspaceDispatchAlreadyExists` is an error to the caller and never a replay permit. If there are no reserved intents, write no empty dispatch marker; persist denial receipts later through `RecordReceipt` in canonical index order. |
| `RecordExecution` | Append a journal-only `Type=tool, ActionState=execution` observation row with the exact intent's full occurrence reference, `ActionID`, `DispatchState`, and optional `ExecutionIdentity`; include a completion proof only when its action-scoped signal is closed. It has no `TranscriptIndex`. While an assistant group is open, allow this row only for an exact occurrence in that same group, including an occurrence whose terminal receipt is already durable; require its exact earlier intent and full action reference. A late proof for another group waits until no group is open. A later completion proof gets a distinct proof-bearing row rather than mutating an already synced identity-only row. The shared durable-action analyzer described below validates these relations for append, recovery, and direct `SessionViewFromEntries` calls. Index each physical row returned by `AppendAndSync` by its row kind/state. These rows are evidence/readiness, never a resolution checkpoint. | None. |
| `RecordReceipt` | Append one terminal `Type=tool` row only at the run's next expected `TranscriptIndex`, with the complete tool `AgentMessage`, original `ToolCallID`/`ToolName`, `RunID`, assistant ordinal, `ReceiptOutcome`, `DispatchState`, and reserved `ActionID` when present. A pre-reservation denial has no `ActionID` and is `not_dispatched`. Preserve provider IDs unchanged; repeated IDs at later assistant ordinals remain distinct occurrences. The Loop/coordinator buffers parallel completions keyed by transcript index and calls this method in ascending canonical order; the adapter rejects an out-of-order call without writing. | None. A receipt never clears a marker. The Loop must sync the complete receipt group before the next provider request. Receipt success is not a quiescence proof. |
| `ResolveExecution` | Require the target occurrence's exact terminal receipt to be synced first. If no group is open, this is an ordinary journal-safe point. If a group is open, allow a resolution row only for an exact receipt-closed occurrence in that same assistant group; this narrow exception is required for sequential calls, where the next one-action dispatch marker is blocked until the previous marker is resolved. A ready proof for another group waits until no group is open. If `EvidenceRef` is empty, resolve exactly one matching durable evidence row using the full identity index above; if non-empty, require an exact match. Evidence must be a prior exact `not_dispatched` receipt for `never_dispatched`, a prior completion-bearing execution row for local quiescence, or a prior reconciliation checkpoint at a no-open-group safe point. The shared analyzer must reject future-row references, self-reference, duplicate/missing/ambiguous/conflicting evidence, and mismatched full action references before any write. While a group is open, this is the only checkpoint kind that may interleave; only matching execution metadata described above may appear as another journal row. Compaction, terminal, reconciliation, other checkpoint kinds, and unrelated transcript/journal rows remain forbidden. Current remote-terminal evidence is unsupported: do not treat a generic successful tool receipt as proof. Append the resolution checkpoint, read its real canonical `EntryID`/`Seq`, then call `ApplyDurableResolutions` with that checkpoint identity and the full `PendingActionRef`. | After session checkpoint sync, call `ApplyDurableResolutions` with the exact proof. On index failure return an error and leave the marker quarantined; reopen recovery retries only this same validated checkpoint, never the action. A no-marker no-op is allowed only for validated `never_dispatched` plus its matching durable receipt. |
| `CommitCompaction` | Validate the projection against the immutable run-start `PublishedView.Revision` and source IDs. Map its cursor to an exact `CompactedThroughEntryID`; reject stale revisions, invalid prefixes, unmappable boundaries, and cuts through an open assistant-call/receipt group. Append one `Type=compaction` row with the summary, source boundary, current active leaf parent, and run provenance. | None. Sync before the next provider request uses the projected history. Keep the original source entries. |
| `CommitTerminal` | Treat the final transcript slice position as its zero-based `TranscriptIndex`. In physical `Seq` order, existing transcript rows for this `RunID` must be an exact canonical prefix `0..k-1`, each payload field-equal to the matching terminal transcript entry. Append only the missing continuous suffix `k..N-1`; reject holes, later indexes before earlier ones, duplicates, or payload conflicts without writing. Verify projections match those already committed (or persist missing valid projections first), then append one `Type=checkpoint, CheckpointKind=run_terminal` row whose `ID` is the caller's stable `TerminalCheckpointID` and whose `RunOutcome` is exact. The suffix and terminal checkpoint are one `AppendAndSync` batch. | None. Return success only after final sync; any conflict or failure withholds the terminal/saved acknowledgment. |

## Transcript ordering and resolution ordering

Keep the public seven-method sink error-only. The Loop/run coordinator owns parallel result buffering; the session adapter owns durable order enforcement. The coordinator tracks the next per-run transcript index and a volatile `completedReceipts[index]` map. A result that completes out of order, including a known denial from `RunIntentBatch.KnownReceipts`, stays in this map and is not passed to the sink. Once the next index is available, the coordinator calls `RecordReceipt` serially and advances only after that method returns nil. The adapter independently requires exactly its next expected transcript index and returns an error without writing on a gap or reorder. This preserves the meaning of nil as “this receipt is synced”; it does not mean merely accepted into a memory queue. A failed append/sync poisons the prepared writer, so the coordinator stops and recovery reloads the visible durable prefix; it must not keep feeding higher indexes to a poisoned handle.

For a mixed parallel group such as `call[i0]=success`, `call[i1]=denied`, `call[i2]=success` where `i0 < i1 < i2`, `BeginIntentBatch` syncs the assistant and two approved intents but no receipts. Workers may finish in order `i2, i0, i1`; the coordinator buffers them and then commits receipts `i0, i1, i2`. A sequential call has no completion buffer, but the same next-index rule applies. If any receipt append/sync fails, stop before the next provider request, retain the unacknowledged IDs for recovery, and do not flush later indexes around the failed receipt. Reopen reconciles remaining occurrences from the exact session intent and global dispatch marker; it never replays work just to fill a transcript gap.

The current zero-open-group-only proposal deadlocks sequential multi-call messages and must not be implemented. `WorkspaceQuarantineIndex.BeginDispatchBatch` rejects every new batch while any unresolved marker exists (`internal/session/workspace_index.go`); it has no same-run exemption. The contract requires a sequential call's receipt and, where needed, its separate resolution before preparing the next one-action batch. But the current `validateToolCallJournalTail` permits only action rows whose key is still open and matching receipts; a receipt removes its call from `open`, and every checkpoint is otherwise rejected while a sibling call remains open (`internal/session/derive.go`). So after call 1's receipt, the current code rejects its late completion row or resolution checkpoint while call 2 remains unreceipted, and the index blocks call 2 until that resolution exists.

Make the exception row-specific, not a blanket checkpoint allowance. Extract/reuse one pure `analyzeDurableActionJournal` relation validator from recovery and call it from append validation, recovery, and `SessionViewFromEntries` before projection. It receives the selected root-to-leaf physical branch rows, preserves legacy-v0 handling, and validates version-one intent, execution, receipt, and resolution relationships from durable rows. During an open assistant group, permit a journal-only execution row only when its exact occurrence belongs to that current group and its matching intent/full action reference is physically earlier; the occurrence may already have its terminal receipt. Permit an `execution_resolution` checkpoint only when its exact current-group occurrence has an earlier terminal receipt and every typed evidence reference names one matching earlier row with the same full action reference and the required row kind/state. No validator may accept a future row, a reused/ambiguous evidence ID, a duplicate resolution, or a self-reference. Projection continues to omit execution rows and checkpoint rows, so these metadata entries do not move transcript messages or receipt indexes. All other checkpoint kinds and transcript/journal interleaving remain rejected while the group is open. Late evidence for another group is deferred until the active group closes; it does not justify an unrelated row inside this group's tail.

These two physical sequences make the sequential path explicit; `execution` rows and resolution checkpoints are metadata, not provider messages. Until call 2 also has a receipt, the prepared handle keeps the prior complete `PublishedView`; it does not expose the incomplete assistant group. Direct `SessionViewFromEntries` must validate the open group's journal relationships, then continue to withhold that incomplete view with `errUnclosedToolCallGroup`:

```text
# Completion proof was ready before call 1's receipt.
assistant(ordinal=7, calls=[call-1, call-2])
intent(call-1, batch-1)
execution(call-1, completion-proof=P1)
receipt(call-1, transcript-index=k)
execution_resolution(call-1, evidence_ref=execution-P1)
workspace-resolution(call-1)
intent(call-2, batch-2)       # now the index admits the next marker
...
```

```text
# Completion proof arrived after call 1's receipt.
assistant(ordinal=7, calls=[call-1, call-2])
intent(call-1, batch-1)
receipt(call-1, transcript-index=k)
execution(call-1, completion-proof=P1)  # exact late row in the same open group
execution_resolution(call-1, evidence_ref=execution-P1)
workspace-resolution(call-1)
intent(call-2, batch-2)       # no same-run marker exemption is needed
...
```

In both cases, the next action marker is attempted only after the prior session checkpoint and workspace resolution have succeeded. For a parallel group, receipt calls still arrive at the adapter in canonical `TranscriptIndex` order; a proof-bearing row or resolution checkpoint may be physically between two such receipts only after its own exact receipt is durable. Because these rows are not transcript messages, the restored provider history remains in receipt-index order. A pre-dispatch denial has no marker; its receipt still waits in the canonical buffer and is committed at its index.

Completion is a readiness event, not permission for a worker to write a checkpoint. The resource observer publishes `(full PendingActionRef, closed PreparedCompletionProof)` to the run owner's nonblocking `resolutionReady` queue; this is internal owner/coordinator state, not a new `RunCommitSink` method. A dispatch worker and cleanup path only register/enqueue readiness; they never wait for receipts or call `ResolveExecution` directly. If proof is ready before its receipt, the coordinator may append the exact proof-bearing execution row while that occurrence is open, then waits only for the normal receipt path; once that receipt is synced, it appends the resolution checkpoint and resolves the workspace marker. If proof arrives after the receipt, the coordinator appends a distinct proof-bearing execution row and resolution checkpoint for that receipt-closed occurrence in the same still-open assistant group. This lets sequential execution clear call 1 before it reserves call 2 without blocking a worker or weakening workspace-index admission. A ready proof for a different assistant group is retained until no group is open. The session analyzer and adapter both enforce these boundaries. A crash before readiness is durably recorded leaves the marker unresolved; recovery does not infer completion from an in-memory event.

Required order regressions include mixed denied+success receipts, reverse worker completion with restart reconstructing messages in canonical transcript order, and both completion-proof orderings shown above. Add a two-call sequential regression: after call 1's receipt/proof/resolution, its workspace marker is cleared and call 2's marker can be committed while the same assistant group remains open. `PrepareResume` succeeds at each durable boundary and retains the prior complete `PublishedView`; direct `SessionViewFromEntries` validates the journal references but withholds the incomplete group with `errUnclosedToolCallGroup`. Once call 2's receipt syncs, reopening publishes the assistant plus both tool receipts in canonical transcript order, with execution/resolution metadata absent from `Messages`. Direct `SessionViewFromEntries` must reject mismatched/duplicate/future evidence before projection and accept only exact current-group late metadata, without depending on `PrepareResume` having run first. A non-resolution checkpoint, unrelated transcript row, or other-group late proof inside the open tail remains rejected/deferred.

For compaction, the run-start snapshot must be captured before the initial user row is appended. If `TranscriptCount > 0`, `PriorHistoryCount` must equal the original view length and the boundary maps through the run's canonical transcript index map. If `TranscriptCount == 0`, the boundary maps through the original view's `SourceEntryIDs`. The adapter must not compare message text to find the current input or compare a projection against the view revision after this run's own writes.

## Acknowledgment and retry rules

`BeginIntentBatch` is the only adapter operation that reaches the global dispatch index. The sequence is always:

```text
session assistant row once: AppendAndSync
for each sequential action or parallel batch:
  session current intent row(s): AppendAndSync
  workspace BeginDispatchBatch: append + Sync
  core final prepared-invocation fence -> executor(s)
  Loop buffers concurrent results; session receipts sync in canonical index order
  after each synced receipt, for its action when valid evidence is ready:
    session execution proof row if needed, then resolution checkpoint: AppendAndSync
    workspace ApplyDurableResolutions: append + Sync
next sequential action marker / next provider request
```

The index marker is batch-level and may mean every reserved call could have started. If the index call errors after a possibly visible write, the adapter returns an error and the core does not dispatch. A retry that observes `AlreadyExists` also returns an error; recovery will classify the marker as possibly dispatched and will not replay. Calls rejected before reservation keep no `ActionID`; reserved calls fenced by the final prepared-invocation check keep their original `ActionID` in a durable `not_dispatched` receipt.

Session `AppendAndSync` errors poison the handle. Do not proceed to an index marker, executor, provider request, or durable acknowledgment after such an error. A receipt sync failure prevents the next provider call. A resolution index failure leaves the already-synced local resolution checkpoint available for exact recovery replay. Unknown remote outcomes and local transport completion do not clear the workspace marker. The completion-proof schema and validator are not yet present in this source baseline; generic success receipts also are not remote-stop evidence. Until trusted remote-terminal evidence has a typed durable representation and recovery validator, `ResolutionRemoteTerminal` is rejected and the marker stays quarantined. Only validated never-dispatched proof, locally joined resources, a future trusted typed remote-terminal fact, or explicit durable reconciliation may clear it.

## Test boundary and fault injection

Adapter tests belong in `internal/session/run_commit_test.go`; the adapter implementation belongs in `internal/session/run_commit.go`. Use a prepared test handle backed by the real durable JSONL store and a temporary `WorkspaceQuarantineIndex` with its existing per-instance write/sync hooks. Keep core/Loop/CLI production edits in their owning consumer lane.

Required adapter regressions:

- Bound context, session, workspace, run, and owner-generation mismatch fails before any session or index write; an absent sink/binding fails before provider entry in the later core integration test.
- Session intent sync failure results in zero index calls; marker success is ordered after session sync. `AlreadyExists` and index write/sync failure produce no dispatch permit and no executor call in the later core integration test.
- Receipt sync failure prevents another provider request. A visible marker after index sync error recovers as possible-dispatch/unknown, with zero action replay.
- Mixed denied+success and reverse parallel completion: the later-index denial is not written before an earlier success receipt; reopen rebuilds `SessionView.Messages` in canonical index order.
- Terminal commit with an existing hole, later index already present, duplicate index, or payload conflict fails before any append. A valid persisted prefix plus missing suffix appends only that suffix and the checkpoint in one sync.
- Evidence resolution fills an empty `EvidenceRef` from exactly one durable row and uses that row's actual returned `EntryID`/`Seq`; a supplied non-empty reference must match. Missing, ambiguous, conflict, wrong row kind/state, and self-reference all fail before the resolution write. Reopen reconstructs the same mapping from `Snapshot().DurableEntries`.
- Completion proof arrives before receipt and after receipt in a two-call sequential assistant group. Worker/cleanup paths only enqueue readiness; after the target receipt sync, exact execution/resolution metadata can be written while a sibling call remains open, allowing the next one-action marker only after workspace resolution. Assert no wait cycle, no unrelated/ordinary checkpoint in the open tail, and successful direct `SessionViewFromEntries` plus reopen validation.
- Reorder, duplicate, future-row, self-reference, wrong-kind, and wrong-action evidence cases fail in the shared durable-action analyzer; exact current-group receipt-closed execution/resolution metadata is accepted by both recovery and `SessionViewFromEntries`.
- Identity-only execution rows do not authorize local resolution; loader requires the approved closed completion proof. Ordinary `success` receipt plus `remote_terminal` resolution is rejected on reopen and leaves the marker unresolved. A trusted typed remote-terminal proof remains a future schema test, not a test this adapter may assume passes.
- Resolution session-sync failure produces zero index calls. If session resolution sync succeeds but index sync fails, the local checkpoint remains, quarantine remains, and reopening applies exactly that checkpoint once before view publication.
- Exact retries are idempotent; conflicting payload at the same transcript/action/terminal coordinate fails closed. Repeated `ToolCallID` at different assistant ordinals does not collide.
- Stale compaction revision, invalid source cursor, and a boundary splitting an assistant-call group write no bytes. Successful restore inserts one untrusted summary at the exact source boundary and retains the uncovered suffix.
- Terminal transcript mismatch, terminal writer/sync failure, or missing stable terminal checkpoint ID never acknowledges a saved run. Retrying the same `TerminalCheckpointID` and payload does not duplicate rows.
- Real cross-session index contention exercises the workspace lock; no test substitutes a process-kill/restart matrix for R2-REV-01.

## Blocking source gaps and ownership

1. `WithRunCommit`, `RunCommitFromContext`, binding validation, and run-owner generation injection are implemented at this baseline (`c1edd4d`). The `RunCommitSink` API remains error-only. Production Loop/Agent sink call sites and the CLI adapter binding remain consumer-lane work; do not reintroduce a second context binding API.
2. `PreparedCompletionProof` values are defined by the approved tools design, but the completion signal is not yet durable in `ActionExecution`/`SessionEntry` at this source baseline. Before local resolution, BLD-01 must add the closed proof field and make the loader require it. The current validator's identity-only acceptance is insufficient and must become fail-closed for historical resolution checkpoints that have identity but no completion proof. `ExecutionIdentity` remains optional diagnostic identity and never substitutes for positive completion evidence. Do not enable local `ResolveExecution` before that schema/validator handoff lands.
3. Remote terminal proof is also unsupported by the current durable schema. `RunToolReceipt` persists only generic outcome/dispatch/message data, while `validateExecutionResolutionEvidence` presently accepts a known dispatched receipt when its outcome is not `unknown`; that would let a generic `success` clear quarantine. The adapter must reject `ResolutionRemoteTerminal` until a separate reviewed typed protocol-terminal fact is persisted and validated on reopen. Do not invent that field or treat a normal success as remote stop proof in this handoff.
4. The complete-LF reopen Sync gap described in the original `bf073e8` source note is closed by `0c01907`: `PrepareResume` now re-Syncs the validated file before any `ApplyDurableResolutions`/`InspectDispatchMarkers` call or handle publication, and a Sync failure returns no handle. It is an integrated prerequisite, not adapter work; keep the permanent fail/reopen and authority-not-called regressions.
5. `RunIntentBatch` carries assistant ordinal but not assistant `TranscriptIndex`; `RunToolReceipt` carries its index and `RunTerminal.Transcript` uses vector position. The consumer assigns assistant indices from its per-run canonical transcript cursor and invokes sink methods in canonical order. Add a Loop integration regression; do not infer indexes from message text or provider call IDs.
6. Current `WorkspaceQuarantineIndex.BeginDispatchBatch` conservatively blocks all actions while an unresolved marker exists because it has no enforced-scope permit. Preserve that behavior until the reviewed R4 path-scope capability is wired through; this adapter must not trust the `EffectSet` DTO as a read authorization.

After the completion-proof validator and typed remote-terminal evidence contracts are independently closed, implement only the session adapter file/tests first. Core's prepared invocation, actual Loop result buffering/safe-point notifications, and CLI input/terminal acknowledgment remain consumer-lane responsibilities.
