# R4 path-scope independent review

**Reviewed snapshot:** `9f783d84f68d1398c59d73d72a946a5dfbc3e14b` (`fix(r4): scope default file tools to allowed paths`), based on `78b1bb3`.

**Decision:** The normal wiring and intended compatibility semantics are sound, but two `PathWhitelist` edge cases should be corrected before treating this slice as closed: an invalid scope can be mistaken for an absent scope, and the filesystem root does not contain its descendants under the current prefix check.

## Findings

### R4PATH-01 — Invalid nonempty whitelist can become unrestricted in file tools

**Priority:** P1, conditional on relative-root canonicalization failing. **Evidence:** source control-flow plus an internal sentinel probe; the host could not induce the constructor's `filepath.Abs` error directly.

`NewPathWhitelist` returns `PathWhitelist{invalid: true}` with an empty `paths` slice when `filepath.Abs` fails for a configured root (`internal/tools/bash_sandbox.go:95-104`). `PathWhitelist.IsAllowed` correctly rejects that value (`:110-120`), and Bash calls `IsAllowed` directly (`:363-365`). The file tools instead use `len(paths) == 0` as the “unrestricted / not configured” test: Read returns early at `internal/tools/read.go:216-223`, while Write, Edit, Grep, Find and Ls use the shared early return at `internal/tools/write.go:107-138` (called from `edit.go:123`, `grep.go:149`, `find.go:106` and `ls.go:95`).

The trigger is a nonempty relative `Sandbox.AllowedPaths` entry when resolving it with `filepath.Abs` fails, such as when the process cannot resolve its current working directory. In that state, an absolute file path bypasses the scope check in every affected file tool; the failure is therefore fail-open for the configured scope. A temporary package-local probe injected the exact invalid sentinel and confirmed that Read returned an outside-scope absolute file even though `PathWhitelist.IsAllowed` denied it. An attempt to induce the constructor error by removing the working directory was skipped on this Darwin host because `filepath.Abs` still returned a path; the production error branch is established by source, not claimed as host-reproduced.

**Suggested correction:** distinguish an explicitly unrestricted whitelist from an invalid whitelist instead of using `len(paths) == 0` alone. Let file-tool validation consult `invalid` (or a small `IsUnrestricted`/`IsConfigured` helper) and reject invalid scope before any file operation.

**Regression acceptance:** exercise an injected `Abs` failure for a configured relative root; Read/Grep/Find/Ls must reject an outside absolute target, Write/Edit must leave outside targets unchanged, Bash must continue to reject the scope, and nil/empty configuration must remain unrestricted for file tools. Keep the test seam narrow; no new sandbox framework is needed.

### R4PATH-02 — Filesystem-root whitelist rejects all descendants

**Priority:** P2. **Evidence:** direct runtime probe on the reviewed snapshot.

`PathWhitelist.IsAllowed` accepts exact equality, then checks `strings.HasPrefix(cleaned, base + separator)` (`internal/tools/bash_sandbox.go:122-128`). When `base` is `/`, the prefix becomes `//`, so `/tmp` and every other descendant are rejected. The analogous volume-root case applies to Windows drive roots such as `C:\`. A temporary probe confirmed `NewPathWhitelist([]string{"/"}).IsAllowed("/tmp") == false` on the reviewed host.

**Suggested correction:** make containment relative to the volume/root boundary, for example by handling volume roots explicitly or using a separator-aware relative-path check that handles them. Do not loosen sibling-prefix checks such as `/work` versus `/work-old`.

**Regression acceptance:** root `/` admits `/tmp` and nested paths on Unix; a Windows volume root admits a child path on Windows; ordinary roots still reject siblings sharing a textual prefix.

## Verified behavior and boundaries

- **Assembly propagation is complete for the six default file tools.** `assembleState.assembleTools` passes nonempty `Sandbox.AllowedPaths` to `WithRegisteredPathWhitelist` (`internal/cli/assemble.go:866-879`). `RegisterDefaults` wires the values into Read, Write, Edit, Grep, Find and Ls (`internal/tools/builtins.go:69-75,92-153`). Existing tests check all six registered tool instances and exercise Write/Edit through `RegisterDefaults` (`builtins_test.go:216-310`); the actual `AssembleAgent` scope test exercises Read/Grep/Find/Ls, including absolute escapes and parent-symlink escapes (`internal/cli/assemble_path_scope_test.go:14-84`).
- **Relative roots are anchored at construction time.** `NewPathWhitelist` cleans and makes each root absolute before resolving symlinks (`bash_sandbox.go:92-104`). Existing tests exercise relative roots for both `PathWhitelist` and Bash (`bash_sandbox_test.go:48-61,246-258`), and the assembly test creates its allowed directory as a relative path (`assemble_path_scope_test.go:14-16,34-42`). The roots are copied into a newly allocated canonical slice, so mutating the caller's slice after `RegisterDefaults` returns cannot change the registered tools' scope. `WithRegisteredPathWhitelist` temporarily captures the input slice until its option is applied, but registration applies it synchronously.
- **Read symlink behavior remains correctly scoped.** The whitelist checks the resolved target, including the final component, while `Execute` still applies `FollowSymlinks` (`read.go:214-234`). Tests cover following an in-scope final symlink, rejecting an out-of-scope target, and rejecting a parent-symlink escape (`read_test.go:172-227`). Write/Edit reject a final symlink and reject a parent symlink that resolves outside the whitelist; their positive and negative cases are covered in `write_test.go:300-397` and `edit_test.go:334-455`.

- **Nil and empty path lists preserve the intended legacy behavior.** Assembly only passes a file-tool scope when `AllowedPaths` is nonempty (`assemble.go:873-875`). Direct nil/empty registration does not add path options (`builtins.go:100-153`), matching `Read`'s empty-scope test (`read_test.go:267-282`) and the assembly-level unrestricted-read test (`assemble_path_scope_test.go:86-105`). Bash has different documented semantics: `WithAllowedPaths(nil)` uses the current directory, with `"."` as the `Getwd` fallback (`bash_sandbox.go:307-320`); the reviewed code keeps this path unchanged.
- **`WithNoSandbox` does not remove file-tool path wiring.** The option selects `AllowAllSandbox` only for Bash (`internal/cli/assemble.go:795-812`); the separate file-tool whitelist option is still applied when configured (`:866-879`). The assembly path-scope test deliberately combines `WithNoSandbox` with a nonempty whitelist and confirms that file tools reject outside paths (`assemble_path_scope_test.go:34-42,59-82`). `WithNoSandbox` does make Bash unrestricted, as its name and documentation state; `AllowedPaths` is not a filesystem sandbox for shell commands, custom tools, MCP tools, or every other possible file-access path.
- **This is path validation, not an OS isolation boundary.** `PathWhitelist` explicitly says checks are not atomic against concurrent symlink changes (`bash_sandbox.go:83-86`), and Read explicitly describes its check-then-use race (`read.go:225-229`). Write/Edit likewise validate with `Lstat` before later filesystem operations (`write.go:107-138,238-304`; `edit.go:123-187`). The `O_NOFOLLOW` wording in `write.go:113-120` should not be read as an atomic kernel guarantee: no `O_NOFOLLOW` flag is passed to the later open, and the check can race. Preserve the documented limitation and avoid describing this feature as a sandbox.

## Independent follow-up: fixed PathWhitelist edge cases

Re-reviewed fixed commit `944189db500e1f2f205892df09075daee559bf1e`, directly atop `9f783d84f68d1398c59d73d72a946a5dfbc3e14b`.

**Both findings above are closed in this follow-up; the PathWhitelist edge-case slice is accepted.** The new `unrestricted()` predicate distinguishes an explicitly empty/nil configuration from an invalid scope even when both have zero usable paths. The constructor returns an all-or-nothing invalid whitelist on path-resolution error, and both Read and the shared Write/Edit/Grep/Find/Ls path resolver use the predicate before allowing unrestricted access (`internal/tools/bash_sandbox.go:95-141`, `internal/tools/read.go:214-234`, `internal/tools/write.go:107-138`). This closes the fail-open path without changing the deliberate nil/empty compatibility behavior.

The constructor now uses an injectable private `absPath` function for deterministic error-path testing. The test injects failure resolving a configured relative root, then checks all six file tools reject an outside absolute target; Write creates no file and Edit leaves existing content unchanged (`internal/tools/path_whitelist_failclosed_test.go:16-92`). This verifies the error branch by injection; it does not claim that an actual process-wide `Getwd` failure was reproduced. Containment now uses `filepath.Rel` and `filepath.IsLocal`, which admits a path equal to or beneath the volume root while rejecting paths outside ordinary bases (`internal/tools/bash_sandbox.go:129-140`). A platform-root regression uses the host volume root and confirms an absolute descendant is allowed (`internal/tools/path_whitelist_failclosed_test.go:94-100`).

Independent fixed-snapshot evidence: `go test -list` confirmed all 12 selected tests were present. `rtk proxy env GOMAXPROCS=2 go test -race -p 2 ./internal/tools -run '^(TestPathWhitelistConstructorAbsFailureProducesInvalidEmptyScope|TestInvalidPathWhitelistRejectsEveryFileTool|TestPathWhitelistFilesystemRootAllowsAbsoluteChildren|TestPathWhitelist_AllowedPath|TestPathWhitelist_DisallowedPath|TestPathWhitelist_EmptyAllowsAll|TestPathWhitelist_InvalidScopeFailsClosed|TestPathWhitelist_ExactPathAllowed|TestPathWhitelist_RelativeRootMatchesAbsoluteAndRelativeCandidates|TestReadEmptyPathWhitelistPreservesUnrestrictedBehavior|TestPathWhitelist_SymlinkBypassBlocked|TestPathWhitelist_RealNestedSymlinkAllowed)$' -count=5` passed. Existing check-then-use symlink race limitations remain; this review does not treat path checks as an OS sandbox or claim whole-package validation.
