# R6 scoped-auth onboarding handoff

Read-only source audit at `b1d5cc92b0835fba5021f12ada0926e72cd9ba71`. Authority: the design-only approval for [`r6-entrypoint-design.md`](r6-entrypoint-design.md), reviewed at `dfa419d0f0631b8092e2d7d943329f797f3f8521`. No product code was changed for this handoff.

## Finding

There is no `login` command today. Bare `go-cli` dispatches to `interactive`; only `REPLSession.start` invokes `RunOnboarding` ([`cli.go`](../../../internal/cli/cli.go#L140), [`interactive.go`](../../../internal/cli/interactive.go#L48), [`repl_session.go`](../../../internal/cli/repl_session.go#L143)). `prompt` is a separate one-shot path and does not invoke onboarding ([`prompt.go`](../../../internal/cli/prompt.go#L56)).

On a first run with no config, onboarding collects a key into `cfg.Provider.APIKey`, writes YAML without the key, then calls `defaultSaveAPIKey`. That saver currently writes the legacy unscoped keychain account via `KeychainSource.Set`, or writes `{"api_key":"…"}` through `saveAuthFile` ([`onboarding.go`](../../../internal/cli/onboarding.go#L158), [`onboarding.go`](../../../internal/cli/onboarding.go#L364), [`onboarding.go`](../../../internal/cli/onboarding.go#L456), [`onboarding.go`](../../../internal/cli/onboarding.go#L512)). When a config already exists but has no `Provider.APIKey`, onboarding only prompts and updates the in-memory config; it returns without calling the saver.

R3 assembly correctly binds an inline config key to a `CredentialRef` using its model resolver. After restart, however, `AuthChain.ResolveCredential` only visits scoped sources: keychain `LookupScoped`/`GetScoped`, scoped auth-file `credentials` records, scoped environment, then scoped `models.json`. The unscoped keychain account and legacy `api_key` file are intentionally not candidates ([`assemble.go`](../../../internal/cli/assemble.go#L1509), [`auth_chain.go`](../../../internal/config/auth_chain.go#L135), [`auth_chain.go`](../../../internal/config/auth_chain.go#L282), [`keychain.go`](../../../internal/config/keychain.go#L79)). Thus first-run persistence is unusable by the production scoped resolver, and the existing-config path does not persist at all. A later interactive run also prompts based only on `cfg.Provider.APIKey`; it does not first check for an already stored scoped credential.

## Smallest implementation boundary

Pass the effective primary credential scope from `REPLSession.start` into the onboarding flow. Use `s.providerName` after `parseFlags`, and obtain the scope through the same `llm.ModelResolver.CredentialRefFor` path used by `newCLIModelResolver`; convert its canonical provider ID, protocol ID, and origin into `config.AuthScope`. Do not derive the origin from `Provider.Name` alone or add another URL normalizer. The resolver canonicalizes provider/protocol and reduces the configured endpoint to scheme, host, and effective port; endpoint paths are deliberately excluded. The default `eino` route therefore uses the resolver's OpenAI-compatible protocol and default OpenAI origin. In first-run onboarding, compute or recompute this scope only after the final provider selection/config mutation; never save against a scope cached before selection. Unsupported native Claude/Gemini providers or incomplete custom-provider endpoints must fail before storing a key; this slice adds neither native protocols nor OAuth.

Keep the current source order and scoped-reader contracts unchanged. Before prompting, resolve the exact scope through the existing `AuthChain`: a found credential skips onboarding, genuine not-found permits a prompt, and an invalid/insecure source error stops startup rather than prompting over it. This decision must use the resolver result for the selected current scope, not `cfg.Provider.APIKey != ""` alone. A configured inline key is eligible only when R3's provider identity binding puts it in that exact scope; for example, `provider.name: openai` plus `interactive --provider=eino` must not skip onboarding or reuse the OpenAI key, while a matching provider/scope key may skip. Thread the same final scope through both onboarding branches. The current `promptAPIKey` mutates `cfg.Provider.APIKey`, and `saveOnboardingConfig` then reads that field; change the input boundary to return/pass the newly entered secret separately and persist/bind it only to the exact resolved scope. Preserve any pre-existing inline config key unchanged. In particular, with an OpenAI config key and an `eino` provider override, the original key must remain bound only to OpenAI and the newly entered key only to the override's resolved scope. `serializeOnboardingYAML` must continue to omit secrets.

Preserve three distinct keychain lookup outcomes. If `KeychainSource.Available()` is false, treat that backend as disabled/unavailable and continue to the next source as today. Map only a positively classified absence of the exact scoped item to `ErrAuthNotFound`; do not treat every `security` command `ExitError` as a miss. Command execution failures, access denial, and unexpected or malformed output are source errors, so `AuthChain` must fail closed before the onboarding prompt. Use a narrow missing-item classifier/sentinel (or a proven typed OS error) and keep other failures distinguishable. Likewise, when the keychain is available but `SetScoped` fails, return a save error and do not report successful file fallback: an old exact-scope keychain item may still shadow the file record. File persistence remains the fallback when the keychain backend is unavailable. Any different fallback policy needs a reliable exact-item absence proof and a documented recovery path.

Change the saver boundary (`saveAPIKeyFunc`, `defaultSaveAPIKey`, `saveAuthFile`) to accept a `config.AuthScope` alongside the key. Use `KeychainSource.SetScoped` when the backend is available; write the exact tuple into an auth-file `credentials` array only when the keychain backend is unavailable. Preserve other valid scoped records, replace only the matching tuple, and do not infer a scope for old `api_key` or provider-only data. Reuse the accepted private-directory/file checks. Keep `KeychainSource.Set` and old-format readers available for legacy callers, but do not make them scoped fallbacks or change precedence. If scoped keychain persistence fails while an old value for that scope may still win ahead of the file source, report the save as failed rather than claiming rotation succeeded.

## No-HOME and automated startup

An empty/unavailable HOME makes the default auth and onboarding config paths unavailable. The scoped `authFilePath` and `modelsConfigPath` must return no default path; do not feed the legacy `configFilePath` project-relative fallback into scoped credential lookup. Preserve the scoped auth reader's behavior of disabling the default file source instead of searching project-relative `.config`. Test with a canary at CWD `.config/go-cli/auth.json` and prove no-HOME execution neither reads nor writes it. When onboarding cannot persist because there is no default path, fail clearly before claiming success; an available scoped keychain or an already valid explicit scoped source may still work. Do not migrate an unscoped legacy secret just because the current default provider is `eino`.

The startup bypasses are `GO_CLI_NO_ONBOARDING=1` and `interactive --no-onboarding`; `--no-onboarding` is parsed by the interactive command, not as a top-level global flag ([`onboarding.go`](../../../internal/cli/onboarding.go#L216), [`repl_session.go`](../../../internal/cli/repl_session.go#L170)). `prompt --output=json` never runs onboarding and is the machine-mode route for the HTTP check. Current JSON mode emits raw `AgentEvent` NDJSON; the approved R6 design's versioned `go-cli-output/1` format is still a broader R6 deliverable. This auth slice should keep wizard text and secret values out of machine stdout, errors, logs, and traces without changing that output protocol.

## Acceptance evidence

Unit tests should prove: the first-run and config-exists onboarding branches persist the key under the exact provider/protocol/origin tuple; the file is private; config YAML, stdout, stderr, logs, and traces omit the canary; an existing matching scoped key skips the prompt; provider/origin mismatch never reuses it; malformed or overbroad auth sources fail closed; legacy unscoped auth remains unmatched; and no-HOME never reads/writes a project-relative credential file. With `cfg.Provider.Name=openai`, an existing inline OpenAI key, and `interactive --provider=eino`, verify that the old key is still bound only to its original OpenAI scope and the newly entered key only to the override's resolved scope. Also cover first-run provider selection followed by scope recomputation before save. For keychain lookup, cover a positively classified exact-item miss falling through to the next source, plus fake `security find` access/operation failures and malformed output returning non-not-found errors before any prompt. For save, seed the fake keychain with an old exact-scope canary, make `add -U` fail while `find` continues returning the old item, and verify onboarding exits with an error, never claims setup is complete, and does not report the file fallback as successful. Keep existing source precedence unchanged.

The closure test should build and launch the absolute real CLI binary with isolated HOME, `XDG_CONFIG_HOME`, working directory, and trace/output directories plus a local OpenAI-compatible `httptest.Server`. On macOS, the real CLI will consider the keychain backend available, so put a temporary `security` shim as the only entry in the test process's PATH. Have it record arguments and maintain fake exact-scope state; assert all keychain reads/writes went through that shim and never touched the real OS Keychain or triggered OS authorization. This is a controlled external-command simulation, not OS-Keychain verification; do not add a product test-bypass environment variable. Include the access-failure and stale-item/write-failure cases above.

Seed a project `.go-cli.yaml` with `provider.name: openai`, the server's `base_url`, a model, and tracing disabled; this makes the first invocation take the existing-config onboarding branch without a registry refresh. Pipe one key to bare `go-cli`, verify the persisted scoped record's canonical origin, then start a second interactive process with EOF and verify it does not display the key wizard. In a third process run `go-cli prompt --output=json …`; the server must receive the canary only in `Authorization` at that configured origin, while stdout remains machine-readable and contains no onboarding text or secret. A second endpoint/provider fixture must not receive the first key. Also test an OpenAI inline config key with `interactive --provider=eino` to prove the wrong scope does not skip onboarding or reuse the key, the original key stays bound to OpenAI, and a newly entered key is bound only to the selected override scope; the matching OpenAI scope may use the original key. Keep this as an auth-focused journey; do not use it to claim the broader R6 protocol, trust, session, or output-version gates are complete.

## Compatibility and rollback risks

Existing users with only a legacy unscoped keychain item or `{"api_key":"…"}` will need to enter the key again (or provide another scoped source); automatic binding to `eino`/OpenAI would silently assign an unknown provider/protocol/origin and is out of scope. Keep legacy decoding for pre-existing files, but do not copy an old secret into a new scoped record. Once the user explicitly enters a new scoped key, replacing a legacy-only file with the scoped format is an intentional one-way update; a downgrade to old binaries may no longer read that file. A secret-write failure currently happens after YAML is written on first run, so the command must return an error and a later launch must prompt again rather than treat partial setup as complete. The CLI provider override must be included in scope derivation so a key cannot be saved against the config provider when the selected provider differs.
