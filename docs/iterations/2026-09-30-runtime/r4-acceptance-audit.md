In particular, the current tree has a real Assembly test which enumerates the fixed 39-tool registry, asserts each definition's registration source/effect/scope/schema, and checks the active Plan gate. This is **not R4 acceptance**. The manifest still marks EFFECT-01 and BLD-01/02 `in_progress`, and REV-01 `pending`. The fixed Assembly inventory also does not cover configured MCP, LSP, remote Bash, custom, skill, and extension registrations. `D-01` remains an unresolved product decision, and the manifest's `R3-REV-01` dependency remains pending.

Test names below are source evidence that a regression exists; this audit did not execute them. Parent-reported verification is separated in the final section.

## EFFECT-01 and prepared dispatch

Trusted identity is minted at registration, not read from model arguments or inferred from tool names. `TrustedToolIdentity` binds registration provenance, tool name, registration generation, an executor-instance fingerprint, and an opaque scope fingerprint; `TrustedEffectSet` defaults to `unknown`. Registration snapshots also freeze schema, description, prompt guidelines, streaming/top-tools capability flags, runtime path scope, completion proof, and the shared dispatch-fence snapshot. Prepared policy keys include identity and scope fingerprints, effects, schema and argument digests, registry/approval/Plan generations, permission mode, and policy/cache/store epochs.

With configured roots, `registerDefaultTool` takes only concrete Read/Ls/Grep/Find definitions through the private scoped reader seam. Empty or invalid whitelists stay `unknown` (Read/Ls may retain their existing completion proof, which is not read authority). Write/Edit receive `workspace_write`; Bash receives `unknown` even when the default process-group completion path can be proved; ordinary Git and extras stay `unknown`; only fixed control and reviewed concrete web readers receive their explicit effects. A custom definition that replaces a familiar name is ordinary provenance and cannot inherit the built-in effect.

`PrepareToolCall` resolves one registry snapshot, freezes and normalizes the call, validates any captured schema, preflights scoped read paths before policy, and returns a one-use invocation only after policy allows it. `Dispatch` checks the final shared registry/approval/Plan fence before setting `DispatchCommitted` and invoking the captured executor. Streaming and direct dispatch share the same consumed state. Write/Edit capture the executor and wrapper chain in preparation; the per-file queue receives the original context and prepared invocation, commits at dequeue, then invokes the captured stage without public name lookup or re-entering approval/normalization/queue.

Semantic test coverage already present includes:

- Identity, capability snapshots and same-name replacement: `TestProtectedProxyRejectsSameNameRegistrationReplacement`, `TestProtectedProxyRejectsUnrelatedRegistryGenerationChange`, `TestProtectedProxyUsesRegisteredDescriptorSnapshot`, `TestProtectedRegistryGetListAndTopToolsPreserveCapabilities`, and `TestProtectedStreamingToolDispatchesThroughPreparedPermit` in `internal/tools/prepared_registry_test.go`; `TestTrustedScopedWorkspaceReadRejectsSameNameCustomDefinition` and `TestScopedReaderReplacementChangesScopeAndStalesPriorInvocation` in `internal/tools/trusted_scoped_read_test.go`.
- Schema/path preflight and frozen arguments: `TestPrepareToolCallNormalizesValidatesAndFreezesCapturedArguments`, `TestPreparedWorkspaceReadPreflightUsesFrozenCallSnapshot`, and `TestPrepareToolCallRejectsInvalidSchemaBeforePolicy` in `internal/tools/prepared_registry_test.go`; `TestAssemblePreparedWorkspaceReadsValidatePathsBeforePolicy` in `internal/cli/assemble_path_scope_test.go`.
- Registry/mode/Plan changes during and after approval: `TestPreparedPermitStalesOnModePlanAndRegistryChange`, `TestPreparedWritersDuringApprovalWaitInvalidatePermit`, `TestPreparedApprovalUserDenyInvalidatesSiblingPermit`, `TestPreparedApprovalPolicyReplacementDoesNotReusePriorGrant`, and `TestPreparedStoreGrantRejectsSnapshotRevokedBeforePersistence` in `internal/approval`.
- Parallel positive grants without invalidating each other: `TestPreparedParallelAlwaysAllowGrantsBothDispatch`, `TestPreparedPositiveGrantsDoNotInvalidateSiblingSnapshots`, and `TestApprovalCacheParallelPositiveGrantsShareSnapshot`.
- Direct/streaming one-use and queued mutation fences: `TestPreparedStreamingBashDispatchAndDispatchStreamingShareAdmission`, `TestPreparedMutationUsesCapturedExecutorAndConsumesOnce`, `TestPreparedMutationDequeueRejectsStaleRegistration`, and `TestPreparedMutationCanceledAtDequeueCannotCommitLater`.
- Context propagation: `TestMutationQueuePassesContextToHandler` plus the prepared queue cancellation regression above. Assembly's `TestAssemblePreparedApprovalRunsWriteAndEditThroughMutationQueue` confirms actual Write/Edit use the queue.

One source-versus-verification boundary remains for the trusted search readers. Find/fd passes `--` before pattern and root. `TestGrepSeparatesPatternAndIgnoresRipgrepConfig` / `TestGrepRipgrepArgvAndEnvironment` and `TestFindFDArgvKeepsDashPatternsAfterOptionSeparator` / `TestFindAvailableFDDoesNotExecuteDashPattern` exercise those executor/helper boundaries. ## BLD-01: approval and Plan policy

`PreparedPolicy` checks the exact identity and fence, validates permission mode, checks Plan before ordinary classifiers/caches (including AutoFull), allows only a single scoped built-in `workspace_read`, the reviewed network-read pair, or the explicit trusted-control names, and rejects unknown/composite effects in Plan. Outside Plan, an untrusted classifier `Allow` for an effect that has no reviewed trust path is converted to `Ask`; a missing/invalid classification and invalid mode fail closed. Approval grants are published against the exact fence tuple. An explicit callback denial advances the approval generation and invalidates sibling permits.

The fixed Assembly now has real prepared approval-mode coverage, not only isolated policy tests. `TestAssemblePreparedWriteApprovalModesKeepDecisionAtAssemblyBoundary` checks headless Ask denial, explicit Auto dispatch, explicit Deny, and Plan blocking even with Auto. `TestAssembleTUIApprovalChannelControlsPreparedWriteDispatch` covers TUI-channel Allow and Deny. These exercise the Assembly's protected write registry and prove denied outcomes leave the marker file absent. Unit tests separately cover AutoFull, classifier denial, parallel AlwaysAllow, stale policy replacement, callback argument mutation, and audit decisions. The task's planned names are absent in several cases, but the semantic behaviors have related tests.

Remaining BLD-01 gaps:

1. `D-01` is still explicitly unresolved in `r4-policy-design.md`. Current code does not register `enter_plan_mode`/`exit_plan_mode` in real Assembly; `/plan` remains user-controlled. Preserve this boundary and do not turn a unit-level Plan tool fixture or an allowlist name into a product decision.
2. ## BLD-02: schemas, paths, bounded capture, provider behavior

**Schemas.** All seven default tools (`read`, `bash`, `write`, `edit`, `grep`, `find`, `ls`) expose closed object schemas. All 17 Git tools also implement `Parameterized`. Fixed Assembly's 39-row test requires every current entry to implement `Parameterized`, derives schema-valid sample args, and prepares each through the exact Assembly registry. The default schema tests (`TestRegisteredDefaultToolsExposeAccurateParameterSchemas`, `TestDefaultToolPreparedProxyValidCallsAndOptionalDefaults`, `TestDefaultToolPreparedProxyRejectsInvalidArgumentsBeforePolicyOrDispatch`) cover field/enum/default boundaries and prove malformed calls stop before policy/dispatch. The extra schema tests cover required fields, type/enum/unknown keys and executor behavior; `TestAssembleAgentExtraToolSchemasReachLoopModel` checks protected proxies → Loop → OpenAI-compatible HTTP tool serialization. `TestExtraToolSchemaMixedProviderDecodersReachPreparedExecutor` covers OpenAI-compatible and native Claude *inbound* tool argument decoding.

`todo_write` action-dependent checks remain in its executor because the prepared schema validator does not implement conditional schema keywords. Blank required strings likewise pass presence/type validation and then fail in the concrete executor; this is the reviewed prepared/model boundary documented in `r4-extra-tool-schemas-handoff.md`, not a schema claim of non-blank validation. `image_read` is not registered by Assembly. Plan mode tool definitions expose schemas and have unit execution coverage, but are not model-visible in the actual Assembly as noted above.

Dynamic definitions remain a reviewer-led inventory item: configured MCP may lack an input schema; LSP, remote Bash, custom commands and extensions depend on configuration or supplied definitions; skills are prompt/control adapters rather than normal parameterized executors. Ordinary custom/MCP/extension registration still resolves to `unknown`; a final ledger needs explicit “not configured/unavailable” rows or representative configured fixtures rather than silently treating absence as passing coverage. The extra-schema review also records the native Anthropic **outgoing** request/history/non-streaming tool-use gap as a separate R3 provider-contract P1: the mixed-provider test is inbound decoding and the Assembly serialization fixture is OpenAI-compatible only.

**Paths.** Real Assembly passes configured `Sandbox.AllowedPaths` to `RegisterDefaults`; constructors/resolvers apply it to Read/Write/Edit/Grep/Find/Ls. `TestAssembleAgentConfiguredPathsConstrainDefaultFileTools` covers allowed paths plus outside absolute paths and parent-symlink escapes for Read/Grep/Find/Ls, including under `WithNoSandbox`. `TestAssemblePreparedWorkspaceReadsValidatePathsBeforePolicy` proves path rejection occurs before a policy callback for the four read tools. Tool-level Write/Edit whitelist tests cover outside paths, directory-symlink escape and symlink targets; Grep/Find/Ls path-security tests cover their respective traversals. `TestAssembleAgentEmptyAllowedPathsLeavesReadUnrestricted` preserves the deliberate empty-list compatibility behavior.

This is an application-level file-tool boundary, not an OS sandbox. It does not confine Bash; `WithNoSandbox` affects Bash while a separately configured path allowlist still applies to file tools. Existing filesystem validation retains a documented check/use race against concurrent symlink changes.

**Bounded capture and cancellation.** The old source-contract claim of unbounded Read/Ls/Find directory capture no longer matches current source. `directory_capture.go` caps directory retention at 1,000 entries, rendered output at 1 MiB and one entry/path at 4 KiB; Read/Ls use batched `ReadDir(128)`, Find's Go DFS uses `ReadDir(1)` and bounded lexical top-K, and external Find streams NUL-framed records into a bounded collector while continuing to drain/join. Tests include `TestReadDirectoryReturnsSortedPrefixWithinEntryLimit`, Ls sorting/truncation cases, `TestFindGoReturnsGloballySortedTopKAndReportsTruncation`, helper NUL/path-normalization cases, `TestFindCaptureLimitDrainsHelperAndStopsFallback`, and `TestScanDirectoryBatchesDoesNotSwallowCancellationDuringRead`. Current Read/Ls/Find display quoting preserves unusual names.

Grep also has bounded match/frame/output capture and cancellation regressions: `TestGrepMatchCaptureWholeRecordBudgets`, `TestGrepPureGoMidWalkCancellationDoesNotReturnPartialSuccess`, `TestGrepRipgrepSaturationDrainsAndKeepsWholePrefix`, and `TestGrepRipgrepMalformedProtocolDoesNotFallBack`. The managed helper tests verify join/cancellation behavior. `TestRemoteBashMetadataRemainsBounded` covers bounded returned metadata. Assembly's unconfigured search provider does not register `web_search`; `TestWebSearchMissingProviderFailsClosed` checks the executor error, while `TestAssembleAgent_UnconfiguredWebSearchIsHiddenFromCapabilitySurfaces` checks it is absent from actual capability surfaces. These provide semantic equivalents to the planned BLD-02 tests despite different exact names.

**Find path parity.** The integrated Find fix preserves the pure-Go directory output shape for dot, absolute, nested relative, and nested absolute search roots, excludes the directory root, and preserves a file-root result spelling. `TestFindSystemFindNormalizesDirectoryPathsToSearchRoot` uses the real POSIX system `find`; `TestFindFDNormalizesDirectoryPathsToSearchRoot` runs the installed `fd` only when available; `TestFindFDShimNormalizesDirectoryPathsToSearchRoot` deterministically covers all four roots; `TestFindSystemFindExcludesDirectoryRootAndFileRootIsIncluded` checks directory/file-root behavior. Helper capture uses NUL framing, normalizes at the streaming boundary, and rejects paths outside the search root. On Windows the POSIX helper tests skip; the pure-Go path and platform-neutral capture tests remain relevant. Test source exists; this audit did not run it at `bb2`.

## Bounded designer handoff: SubAgent policy inheritance through real Assembly

**Priority:** P1 acceptance gap (verification). The audited source routes the real SubAgent factory through `s.tr`, which becomes the shared protected Assembly registry. The tests prove registry isolation and that the top-level `dispatch_subagent` is unknown/Plan-blocked; they do not prove the actual child model's nested calls hit that same prepared approval policy. No source defect was established by this audit.

**Design task:** define one deterministic `internal/cli` integration fixture using `AssembleAgent`, a scripted parent/child model, a configured write target and a recording approval channel/classifier. The parent invokes `dispatch_subagent`; the child model then requests a scoped `write` through the supplied tools. Keep the fixture local and assert the exact prepared-policy request identity/effect at both boundaries. Specify whether parent SubAgent approval and child tool approval are two separate decisions (the current design implies yes); no child may inherit an implicit side-effect grant merely because `dispatch_subagent` was approved.

**Acceptance cases:**

1. In Ask/TUI mode, deny the parent SubAgent request and assert no child model/tool starts. Allow the SubAgent request, then deny the child's Write request and assert the file is absent. Approve both separately and assert the exact queued child Write executes once.
2. Exercise a Plan transition after SubAgent admission but before the child's mutation is prepared; the child mutation must observe the shared Plan generation, fail before executor/queue commit, and leave the file absent. If the transition cannot be synchronized without a test-only hook, use a barrier in the approval callback rather than timing/sleep.
3. Replace a child registry entry while the child is waiting for approval and assert the stale child permit fails at the shared fence; the replacement must not execute under the old approval.
4. Keep the existing effect inventory invariant: `dispatch_subagent` remains `unknown`, receives no workspace scope, and is blocked when Plan is already active. Do not change effect classification or expose a new Plan transition tool to make the test pass.

**Out of scope:** changing D-01, relaxing Plan policy, treating SubAgent approval as blanket child authority, broad subagent lifecycle redesign, or adding persistent cross-run capability identifiers. The design deliverable is the exact fixture/acceptance contract; implementation and reviewer acceptance remain separate steps.
