# R2 local-quiescence proof handoff

Status: source-based design finding; no product changes. Reviewed recovery validator `b18e78bf7c0c231d487d7b0085fc419538806611` and the R1/tool lifecycle APIs in `98a4cafb04564e7201fe57b454bea379855aa87f`.

## Finding

`session.validateExecutionResolutionEvidence` accepts `ResolutionLocalResourcesStopped` only when its referenced `ActionStateExecution` row has `ExecutionIdentity` (`internal/session/durable_recovery.go:498-518`). That excludes a legitimate trusted synchronous executor with no asynchronous resource. It also treats identity as the gate even though `core.ExecutionIdentity.Validate` checks only process-group/job identity shape and explicitly does not prove that the resource stopped (`internal/core/execution_identity.go:19-67`). Keep identity validation for rows that carry one, but do not use identity presence as quiescence evidence.

R1 provides useful in-process lifecycle signals, but not a per-action durable proof. `tools.PendingExecutionError` promises that `ExecutionDone` closes only after a resource is positively stopped and joined (`internal/tools/pending_execution.go:3-15`); `core.executeSingleToolRegistered` registers that channel with the owner on error (`internal/core/parallel_tools.go:152-188`), and `runOwner` holds the run claim until callback/transcript/workers/resources finish (`internal/core/run_owner.go:88-107,407-409`). The owner counts live workers/resources; it does not export which prepared action completed which resource set. A callback return or absence of `PendingExecutionError` is not enough for global resolution.

The local process path has stronger private evidence: `managedLocalCommand.collect` waits for the leader and output readers and records whether the owned process group is gone (`internal/tools/process_scope.go:90-162`); on delayed cleanup, `observeProcessCompletion` closes only after the leader/readers join and the group is positively absent (`:267-289`). Bash uses this lifecycle but returns ordinary success after it (`internal/tools/bash.go:230-292`); neither the process proof nor a structured `ExecutionIdentity` currently reaches the core sink. Remote Bash deliberately distinguishes local transport completion from remote command completion and keeps uncertain remote execution pending (`internal/tools/remote_bash.go:178-233`). That boundary must remain: stopping an SSH/HTTP client is not remote terminal evidence.

Write/Edit are synchronous when invoked directly: `WriteTool.Execute` and `EditFileTool.Execute` perform their filesystem operation inline (`internal/tools/write.go:200+`, `internal/tools/edit.go:80+`). The configured mutation-queue path is different. `WithMutationQueue` enqueues a per-file job and waits for either its result or `ctx.Done()` (`internal/tools/middleware.go:71-130`); `DefaultFileMutationQueue.startWorker` may still be applying that job after the caller returns on cancellation (`internal/tools/mutation.go:240-254,257-279`). Its current result channel is per job, but it is not surfaced as a lifecycle receipt to R1. Therefore direct Write/Edit may use an explicit prepared synchronous-completion contract; queued Write/Edit must use the exact job-completion channel and stay pending if the caller stops waiting first.

## Minimal proof and validation change

Keep `ExecutionResolutionEvidence` and its `local_resources_quiescent` value. Add one small action-scoped, closed completion enum to `core.ActionExecution` and its durable `session.SessionEntry` execution row. The only proposed values are:

- `inline_pipeline_joined`: the exact final prepared executor pipeline has returned and its installed stages guarantee they leave no detached work.
- `queued_job_joined`: the exact accepted queue job has completed and its handler returned. `ctx.Done()` does not close this proof; the job remains pending until the queued effect stops.
- `owned_process_group_joined`: the owned process group is positively absent after its leader and output readers have joined.

These values describe one action's completion path. Do not add a generic resource list or infer proof from `EffectSet`, a tool name, a normal return, a context error, or `ExecutionIdentity`. Keep `ExecutionIdentity` shape validation for rows that carry it, but it is supplementary metadata and never establishes quiescence. An unknown wrapper or executor with no positive completion signal emits no proof and stays unresolved.

The sealed `tools.PreparedInvocation` is the narrow place to expose this proof because it captures the exact final executor and dispatch fence (`internal/tools/prepared.go:548-560,596-632`). Its completion signal/proof must be produced by that captured final pipeline or queue, and is available only after the corresponding join. For direct Write/Edit the inline proof is valid only if the full prepared chain guarantees synchronous completion. If `WithMutationQueue` accepts the operation, the proof instead comes from that exact job's completion channel; a caller that stops waiting on `ctx.Done()` must still retain/register the job completion. The queue worker may be long-lived, but the per-job signal closes only after its handler returns (`internal/tools/mutation.go:240-254`). Bash/StreamingBash use the owned-process-group proof only after existing leader, reader, and group checks succeed. Remote Bash never turns local transport completion into remote-terminal evidence.

Core must prepare exactly once and dispatch that exact invocation throughout the durable path. In `executeSingleToolRegistered`, durable mode calls `tools.ToolCallPreparer.PrepareToolCall` once, persists the snapshot/intent associated with that invocation, then dispatches the returned invocation. It must not call `Get`, receive a protected proxy, and then prepare again through the proxy's `Execute`; that would create a second invocation and split the recorded identity/fence from the executed one. Streaming follows the same rule: prepare once and call `DispatchStreaming` on the streaming-capable result from that preparation. The same prepared invocation must flow through sequential and parallel execution. If durable mode cannot obtain a `ToolCallPreparer` result, it fails closed before dispatch. This depends on the R4 prepared registry exposing the final executor/queue completion signal; an unknown wrapper cannot be upgraded to trusted by name or by adding a receipt in Core.

Before releasing a dispatch worker, Core registers that same action's trusted, non-nil positive-completion channel with the same `runOwner` for ordinary and streaming dispatch, including an accepted queued job whose caller returns early on cancellation; the owner retains the resource registration until the channel closes, and absent a trusted channel/proof it neither infers quiescence nor releases workspace isolation (nil never means an already-closed channel).

`ActionExecution` and the durable execution row need only the closed `CompletionProof` value (plus the optional existing `ExecutionIdentity`). Keep the resolution checkpoint's `EvidenceRef` pointing to that exact row. `session.validateExecutionResolutionEvidence` should require a matching complete action occurrence and intent, a dispatched action, an execution row after the intent and before resolution, and one recognized action-scoped completion value. A row with identity but no completion value fails; a valid inline proof does not require process identity. The resolution validator checks the linked locally committed fact and identity shape, not process identity as a stopped signal. Unknown/config-controlled executors, untracked helper-capable callbacks, MCP/remote lost-response outcomes, and subagent work without its own durable lifecycle remain quarantined. A known local resource may later be proved stopped while its receipt remains `unknown`; resolution never rewrites the receipt or replays the action.

## Bound run identity for the next consumer

The current core seam has `WithRunCommitSink`/`RunCommitSinkFromContext`, but its private context value carries only the sink (`internal/core/run_commit.go:30-57`). `ActionIntent` needs physical `SessionID`, `WorkspaceID`, `RunID`, `OwnerGeneration`, `ActionBatchID`, and `ActionID` (`:96-111`). `RunIDFromContext` supplies the owner claim ID (`:11-26`, injected by the actual `runOwner` at `internal/core/run_owner.go:256`). `PreparedSession.View()` exposes physical `SessionID` and branch/revision, but no workspace (`internal/session/durable_contract.go:18-25`); the session preparer generates its physical ID in `PrepareNew` (`internal/session/durable_jsonl.go:63-109`). No production call sites for `BeginIntentBatch` or ID generators for action/batch IDs exist yet.

Replace the separate sink-only and binding contexts with one private context value and one atomic binding API:

```go
type RunCommitBinding struct {
    SessionID       string // physical ID from PreparedSession.View()
    WorkspaceID     string // versioned digest of the successfully canonicalized selected root
    OwnerGeneration string // generated by the actual runOwner, never caller-supplied or a PID
}

func WithRunCommit(context.Context, RunCommitSink, RunCommitBinding) context.Context
func RunCommitFromContext(context.Context) (RunCommitSink, RunCommitBinding, bool)
```

The physical session ID comes from the successfully prepared session. `EnsureWorkspace(ctx, workspaceID)` validates/initializes the supplied ID; it does not return a canonical ID. Derive that ID from the explicitly selected workspace root: resolve `filepath.Abs`, `filepath.Clean`, and `filepath.EvalSymlinks` successfully, then hash a versioned, domain-separated representation of the resolved root (for example, `workspace-v1-` plus lowercase SHA-256 hex over `go-cli-workspace-id:v1\x00` and the canonical root). Any canonicalization failure is an error; never fall back to `"."` or infer a workspace from a label. Call `EnsureWorkspace` with that ID and retain the same value for the binding.

The runtime passes the prepared sink plus physical session/workspace descriptor into the run owner. The actual `runOwner` generates a fresh `OwnerGeneration` and injects it with the claim ID before invoking the callback; the CLI caller must not guess or supply it. At that point one atomic context binding carries the sink and its complete identity together. Legacy `WithRunCommitSink` must replace this whole private context value with a sink-only unbound value, explicitly clearing any inherited binding. A child must similarly start with its own prepared session, workspace binding, and sink; it may not inherit a mismatched parent sink or binding. `RunCommitFromContext` provides sink plus binding for `ActionIntent`; `RunIDFromContext` continues to provide the per-run claim ID. Core generates one `ActionBatchID` per assistant dispatch group and one `ActionID` per reserved invocation, retaining those exact IDs and payloads across append/sync retry. Do not derive identity from a display label, raw cwd, tool name, or an unbound sink. Durable mode fails before provider/tool dispatch when any binding component is absent or inconsistent. Keep the approved `RunCommitSink` interface unchanged. Narrow tests should prove missing binding blocks `CommitInput`/provider entry, retries reuse generated IDs, and separate calls/runs do not collide.

## Minimum implementation dependency order

1. **Tools/R4 prepared path:** expose one action's trusted completion enum/signal from the final prepared invocation. Direct inline tools join the full pipeline; queued mutations join their exact accepted job; local process tools join their owned group and readers. Preserve the same prepared invocation for normal and streaming dispatch. Wrappers that cannot prove completion return no proof.
2. **Core/run owner:** have the actual `runOwner` create/inject `OwnerGeneration` beside the claim ID. In the durable sequential/parallel execution seam, call `ToolCallPreparer.PrepareToolCall` once, bind its snapshot and IDs to the action intent, then dispatch that returned normal/streaming invocation without `Get`-proxy re-preparation. Add the sink and physical session/workspace binding atomically; keep dispatch receipts and unknown outcomes attached to that action.
3. **Session/storage:** persist the closed completion enum on the exact execution row and validate its linkage to the full `PendingActionRef`, intent, dispatch, and resolution. Keep `ExecutionIdentity` validation but do not treat it as stopped proof. `EnsureWorkspace` accepts the already-derived workspace ID and must not silently manufacture one.
4. **CLI session preparation:** prepare the new/resumed physical session, resolve the explicitly selected root and derive its versioned stable workspace ID, ensure that workspace, and pass the resulting session/workspace descriptor with the sink into the run owner. The owner creates one complete callback context binding after it generates its own generation. Missing preparation or canonical identity fails before provider entry.

## Child run boundary

`SubagentTool` delegates through `subagentDispatcherAdapter.Dispatch` (`internal/core/subagent_tool.go:345-379`); `realSubAgentRunner.Run` creates a fresh agent/harness but calls `h.Submit(ctx, prompt)` with the parent context (`internal/core/real_subagent_runner.go:114-129`). The current run-ID owner overwrites the child run ID, but `RunCommitSink` remains inherited unless explicitly replaced. Reusing the parent sink would write child input/tool receipts into the parent's open action group; dropping it would silently allow non-durable child mutations. Durable subagent execution therefore needs a child-session factory that prepares an independent physical session/branch, fresh run identity and owner generation, and an atomically child-bound sink/context, while reusing the same workspace index and canonical `WorkspaceID`. The child binding must replace both parent sink and parent binding; it may not inherit a mismatched parent value.

The parent `dispatch_subagent` marker cannot itself reserve the same workspace as a mutation while the child must reserve that workspace; doing so can block the nested child behind its waiting parent. A context-level sink mask or event-stream mask must never bypass an existing unresolved workspace-index marker. Only after R4 proves the exact first-party orchestration registration is pure scheduling, and the child has an independent prepared session/sink on the same workspace index, may a separately reviewed typed delegation fact avoid creating a competing parent mutation marker; all actual workspace effects remain child-owned markers. That proposal is not approved for implementation by this handoff. Until the child sink/lifecycle closure and marker semantics are reviewed, durable mode must reject delegation before launch. Plan Mode and untrusted same-name/custom subagent tools remain denied; no name-based quarantine bypass is acceptable.
