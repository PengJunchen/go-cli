# R4 remaining model-visible built-in schemas handoff

Source snapshot: `575fc5f746f702256a9b5d46150b955951a71066` on `codex/runtime-stabilization`. The default-schema change `fa7c969` is an ancestor of this snapshot. This is a source-grounded design handoff only; it does not claim implementation or acceptance.

## Scope and assembly census

`AssembleAgent` builds the real production registry in this order: default tools, extensions, prepared approval/resilience wrappers, SubAgent, extra first-party tools, then the LoopAgent (`internal/cli/assemble.go:336-376`). `assembleTools` registers the seven default file/shell tools and 17 Git tools, then configured custom, MCP, LSP, remote Bash, and skill tools (`internal/cli/assemble.go:832-966`; `internal/tools/builtins.go:82-184`). All seven default tools expose schemas at this snapshot: Read, Bash, Grep, Find, and Ls were added in `fa7c969`; Write and Edit already had them. Their field matrix and validation findings are recorded in [the accepted default schema review](reviews/r4-default-tool-schemas-review.md). The 17 Git tools also implement `Parameterized`; `git_pr_create` is registered from `assembleExtraTools` and already has a schema.

The fixed extra set is 16 concrete definitions: six ordinary registrations (`todo_write`, `task_create`, `task_update`, `goal_create`, `goal_update`, `git_pr_create`), eight trusted controls (`task_get`, `task_list`, `goal_list`, `goal_get`, `ask_user`, `enter_plan_mode`, `exit_plan_mode`, `tool_search`), and two trusted network reads (`web_fetch`, `web_search`) (`internal/cli/assemble.go:1323-1389`). Only `git_pr_create` currently implements `tools.Parameterized`; the other 15 do not. Their executor contracts are inventoried below. Configured custom/MCP/LSP/remote/skill and extension registrations are conditional or externally defined, so they are not substitutes for schemas on these fixed shipped tools and are outside this bounded gap.

## Current executor contracts for the 15 missing schemas

“Required” below means the concrete executor's existing precondition. It does not imply JSON Schema can encode non-empty strings: the prepared validator supports presence, types, enum, numeric minimum/maximum, arrays, nested objects, and `additionalProperties`, but not `minLength`, conditional schemas, or `default` (`internal/tools/prepared_registry.go:198-340,388-470`). Executor defaults remain runtime behavior; JSON Schema `default` would not apply a value.

All of these `Execute` methods currently ignore unrecognized keys unless noted. The proposed object schemas should be closed with `additionalProperties: false`; on the prepared model-call path this rejects those keys before policy, while a direct call to the raw executor may still ignore them. That is an observable boundary and is listed for root decision below.

`git_pr_create` is the one fixed extra with an existing schema. It declares required string `title`, `base`, `head`, optional string `body`, and `additionalProperties: false` (`internal/tools/git_pr_create.go:35-57`). Its executor rejects blank required values after trimming, uses a string body if present, and otherwise ignores unknown fields (`internal/tools/git_pr_create.go:60-104`). Thus the schema is presence/type closed but does not encode non-blank requirements; direct execution remains more permissive for unknown keys. It accepts no `labels` or `draft` fields. Do not add them based on the tool name or outside descriptions.

## Schema shape and smallest implementation slices

For each missing tool, add a `Parameters() any` method on the existing concrete type. No new `ToolDefinition` method or required interface change is needed. Use a root object schema for every tool. Use `additionalProperties: false` throughout; use `properties: {}` for no-argument controls (`task_list`, `goal_list`). Use only schema keywords accepted by the prepared validator. Declare required fields from the executor's existing hard preconditions, use their concrete Go JSON types, and declare only the exact action/category/status enums already present in source. Do not add length, URL-format, default-value, task-status, priority, or other constraints inferred from descriptions/comments when the executor does not enforce them.

Minimum implementation groups:

1. **Network reads and search control:** `web_search`, `web_fetch`, `tool_search`. Schemas are simple string objects; `tool_search.category` can use the canonical lowercase enum. Keep provider availability/auth/redirect handling owned by the pending WebSearch change (`167b9c7` + `80db3f9` worktree); add only the argument schema to `WebSearchTool` and rebase/integrate after that work lands. The schema does not assert that a real provider is configured or alter fetch URL safety.
2. **Task and goal stores:** `task_create/update/get/list`, `goal_create/update/get/list`. Keep task status and priority as strings because their current storage paths do not enforce enums. `goal_update.status` may publish the six canonical lowercase enum values; that intentionally makes the model-call schema stricter than the executor's accepted case/whitespace aliases, consistent with the accepted Find/Ls schema policy in the default-schema review.
3. **Action and UI controls:** `todo_write`, `enter_plan_mode`, `exit_plan_mode`, `ask_user`. `todo_write` needs one closed object with required `action` enum and the union of optional `id`, `content`, `status`, and `priority` fields. `ask_user.options` is an array of strings. The two plan-mode tools have one optional string each; preserve their current execution and policy semantics.
4. **Assembly/Loop handoff:** retain a real Assembly registry assertion and a Loop-to-model definition assertion for all 16 fixed extras, including already-schema'd `git_pr_create`. Verify that protected registry proxies preserve the `Parameterized` capability and that `tool_search` also retains `TopToolsProvider`.

## Validation order and parity questions for root

The handoff through dispatch already exists. `assembleApproval` wraps the deferred registry in `MiddlewareToolRegistry` and installs a shared prepared policy (`internal/cli/assemble.go:1064-1165`); `assembleLoopAgent` gives that same `s.tr` to Loop and enables tool filtering at threshold 30 (`internal/cli/assemble.go:1393-1483`). Registration snapshots a schema when the definition is registered; `newProtectedToolDefinition` reconstructs the `Parameterized` capability from that immutable snapshot (`internal/tools/trusted_registry.go:352-380`, `internal/tools/prepared_proxy.go:21-79`). `MiddlewareToolRegistry.Get/List` return those protected proxies (`internal/tools/middleware_registry.go:166-199`). Loop's `buildToolDefinitions` calls `List`, copies `Parameters()` into `llm.ToolDefinition.Parameters`, and caches by registry version (`internal/core/loop.go:295-339`); `defsToLLMTools` does the same for filtered definitions (`internal/core/loop.go:1511-1523`). At invocation, `prepareToolCall` validates the captured schema before the prepared policy is asked (`internal/tools/prepared_registry.go:46-133`). No second schema channel or proxy redesign is indicated.

Before the builder implements strict parity, root should decide whether the public model contract is allowed to be narrower than direct calls to `Execute`. Several current raw executors ignore unknown keys or silently ignore wrong-typed optional values; `additionalProperties: false` and typed schemas reject those calls in the prepared path. Required-string blankness also cannot be expressed in the current validator because `minLength` is unsupported, so a present-but-blank value passes schema validation and is rejected by the existing executor after policy. Keep the current implementation simple by testing closed schemas at the prepared boundary and asserting that every schema-accepted valid fixture is accepted by the concrete executor. If exact raw-executor parity is required in both directions, adding strict argument handling to those executors is a separate behavior change requiring an explicit decision.

`todo_write` has action-dependent requirements (`content` for `add`, `id` plus `status` for `update`, `id` for `remove`) that its current validator vocabulary cannot encode. The minimal schema can require only `action` and declare all action fields optional; the executor remains the conditional validator. If prepared schema rejection must match those conditional failures before policy, the validator's supported schema vocabulary must grow (for example `oneOf` or `if/then`) and must be reviewed as a separate prepared-schema contract change. Do not silently broaden that validator in this schema-only implementation.

Case/space aliases on `goal_update.status` and `tool_search.category` are accepted by direct execution but can be omitted from the JSON Schema enum to define canonical model input. The existing default-schema review documents the same deliberate boundary for Find/Ls enums. `ask_user.options` likewise should be declared `array<string>`; the raw executor currently drops non-string array members, while the prepared schema would reject them. Include these in parity tests as documented schema-versus-direct differences rather than accidentally changing executor behavior.
