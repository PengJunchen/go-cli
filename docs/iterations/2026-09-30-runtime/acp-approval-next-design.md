# ACP remote approval: next-design handoff

Status: proposal for design review only. This note does not amend the approved R6 contract, authorize implementation, or claim a supported ACP profile. The approved contract remains [r6-entrypoint-design.md](../2026-09-25-runtime/r6-entrypoint-design.md), reviewed as design-only in [r6-contract-review.md](../2026-09-25-runtime/reviews/r6-contract-review.md).

Source was rechecked on 2026-09-30 at develop commit eed9fff60bb552aab1d4d3fb1261a0d2a4ee942b. This note is bounded to the missing HTTP approval path and the production ownership/correlation needed to make that path safe.

## Frozen requirements

- The supported claim is only the private go-cli-acp-json/1 profile. Remote approval is an authenticated request/response roundtrip over task/session-scoped /events and POST /approval/respond.
- Bearer middleware supplies principal authority. A body principal_id is only a consistency check. sender_id is a display alias.
- An opaque, single-use approval_id is bound to principal, session, task, run, the assistant ordinal and ToolCallID, and the same prepared tool snapshot: trusted identity, registration generation, effects, schema, and normalized-argument digest.
- The event may include only a bounded, redacted tool summary; it must not expose raw args, credentials, schema, or digest. Decisions are allow_once or deny. Remote always_allow is not supported.
- Contract statuses are 200 accepted, 404 unknown/expired, 409 replay or stale target, and 403 principal mismatch. The existing auth middleware must reject missing/invalid Bearer credentials before approval lookup.
- No response denies the approval and cancels the call. Explicit adapter cancellation is owned by the exact R1 RunID; timeout or transport disconnect is not evidence of quiescence. A pending or quarantined owner must remain reachable.
- With --no-auth on loopback there is no authenticated remote approver. Ask is allowed only when the process has a local interactive owner; without that owner it fails closed.

These requirements are already stated in R6 design §§3, 5 and 9 and in the planned R6-BLD-02 acceptance. R6 contract review explicitly closed the private approval wire-shape finding. They should be carried forward unchanged.

## Current source gaps

At the reviewed commit, HTTPServer registers /connect, /send, /disconnect, /stream, and /events only (internal/acp/http_server.go:339-350). There is no /approval/respond handler and no approval.request producer. Its existing profile and Bearer middleware are reusable if the new route is registered behind the same chain.

POST /send (http_server.go:725-809) dispatches asynchronously on the server-generation context and returns an empty 200. It does not accept a request_id or return a task_id. The context carries principal_id and session_id but not a task owner or cancel handle. CoreHandler creates an acp-dispatch-N counter ID inside handleMessage (internal/acp/core_handler.go:443-481); it is neither server-random nor returned to the client. /events subscribes to the whole Session event ring (http_server.go:884-963); CoreHandler's forwarder publishes AgentEvents through task routes into that same session ring, so concurrent tasks can interleave.

/disconnect removes and closes the Session (http_server.go:811-837), but the asynchronous dispatch continues on the server-generation context. There is no run-targeted ACP cancel route. The R6 design's common cancel/drain rule (§9) requires an exact RunID owner and bounded cleanup; the current route cannot express that. Disconnecting /events correctly only closes that subscription and must continue to be treated as transport detach, not run cancellation.

Serve currently rejects ApproveAsk before Assembly (internal/cli/serve_cmd.go:105 and TestServeApproveAskRejectedBeforeTokenWriteOrListener). If this guard is merely removed, Assembly's Ask fallback installs InteractiveApprovalCallback over process stdin (internal/cli/assemble.go:318-341, 1189-1232; internal/approval/callback.go:47-105). Authenticated server Ask must inject a remote callback explicitly; it must never fall through to that stdin callback. ApprovalMiddleware's prepared path currently calls requestPreparedApproval with only ToolCall (internal/approval/prepared_policy.go:219, 270), despite already holding PreparedPolicyRequest. It correctly rechecks the captured generation after an allow (line 229). The lost snapshot and occurrence coordinates need a narrow, reviewable seam.

## Candidate handoff shape (not frozen)

The purpose of this candidate is to close the task bootstrap and owner-lifecycle gap while preserving the approved approval request/response body and status codes.

1. Extend the private /send request with a required client request_id, scoped to the authenticated principal and server session. Before returning, the server admits the dispatch, creates a cryptographically random task_id, binds a per-task cancel/owner record, and captures the current session event cursor. Preserve HTTP 200 for compatibility, but return a JSON acknowledgement such as {"version":"go-cli-acp-json/1","status":"accepted","principal_id":"subject-1","session_id":"session-1","request_id":"client-correlation-1","task_id":"random-server-task-id","event_cursor":16}. A repeated request_id with the same payload returns the original acknowledgement and never starts a second dispatch; reuse with a different payload returns 409. Keep this dedupe record bounded and scoped to principal/session.
2. The client opens /events?session_id=…&task_id=… using the acknowledgement's event_cursor as Last-Event-ID. Keep the existing session-wide monotonic event sequence, but tag each retained event with its task_id and filter delivery/replay to the requested task. Preserve explicit event_gap reporting for an expired session cursor; do not use the process-wide EventBus for this endpoint. Every event in the task projection carries the R1 RunID when the owner has created it. An initial dispatch/started event supplies the exact run_id before the client can request cancellation.
3. Add POST /cancel for an exact session_id/task_id/run_id target. Resolve those values through the authenticated server-side owner record; never accept a client-supplied principal as authority. Ask the matching R1 owner to cancel and wait only to the existing bounded cleanup deadline. Report the R1 status snapshot; use cleanup_pending or quarantined when quiescence is unproven and retain the owner. A request to cancel one task must not cancel other tasks in the session.
4. Define /disconnect as session teardown that stops admission and requests cancel/drain separately for every active RunID owned by that session, then returns the per-run terminal or pending/quarantined statuses. It must not delete owner records that still need cleanup. Repeated disconnect can observe the stable completion result. Closing an SSE response alone only detaches that subscriber.
5. Allocate one RemoteApprovalBroker before AssembleAgent. Inject it via an additive Assembly approval-callback option for authenticated --approve ask, and hand the same instance to HTTPServer for POST /approval/respond. The broker publishes through the dispatch's task-scoped event sink and stores the pending response channel with trusted owner identity. This avoids a constructor cycle and prevents server Ask from reading stdin. Keep the existing callback path for local REPL/TUI.
6. At the prepared-policy seam, pass an additive prepared-approval request containing the immutable PreparedPolicyRequest and trusted occurrence coordinates. The Loop already knows assistantOrdinal (internal/core/loop.go:749) and passes it to executeSequentialCall/executeParallelGroup, but runCommitConsumer.prepareInvocation drops it (internal/core/run_commit_consumer.go:532-565); FrozenToolCall contains the exact call ID. Preserve the R1 RunID from context. The broker binds the pending ID to this exact tuple and snapshot, returns only AllowOnce or Deny, and does not retain a registry/policy lock while it waits. The existing post-wait fence comparison remains mandatory before a prepared invocation can dispatch.
7. The response handler obtains principal_id from the authenticated request context, validates the body consistency field and every session/task/run target against the pending server record, then atomically consumes it exactly once. Do not hold locks while waiting for the user's response. Unknown/expired IDs return 404, a consumed ID or changed owner/generation returns 409, a principal mismatch returns 403, and invalid/missing auth is rejected by middleware. Neither malformed input nor any rejected response may reach Dispatch.

The example acknowledgement and run-targeted cancel endpoint above are proposals, not part of the frozen profile yet. The approved design does not currently specify how a caller learns a server-generated task_id before subscribing to a task-scoped event stream, nor does it give a concrete ACP /cancel wire shape or how /disconnect handles multiple active tasks. A designer should accept or replace those details before a builder changes behavior. The approved design also requires expires_at and a timeout but does not set its duration. Candidate policy for discussion: start a 120-second timer when the approval request is published; timeout returns Deny for that prepared call, so it can never dispatch and sibling calls are unaffected. Explicit cancellation of an entire model run remains a separate RunID-owner operation. Confirm whether that distinction matches the intended meaning of “cancels the call”; do not infer that approval expiry cancels the whole RunID. Approve or replace the duration and its configuration bounds before implementation; never permit an unbounded pending approval.

## Ownership and prerequisites

- Run the broker as a concurrent server-side owner, not as an event-cache lookup. Store the owner tuple, expiry, immutable prepared snapshot, one-use state, and a reply channel in memory. Use an injected clock/ID source for deterministic tests. Bound pending entries; reject overload without spawning one goroutine per approval.
- Redact the summary from the same prepared snapshot used for policy. Use R4-safe display metadata; do not construct it by serializing args. The approval event should remain no more revealing than the approved minimum data shape.
- Authenticated serve currently configures the fixed subject cli; this design remains single-subject, not multitenant. Cross-subject checks still belong in middleware and pending-owner validation. In --no-auth mode, do not expose an effective remote response capability; use a real local interactive owner or fail closed before provider/listener startup.
- Keep TaskID distinct from RunID: TaskID is random per external dispatch; RunID comes from the R1 owner. Carry the trusted task/session/principal scope in context into CoreHandler and its dispatcher. Disconnect, explicit cancel, server Stop, and approval expiry must reach the appropriate owner; subscriber EOF only detaches transport.
- R6-BLD-02 is in progress and depends on R4-REV-01 and R2-REV-01 (execution-tasks.json:1443-1485). R4-REV-01 remains pending (line 1224); the execution status still records R2-REV-01 as open (execution-status.md:80). Keep this handoff proposal-only until those review gates close. Do not infer missing effect/capability policy or persistent-session recovery from the adapter.

The remaining design decisions are protocol/runtime details, not a request to change the accepted authorization policy: approve the /send correlation acknowledgement and retry semantics; choose the explicit run-cancel and multi-task /disconnect behavior; set a bounded approval TTL and settle whether expiry denies only that call (recommended) or cancels its whole RunID. Record the chosen values in a reviewed design revision before implementation.

## Executable acceptance plan

Keep the acceptance name already planned by R6-BLD-02: TestACPRemoteApprovalRoundTrip. Use a real local HTTP client/server and the real serve subprocess/default Assembly/provider factory required by R6 design §11, with only the model/tool peer and clock/ID source controlled. The action fixture should traverse the actual prepared policy and executor path.

- Positive allow_once: receive the /send acknowledgement, subscribe at its task_id/event_cursor, observe exactly one approval.request with matching subject/session/task/run/call coordinates, respond, assert 200 accepted and that the exact captured prepared executor runs once.
- Deny, no response, and expiry: assert no executor side effect. Use a fake clock to assert expiry at the approved TTL; verify timeout affects only the owner run and leaves pending/quarantined state when R1 has not proven cleanup.
- Redaction: put distinct canaries in raw args, credential, schema and normalized digest; assert none appear in SSE JSON, acknowledgement, HTTP errors, logs, or traces. The bounded safe summary is present and understandable.
- Target/status matrix: invalid/missing Bearer -> 401 before lookup; body principal mismatch -> 403; unknown/expired ID -> 404; replay and changed generation/owner -> 409. Try cross-session, cross-task, cross-run, changed call ID, another same-name call at a different assistant ordinal, and remote always_allow; none may dispatch.
- Isolation/races: two concurrent tasks in one session and tasks across sessions each get only their own events/approval response. Race response, timeout, run cancellation, generation replacement and server Stop; one pending ID has at most one winner, locks are not held while waiting, and race tests prove all dispatch work is joined or reported pending/quarantined.
- Cancellation: explicit /cancel targets one exact RunID; disconnect drains only runs owned by that session and preserves incomplete owners; SSE EOF only detaches. Verify R1 outcome/execution_state/event_gap_count, bounded cleanup, and no false quiescent/cancelled report.
- Update TestServeApproveAskRejectedBeforeTokenWriteOrListener into authenticated Ask-wiring coverage. Keep a no-auth case proving that only an actual local interactive owner can answer; non-TTY/headless Ask fails closed before listener/provider activity. Verify invalid auth does not create or resolve pending approvals.

Do not call this implementation-complete from unit tests alone. Separate package race tests, actual local CLI journey, wire transcripts, and any unverified R2/R4 dependency evidence. The existing R6 requirement already names TestACPEventsIsolatedByTask, TestACPRemoteApprovalRoundTrip, exact response fields, stale/replay/expiry/cross-owner rejection, timeout, and always_allow rejection (execution-tasks.json:1455-1457; r6-entrypoint-design.md:107-115).
