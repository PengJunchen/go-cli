## Durable compaction

### P1 — Per-request unknown gate conflicts with the accepted safe-read recovery contract

The new rule runs ValidateCompactionEligible before every durable main-model request, including requests below the compaction threshold, and says an unknown receipt may not be sent in the next main request (durable-compaction-design.md:85,105-107). That expands the original compaction rule into a blanket request-admission rule.

The accepted R3 contract treats unknown as a terminal receipt, not a malformed/open tool group: its outcome does not change group closure, and unknown side effects must not be replayed (2026-09-25-runtime/r3-compaction-design.md:9,40). The accepted R2 contract separately permits a trusted read during a conflicting mutation quarantine when both effect and enforced path scope are positively proven, and requires TestRecoveryAllowsSafeReadWhileWorkspaceQuarantined (r2-contract.md:32,198,225). A fresh user request is a new operation; retaining a closed prior unknown receipt as unchanged context is not replaying its assistant tool call. Blocking that model request prevents the runtime from even proposing the permitted safe read.

Current-source evidence does not justify the broader gate. SessionView preserves a complete unknown receipt in recovered PublishedView (internal/session/durable_recovery_test.go:209-224); NewSessionRunCommitSink captures and validates that view without rejecting unknown receipts (internal/session/run_commit.go:64-94). WorkspaceQuarantineIndex currently blocks every new action because it has no R4 trusted-effect/path-scope permit yet (internal/session/workspace_index.go:274-278); docs/iterations/2026-09-25-runtime/execution-status.md:80 records that limitation and says the R2 exception is pending proof/wiring. This is an implementation gap in the tool-admission seam, not an accepted rule that the provider cannot receive a fresh request with that history.

**Required correction:** split source/group integrity for ordinary request admission from compaction eligibility. A complete historical unknown group may be passed unchanged on a fresh operation when no compaction is attempted; the same-operation post-action continuation/replay remains denied, and R2/R4 still controls whether any resulting tool invocation may dispatch (trusted read plus real path scope only while quarantined). Unknown receipts must never be summarized, placeholder-rewritten, truncated away, or treated as known. Keep missing/open/malformed groups fail closed. If compaction is attempted and its replacement region would include an unknown receipt, reject before calling the summarizer; do not reject the fresh request merely because the unchanged history contains one.

Add a RED using a recovered PreparedSession/SessionRunCommitSink view with a complete unknown receipt and an active unresolved workspace marker. A new, below-budget user request must reach the main model with the prior assistant/tool group unchanged and make no compaction/summarizer call; a positively proven scoped read may pass the R2/R4 gate while mutation remains denied. Also assert that replaying the prior action in the same operation is denied. The current index cannot pass the safe-read half until its trusted scope permit is wired, so record that as an explicit R2/R4 prerequisite rather than claiming it already works. A separate over-budget RED must show an attempted summary cannot include the unknown group and invokes the summarizer zero times.

### P2 — PendingRunInput cannot satisfy the declared source union

SourcePendingRunInput requires both RunID and PriorSourceCount (durable-compaction-design.md:29-47), and SourceRunTranscript also requires PriorSourceCount. But the Agent API says the initial input is marked only as PendingRunInput{RunID}; it does not specify where the required count is attached or copied to the writer-assigned RunTranscript (line 65). The compaction cursor then has no declared source for the prior-prefix length when the first current-run transcript item is covered (line 97).

**Required correction:** persist the exact prior count on AgentImpl when SetHistoryFromSourceSnapshot validates the sink snapshot, using that snapshot's one-to-one SourceEntryIDs count. AgentImpl.Run must stamp PendingRunInput{RunID, PriorSourceCount}; the canonical writer transition to RunTranscript must preserve the same count while adding its exact TranscriptIndex. Every subsequent current-run transcript source uses the same immutable count. Do not derive it from compacted items or Agent.History length.

Add TestPendingRunInputCarriesExactPriorSourceCount: vary prior history length, include a restored compaction marker, sync initial input, and assert the resulting RunTranscript has the captured source count and exact index; then compact across it and verify the resulting Through maps through the same sink baseView.

The API is otherwise sufficient and appropriately scoped: returning the sink's existing defensive baseView clone avoids a second ledger; the typed CompactionResult with Items, Strategy, and NewProjection reports the real cut; suffix equality validates preservation without guessing the cut; and the explicit rejection when a second same-run cut retains a synthetic summary is conservative and testable. Retain those parts.

## Attempt accounting

### P1 — The retry predicate excludes two required typed transitions

CandidateFailure distinguishes FailureOverflow and FailureBuild from FailureTransientProvider (attempt-accounting-design.md:44-50,83-92). Yet AuthorizeCandidate requires a previous transient-provider terminal (lines 212-216). The stated OperationKind/candidate reasons include overflow and cycler-primary (lines 33,44-64), and the design requires overflow retry, selected-to-primary fallback, and pre-dispatch setup-failure proposals (lines 194,198,220,241-253). As written:

- A genuine FailureOverflow result is not FailureTransientProvider, so the overflow-triggered compact-and-retry permit has no allowed policy branch.
- A FailureBuild/setup failure has no AttemptID by definition. The draft does allow its notice to retain a prior dispatched PreviousID, but its authorization predicate requires that referenced attempt's terminal/failure classification to match the proposal failure; a setup failure cannot be the terminal result of that prior dispatch. The draft therefore both requires a typed setup proposal and makes it ineligible unless the cause and prior attempt are modeled separately.
- CandidateFailure currently combines the failure class with PreviousID. After a transient failed request, a later candidate build failure is a different event from that finished attempt's immutable terminal; the proposal must not appear to claim that the previous attempt itself had FailureBuild.

**Required correction:** make the proposal antecedent a typed tagged union separate from candidate selection reason: `Initial`; `FinishedAttempt{AttemptID}` for a transient retry/failover; `FinishedOverflow{AttemptID}` for the one context-limit path; or `PreDispatchFailure{FailedCandidateID, FailureBuild, PreviousAttemptID?}`. The optional previous ID remains the actual prior dispatch and is never relabeled as the build failure. The owner accepts `FinishedAttempt` only after the immutable result and safety facts pass; it accepts `FinishedOverflow` only after Loop records successful compaction (and, for durable mode, projection sync); and it accepts `PreDispatchFailure` only for explicitly allowed initial/cycler-primary/failover candidate selection. A pre-fence setup failure creates no new AttemptID and cannot authorize a second attempt of the same failed candidate. `ContinuationNoReplay` denies every automatic fallback after its initial candidate. If the accepted R3 “at most one overflow compaction-and-retry” bound remains in force, record and test that per-operation bit in addition to the shared HTTP dispatch cap.

Add REDs for (1) typed FailureOverflow, successful compaction/projection sync, and authorized next candidate; failed sync means no permit/request; (2) selected-candidate BuildFailure before any HTTP request, proving the documented allowed/denied primary transition and no fabricated attempt; (3) a later candidate BuildFailure retains the prior actual AttemptID/class separately; and (4) the same build failure under ContinuationNoReplay denies the primary. Keep assertions on httptest counts and the exact AttemptIDs/results.

### P1 — Historical unknown receipts need the same operation scope as compaction

AuthorizeCandidate says any unknown/pending receipt denies a permit (attempt-accounting-design.md:218,220), but the same authority is also required for the initial candidate of every operation (lines 194,212). Without a scope distinction, a fresh user operation whose PublishedView contains a complete old unknown receipt can never issue its initial main-model request, even if the request only needs the R2-permitted trusted read. This duplicates the request-gating conflict above at the attempt authority.

**Required correction:** scope the no-replay denial to a current operation's unresolved action/tool state and subsequent retry/replay. A new operation's initial candidate may use a validated historical closed unknown receipt unchanged as context; R2/R4's prepared executor and quarantine permit still deny untrusted or mutating tool dispatch. Do not let an old receipt become a retry terminal or an attempt of the new operation. Add an initial-candidate RED for the safe-read recovery case and a separate same-operation retry RED that remains denied.

### P2 — Standalone provider builds need an explicit dispatch mode

The revised API requires every adapter call to consume a Loop-issued permit immediately before client.Do (attempt-accounting-design.md:194-202), but it does not define the no-resolver direct-build path. EinoProvider.Build is an exported direct constructor (internal/llm/provider.go:145-169), and current compatible/native tests build a provider model and call Generate without a resolver or operation (internal/llm/provider_test.go:62-70; internal/llm/native_test.go:91-96). ModelResolver.ResolveModel currently returns ResolvedModel and ResolvedModel.Build delegates to the provider; the new candidate-handle issuance is not present in that source yet (internal/llm/model_resolver.go:111-128,145-153).

**Required correction:** choose one construction rule: all exported direct provider `Build`/`BuildModel` APIs, including Eino and native adapters, are deliberately unbound one-call library paths outside the Loop operation guarantee; every model built from a resolver-issued `ResolvedCandidateHandle` is permanently guard-required. The built model's mode is fixed at construction, never inferred from missing context. The resolver assigns a unique opaque CandidateID and binds actual provider/model/protocol, endpoint, and credential scope into the private handle; `ResolvedModel.Build` passes that handle into guard-required adapter construction. Default CLI assembly, retry/failover, and cycler selected/primary must use only those guarded builds. No resolver handle in a production Loop operation is a typed setup failure, not permission to fall back to the direct library path. Guard-required adapters reject missing, mismatched, or consumed permits before `client.Do`.

Executable REDs: existing direct-build behavior follows the chosen explicit contract; an assembled guarded candidate with no permit makes zero HTTP requests; a mismatched or consumed permit makes zero additional requests; resolver-built candidates for primary, small-model summary, failover, and cycler each carry the actual identity without exposing URL/credentials.

### P2 — Actual-dispatch cap does not bound pre-dispatch candidate proposals

The draft correctly says build/setup failures do not consume MaxAttempts because no client.Do fence was crossed (attempt-accounting-design.md:196,198,215-216). There is no separate rule preventing a wrapper from proposing the same candidate repeatedly after the same pre-dispatch setup failure. Thus the dispatch cap alone does not bound the proposal/selection loop.

**Required correction:** make an immutable finite candidate set part of the operation-authority input (for example, pass a resolver-issued `CandidateSet` to `NewOperation`), containing configured primary/failover handles and, for a cycler, its distinct selected/primary handles. Reject proposals outside this set. Actual transient dispatch retries may reuse a handle only under the shared MaxAttempts budget; pre-fence setup failures do not consume that budget, so count them separately and reject a repeated setup-failed CandidateID within the operation. This bounds proposals by dispatched-attempt allowance plus the finite set size without preventing an authorized retry of the same model. Do not add a free-form callback that can mint handles. If the resolver cannot enumerate the set before entering the wrapped call, add one bounded resolver method that returns handles in policy order. Do not mint AttemptIDs for pre-fence failures.

Add TestRepeatedPreDispatchFailureCannotLoop: all configured candidates fail before the fence; assert the number of distinct proposals is bounded by the resolved candidate set, HTTP requests and attempt rows remain zero, and the operation terminates with typed setup failure.

The core API direction is implementable without putting accounting in session: RunOperationFactory scopes state per Loop request; proposal data omits wrapper-authored visibility/ack/join booleans; Loop reads those facts from its event, tool, RunCommit, and joined-attempt owners; the one-shot permit is bound to an actual resolved handle; and the adapter allocates AttemptID at the real fence. Keep Summary as a separate operation on the same attempt/cost sink with explicit unknown usage, while preserving one breaker call per logical chain.

## Handoff

Neither current revision is ready for builder acceptance. The compaction author should make the fresh-request/safe-read distinction and stamp PriorSourceCount from the captured source snapshot. The attempt author should enumerate allowed transient/overflow/setup transitions, apply the same fresh-operation versus replay distinction, declare direct-build mode, and bound non-dispatch candidate proposals. These are targeted contract fixes; no new persistence framework or broad redesign is needed.
